# Telegram-секретарь: подключение, архив, саммари и автоответчик

Node.js backend на `@daevox/framework` обслуживает страницу `/telegram`.
Транскрибация и перевод видео работают в [отдельном FastAPI-сервисе](../transcription-backend/README.md).

Backend слушает `127.0.0.1:3000`. Экран подключения работает без входа в Daevox.
`GET /healthcheck` проверяет только доступность backend; отсутствие настроек Telegram не мешает
healthcheck и `GET /api/telegram/state`.

## Подготовка

1. Использовать Node.js 26 с `node:ffi` и npm 12. Установить зависимости из корня: `npm install`.
2. Подготовить закреплённую TDLib: `npm run build -w @daevox/tdlib`.
   Системные требования описаны в [README TDLib](../../lib/tdlib/README.md).
   Если соответствующий native artifact уже собран, повторная сборка не нужна.
3. Скопировать корневой `.env.example` в `.env` и заполнить локально:
   - `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` — реквизиты собственного Telegram API-приложения;
   - `TELEGRAM_DATABASE_KEY` — стабильный ключ из 32 случайных байтов в base64;
   - `TELEGRAM_DATABASE_DIRECTORY`, `TELEGRAM_FILES_DIRECTORY` — разные абсолютные пути вне
     репозитория. TDLib создаёт и использует их постоянно. Не направлять два процесса на одну базу.
4. Сохранить ключ и каталоги между запусками. Не передавать реквизиты и ключ в браузер или чат.
   `.env` исключён из Git. Сессия хранится вне репозитория; удаление её файлов не заменяет выход.
5. Архив секретаря хранится в `db/daevox.sqlite` в корне репозитория. URL файла задаётся
   через `DATABASE_URL` в `.env`, например `file:///absolute/path/to/daevox-platform/db/daevox.sqlite`.
   Перед первым запуском и после изменения схемы выполните `npm run db:push` из корня.
   Схема и запросы используют Drizzle; backend не выполняет миграции при запуске.
   Подробности: [пакет базы](../../packages/db/README.md).

Пример локальной генерации ключа (вывод вставить только в `.env`):

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

## Запуск

В двух терминалах из корня:

```sh
npm run dev -w @daevox/backend
npm run dev -w @daevox/web-client -- --host 127.0.0.1
```

Открыть `http://127.0.0.1:5173/telegram`. Для других портов согласованно изменить `PORT`,
`WEB_CLIENT_ORIGIN`, `API_PROXY_TARGET` в корневом `.env` и порт запуска web-client.
Frontend отправляет относительные запросы `/api/*` на свой origin. Vite перенаправляет их в backend
по `API_PROXY_TARGET` (по умолчанию `http://127.0.0.1:3000`), поэтому браузеру не нужны CORS и preflight.
`VITE_API_BASE_URL` больше не используется. Dev-сервер по умолчанию слушает `127.0.0.1:5173`
и не переключается автоматически на другой порт.

Vite меняет Host на адрес backend и сохраняет исходный Origin. Проверка локального Host/Origin
в backend остаётся: `WEB_CLIENT_ORIGIN` должен совпадать с адресом frontend, включая
`localhost` / `127.0.0.1`. Для production-сборки нужен reverse proxy `/api/*` на backend
под тем же origin, поскольку Vite dev proxy там не работает.

Нажать «Подключить Telegram», отсканировать QR в Telegram → Настройки → Устройства → Подключить
устройство. При наличии 2FA ввести пароль на экране. QR кодируется локально; пароль очищается
после отправки. Native-логи выключаются до передачи параметров авторизации.

Штатная остановка через SIGINT/SIGTERM сохраняет сессию. «Отключить аккаунт» вызывает `logOut`;
успех отображается после `Closed` и освобождения клиента. При отсутствии сети нужно дождаться
Telegram. Перезапуск может продолжить записанный TDLib выход, но приложение само не хранит и
не повторяет это намерение. Фатальная ошибка требует явного перезапуска подключения.

## История и суммаризация

При включении наблюдения секретарь автоматически загружает доступную историю за последние
30 дней через `getChatHistory` (до 100 сообщений в запросе). Курсор и страницы сохраняются
транзакционно; после перезапуска загрузка продолжается, выключение наблюдения останавливает
дальнейшее сохранение страниц. Защищённое содержимое не архивируется.

После завершения импорта создаются постоянные задачи по дням в `daily_summaries`.
Граница дня — время Алматы (UTC+5). `SummaryScheduledTask` проверяет очередь каждую секунду
через scheduled tasks API framework и запускает `SummaryJob` в общем Worker Pool приложения.
Job открывает своё SQLite-соединение и обрабатывает дни последовательно; framework исключает
перекрытие запусков и передаёт сигнал отмены при остановке приложения.
`SecretaryRefreshTask` обновляет каталог раз в минуту; обновления при старте и событиях Telegram
выполняются сразу. Большие дни разбиваются на части,
затем промежуточные сводки объединяются. Лимита 200 сообщений у автоматических дневных сводок нет.
Незавершённые задачи после перезапуска возвращаются в очередь; ошибки можно повторить из интерфейса.

Кнопка «Сводки» в чате показывает результаты, очередь и прогресс по датам. Разовая сводка по запросу
дополнительно доступна для последнего обновления или последних 200 сообщений (до 24 КБ текста).

В корневом `.env`:

```dotenv
LLAMA_BASE_URL=http://127.0.0.1:8080/v1
LLAMA_MODEL=
```

Если `LLAMA_MODEL` пуст, модель определяется через `/v1/models`. Пакет `openai` используется
только на backend с Chat Completions API локального llama-server. `LLAMA_API_KEY` необязателен
и нужен только если на локальном сервере включена авторизация. Ключ OpenAI не используется.

Схема очереди применяется командой `npm run db:push`. Результаты сохраняются в архивной SQLite-базе.

## Проверки

```sh
npm run verify -w @daevox/telegram-contract
npm run verify -w @daevox/backend
npm run verify -w @daevox/web-client
npm exec -w @daevox/web-client -- playwright install chromium
npm run test:e2e -w @daevox/web-client -- telegram.spec.ts auto-reply.spec.ts theme.spec.ts
npm run verify -w @daevox/tdlib
npm run lint
npm run format:check
```

Browser e2e запускает отдельный HTTP backend с управляемым transport TDLib на `127.0.0.1:3001`
и web-client на `127.0.0.1:5174` с Vite proxy на тестовый backend; эти порты должны быть свободны. Тестовый entrypoint не загружается
production bootstrap. Реальные реквизиты и сессия в тестах не используются. Трассировка браузера
отключена, чтобы не сохранять тела запросов авторизации.

Приёмка реального аккаунта выполняется по [спецификации](../../.scratch/telegram-qr-auth/spec.md):
ротация QR, вход с существующей настройкой 2FA, повторное открытие страницы, перезапуск backend,
выход с проверкой сессии в Telegram, повторный вход. Native offline smoke и автоматические сценарии
не заменяют ручной прогон.

## Автоответчик Telegram

В выбранном чате включите «Автоответчик». Это также включает наблюдение; затем его можно выключить
независимо. При явном включении в чат отправляется «ИИ-секретарь: автоответчик подключён к этому чату.»,
при выключении — «ИИ-секретарь: автоответчик отключён от этого чата.». Это отдельные сообщения без Reply
и без обращения к модели. Повторное сохранение того же положения, перезапуск и восстановление связи
не создают уведомлений. Уведомления одного чата отправляются в порядке переключений, без оплаты и
смены автора; при ошибке настройка сохраняется, причина видна в интерфейсе. Неопределённую отправку
не повторяем и не досылаем уведомления после завершения сессии.

Автоответы выполняет backend, поэтому открытая вкладка не нужна. После явного выхода
из Telegram требуется повторное включение. Перед запуском обновлённого backend примените схему
через `npm run db:push`: добавлены `auto_reply_settings` и `auto_reply_intents`.

Используется существующий `llama-server` и переменные `LLAMA_*`. `ModelScheduler` последовательно
обслуживает модель: текущая дневная или ручная сводка завершается, ожидающие автоответы имеют
приоритет перед следующей сводкой. Scheduled task передаёт worker одну дневную задачу за запуск.
Запускайте один backend на один архив и Telegram-сессию.

Источник — готовая сводка за самый поздний день выбранного чата и аккаунта. Известные изменения
исходных сообщений исключают старый результат до обновления. Если сводки нет, ставится задача
за самый поздний день с доступным текстом. Завершение подготовки не вызывает второй ответ.
Содержательные ответы и перевод служебных фраз выполняет локальная модель; подпись и Reply
формирует backend. Без текста или при неопределимом языке используется русский. При отказе модели
аварийная фраза выбирается по распознаваемому письму/словам (`errorPhrase`); если язык не определён,
используется русский. Качество определения языка и содержания проверяется отдельно с реальной моделью.

В журнале хранятся исходный срок (пять минут), версия сообщения, период обработки, версия настройки,
Reply/тема в JSON входящего, состояния и идентификаторы доставки. После завершения содержимое
входящего и подготовленного ответа очищается; идентичность намерения остаётся для защиты от дублей.
Неопределённая доставка автоматически не повторяется. После перезапуска ожидающие намерения
отменяются, переданные Telegram отмечаются как неизвестные. Это не гарантия exactly-once Telegram.

Новые входящие допускаются только после `connectionStateReady`, получения аккаунта и включения чата.
Сообщения с временем не позднее границы обработки пропускаются, включая пограничную секунду.
Используются часы backend; держите системное время синхронизированным. История и импорт не являются
источником автоответов. Очередь ограничена 1000 активными намерениями; внутри чата сохраняется порядок,
между чатами применяется круговое обслуживание. Права приостановленных чатов проверяются раз в секунду
после обработки доступной очереди. После восстановления отменяется накопленное и принимается только новое.

В интерфейсе различаются включённая настройка, подготовка, недостаток данных, ошибка и приостановка.
Причина последнего пропуска или неизвестной доставки видна рядом. Каналы, секретные чаты, недоступный
Reply/тема, платная отправка и авторство от имени чата блокируют отправку. Выбранный автор Telegram
не меняется автоматически. При снятии препятствий неотправленная очередь не досылается.
