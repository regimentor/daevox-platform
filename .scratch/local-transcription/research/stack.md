# GPU-транскрибация: факты и кандидаты стека

Дата проверки: 2026-09-10. Исследование для карты «Локальная транскрибация аудио, видео и YouTube». Это рекомендации для дальнейшего решения, не утверждённая спецификация. Пакеты и веса не устанавливались, inference не запускался.

## Граница достоверности

Локальные факты взяты из Notes карты: RTX 5080 и RTX 4070 Ti обнаружены, CUDA из окружения агента недоступна; объём доступной VRAM, время работы и качество на пользовательских записях не измерены. Само наличие драйвера не подтверждает доступность устройства из процесса сервиса.

NVIDIA относит RTX 5080 к compute capability 12.0, RTX 4070 Ti — к 8.9. Название «Blackwell» без проверки конкретной архитектуры и бинарной сборки недостаточно. [Таблица NVIDIA](https://developer.nvidia.com/cuda/gpus).

## Матрица совместимости

| Кандидат | RTX 5080 | RTX 4070 Ti | Python / библиотеки | Вывод для решения |
| --- | --- | --- | --- | --- |
| faster-whisper + CTranslate2 4.8.2 | Предмет проверки на sm120; исходный режим FP16 | Предмет проверки на sm89; FP16, затем int8_float16 | faster-whisper требует Python ≥3.9; CTranslate2 добавил Python 3.14 в 4.6.1 | Основной кандидат: сегментный Python API и локальные веса |
| CTranslate2 до 4.6.3 | Не брать за исходную основу для нового стека | Возможен, но нет основания выбирать старую ветку | В 4.6.3 добавлена поддержка CUDA 12.8 | Фиксировать точную современную сборку, а не произвольный CUDA 12.x |
| Whisper через PyTorch | PyTorch 2.7 официально добавил Blackwell и CUDA 12.8 wheels | CUDA-кандидат для Ada | Требуется отдельная согласованная матрица Python/PyTorch/Whisper | Запасной путь при проблемах CTranslate2, не второй обязательный движок |

Основания: [faster-whisper](https://github.com/SYSTRAN/faster-whisper), [релизы CTranslate2](https://github.com/OpenNMT/CTranslate2/releases), [PyTorch 2.7](https://pytorch.org/blog/pytorch-2-7/).

Рекомендуемая отправная точка: Python 3.12 под uv, faster-whisper с точной версией в lock, CTranslate2 4.8.2, CUDA runtime/cuBLAS 12.8 и проверенная cuDNN 9 при использовании сборки с cuDNN. Python 3.12 — консервативный выбор для всей цепочки native wheels, не утверждение, что установленный 3.14 несовместим. Полный uv resolve и проверка wheel-артефактов здесь не выполнялись.

Документация расходится: README faster-whisper требует CUDA 12/cuDNN 9, страница установки CTranslate2 всё ещё упоминает cuDNN 8, но релиз 4.6.3 вводит собственный CUDA Conv1d и делает cuDNN необязательной. Поэтому наличие/отсутствие зависимости нужно проверять для выбранного wheel, не переносить старую инструкцию вслепую. [Установка CTranslate2](https://opennmt.net/CTranslate2/installation.html), [релизы](https://github.com/OpenNMT/CTranslate2/releases).

В 4.6.2 INT8 отключался для sm120; в исходнике v4.8.2 проверка `gpu_supports_int8` снова допускает major >6, исключения sm120 нет. Это не локальный benchmark: FP16 рекомендуем как исходный режим, INT8 сравниваем отдельно по качеству, скорости и памяти. [Исходник v4.8.2](https://raw.githubusercontent.com/OpenNMT/CTranslate2/v4.8.2/src/cuda/utils.cc).

## Модель и память

Whisper large-v3 и turbo — мультиязычные кандидаты; выбирать `.en` для общей RU/EN-функции нельзя. Turbo оптимизирован на скорость с небольшим снижением точности относительно large-v3 по описанию авторов. Таблица оригинального Whisper оценивает large примерно в 10 GB VRAM, turbo — 6 GB; это ориентиры другого backend, а не обещание для CTranslate2. [Whisper](https://github.com/openai/whisper).

У faster-whisper опубликован пример large-v2 FP16 около 4.5 GB, INT8 около 2.9 GB на RTX 3070 Ti. Эти числа не доказывают расход large-v3 на здешнем GPU. [Benchmark](https://github.com/SYSTRAN/faster-whisper). Предлагается сначала large-v3 FP16 без batching как точка сравнения качества; turbo — альтернатива после проверки RU/EN. Скорость обработки трёх часов и выбор основной карты пока не установлены.

## Ленивый запуск и длинный материал

`WhisperModel` скачивает модель по имени при создании; есть `download_root`, `local_files_only` и `revision`. Загрузка в GPU происходит при конструировании CTranslate2-модели. Поэтому рекомендуем создавать объект только после принятой команды UI, отделив скачивание весов от загрузки в GPU. В startup/lifespan не создавать модель. [Исходник](https://raw.githubusercontent.com/SYSTRAN/faster-whisper/master/faster_whisper/transcribe.py).

API выдаёт генератор сегментов с началом, концом и текстом; есть word timestamps и VAD. Итерацию нельзя заменять накоплением `list(segments)` перед публикацией. [faster-whisper](https://github.com/SYSTRAN/faster-whisper).

Генератор сегментов не означает потоковое чтение файла: путь декодируется до создания генератора. `log_progress` управляет tqdm, отдельного публичного progress callback в исследованном исходнике нет. [Исходник](https://raw.githubusercontent.com/SYSTRAN/faster-whisper/master/faster_whisper/transcribe.py).

Расчёт: три часа mono 16 kHz float32 — 691 200 000 байт (~659 MiB) только waveform; features, копии/VAD и декодирование добавляют память. Рекомендуем отдельно испытать трёхчасовую запись как контрольный сценарий, а не максимальную разрешённую длительность; при неприемлемом RSS/долгом молчании UI выбрать ограниченные чанки с контекстом и проверкой стыков. Это дальнейшее решение, не скрытая гарантия streaming.

Измеримость по этапам: upload — переданные байты; YouTube — download hook при известном размере; подготовка — FFmpeg progress; inference — обработанная позиция записи, а не оставшееся время. `segment.end / duration` годится как приблизительная позиция текста, но не точный счётчик обработки: тишина и VAD дают скачки. Для точного продвижения через тишину потребуется учёт завершённых окон/чанков. Загрузка модели может оставаться неопределённым индикатором; нельзя рисовать выдуманный процент.

FFmpeg поддерживает машинный `-progress pipe:1` с периодом через `-stats_period`; `-debug_ts` не предназначен для стабильного парсинга. Это подходящая граница subprocess для нормализации аудио. [FFmpeg](https://ffmpeg.org/ffmpeg.html).

## Публичный YouTube

yt-dlp поддерживает Python ≥3.10. Для полной поддержки YouTube теперь нужны yt-dlp-ejs и JS runtime; Deno рекомендован, Node поддерживается, но его требуется явно включить. ffmpeg/ffprobe рекомендованы; Python API имеет progress hooks. [yt-dlp](https://github.com/yt-dlp/yt-dlp).

Рекомендация: получать аудиопоток одной публичной записи, измерять duration до скачивания и после декодирования для прогресса, без программного ограничения длительности. Не считать публичность гарантией доступности: извлечение может завершиться ошибкой, ограничения провайдера должны попасть в состояние операции. Политика live/playlist и требования к ошибкам остаются продуктовым решением. Очередь не требуется для работы одного subprocess.

## FastAPI, события и интеграция

FastAPI прямо предупреждает, что тяжёлые фоновые вычисления могут требовать отдельного процесса/инструмента вместо простых BackgroundTasks. [Background tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/). Рекомендация для одного локального GPU: один владелец модели в отдельном worker-процессе с ограниченным каналом событий; FastAPI обслуживает HTTP и состояние. Это не очередь пользовательских заданий. Простое `async def` не делает синхронную GPU-итерацию неблокирующей. Число HTTP workers не должно неявно умножать модели или разрешать конкурентный старт.

FastAPI с 0.135.0 имеет native SSE, `ServerSentEvent`, поля `id`/`retry` и обработку `Last-Event-ID`. [SSE](https://fastapi.tiangolo.com/tutorial/server-sent-events/). Рекомендуем POST для запуска и GET SSE для событий. Reconnect требует собственного сохранения событий или snapshot + cursor: заголовок сам не воспроизводит потерянные данные. Обновление страницы также требует восстановления идентификатора операции; отключение клиента не должно неявно останавливать worker. Пользователь уточнил: закрытие вкладки не прерывает обработку, возврат восстанавливает текущий прогресс; история и восстановление после backend restart отложены.

В текущем коде `apps/web-client/app/routes.ts` содержит home и telegram; `apps/web-client/vite.config.ts` отправляет весь `/api` в существующий backend на 3000. Следовательно, отдельному Python-сервису нужен явный маршрут proxy (например, `/api/transcriptions`) перед общим `/api` либо маршрутизация через backend. Dev proxy не решает production routing; это уже отмечено в `apps/backend/README.md`. Новая вкладка может стать отдельным React Router route, не частью TelegramWorkspace.

Корневой `package.json` оркестрирует npm workspaces. Предлагается отдельный каталог приложения Python с `pyproject.toml`, `.python-version`, `uv.lock`; npm workspace-обёртка только для запуска/check, Python runtime-зависимости остаются в pyproject. uv хранит окружение отдельно и фиксирует зависимости в lock. [Структура uv project](https://docs.astral.sh/uv/concepts/projects/layout/). Это рекомендация границы интеграции, имя workspace и API ещё не выбраны.

## Что исследование оставляет открытым

- Доступ к реальному GPU и smoke-test выбранного wheel без CPU fallback; затем качество RU/EN, пик RAM/VRAM и время на длинном файле.
- large-v3 или turbo, основная карта, FP16 или INT8, удержание модели после завершения.
- Точность прогресса, необходимость чанков, поведение второго старта, отмена и технический механизм snapshot/reconnect.
- Папки/сроки хранения исходника, временных и итоговых TXT/JSON; корректные ошибки исчерпания диска/RAM. Пользователь исключил программные лимиты размера и длительности, поэтому три часа — ориентир проверки, не предел поддержки.
- Политика публичных live/playlist и недоступных YouTube-записей.

Исследовательская задача разрешена как сбор фактов для этих решений. Никакие продуктовые варианты этим отчётом не утверждены.
