# Исследование локальной диаризации

Дата: 2026-09-10. Только документация и исходники первичных поставщиков; пакеты, веса и токены не загружались, inference не запускался. Этот отчёт не выбирает продуктовый стек.

## Контекст

Уже выбран faster-whisper large-v3 без turbo/INT8, Python 3.12/uv, основная GPU RTX 5080, альтернативная RTX 4070 Ti. Фактическая доступность CUDA ещё не подтверждена. По переданным ответам пользователя требуются анонимные «Спикер 1/2», автоматическое число спикеров, живой текст с последующим добавлением/уточнением меток, финальное разделение после обработки, метки в TXT/JSON и «Неизвестный спикер». Не требуются имена людей или узнавание человека между файлами.

## Community-1

`pyannote/speaker-diarization-community-1` выполняется локально; после сохранения pipeline на диск документирован offline-запуск. Первичный доступ требует аккаунта Hugging Face, принятия условий модели и access token. Веса имеют CC-BY-4.0. Вход — mono 16 kHz; другие частоты и каналы приводятся автоматически. Результат содержит обычную диаризацию с перекрытиями и exclusive-вариант для согласования с текстом. В опубликованном сравнении Community-1 лучше 3.1 на большинстве наборов, но не на всех: REPERE хуже, VoxConverse одинаков. Таблица не доказывает превосходство на русских материалах пользователя и не обещает безошибочность. [Карточка модели](https://huggingface.co/pyannote/speaker-diarization-community-1).

Официальный пример переносит pipeline на CUDA и передаёт ProgressHook. `precision-2` через тот же интерфейс запускается на серверах pyannoteAI, поэтому этот документированный способ не отвечает требованию локального inference. Код pyannote.audio распространяется по MIT; условия весов отличаются от условий кода. [Репозиторий pyannote.audio](https://github.com/pyannote/pyannote-audio).

В `SpeakerDiarization.apply` число спикеров необязательно; доступны подсказки num/min/max. Pipeline сначала собирает сегментации и embeddings, затем выполняет кластеризацию и формирует общие метки. Hooks показывают этапы и выполненные batches, а не поток гарантированно окончательных speaker ID. **Вывод из реализации:** независимая обработка чанков не обеспечивает одинаковый ID одного человека между чанками; для этого нужен общий контекст кластеризации или отдельное сопоставление. Окончательные метки полного прохода можно принять стабильными внутри одного сохранённого результата, но не обещать их неизменность при повторном проходе или дополнении записи. [Исходник pipeline](https://raw.githubusercontent.com/pyannote/pyannote-audio/develop/src/pyannote/audio/pipelines/speaker_diarization.py).

## Альтернативы

| Кандидат | Факты и ограничения |
| --- | --- |
| NVIDIA Streaming Sortformer 4spk v2.1 | Локальный NeMo/PyTorch, NVIDIA Open Model License. Arrival-Order Speaker Cache поддерживает контекст предыдущих голосов и порядок появления. Максимум четыре спикера; с пятью и более качество падает. Предназначен для нескольких часов, но авторы предупреждают о деградации на очень длинных записях. Обучение преимущественно английское; неанглийская речь может работать хуже. Есть режимы с разной задержкой, перекрытия включены в оценку. Карточка упоминает HF token для загрузки, но её пример в этом месте ссылается на v2; необходимость авторизации именно для публичных весов v2.1 без загрузки не проверена. [Карточка NVIDIA](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2.1). |
| Diart | MIT-код, online incremental clustering, буфер обновляется каждые 500 ms, регулируемая задержка 0.5–5 s, обработка перекрытий. Воспроизведение результатов статьи рекомендует старый pyannote.audio <3.1. Это исследовательская альтернатива для ранних меток, без подтверждённой здесь совместимости современного Python/Blackwell; доступ к весам зависит от выбранных моделей. [Официальный репозиторий](https://github.com/juanmc2005/diart). |
| WhisperX | Интегратор faster-whisper, forced alignment и pyannote, а не отдельная более качественная модель диаризации. Поддерживает назначение меток сегментам/словам; alignment требует дополнительных языковых моделей. Авторы прямо отмечают ошибки диаризации и трудности одновременной речи. Полная замена текущего ASR на WhisperX меняет поведение декодирования, поэтому не является нейтральной зависимостью. [README WhisperX](https://github.com/m-bain/whisperX). |

Сравнивать DER Community-1 и Sortformer по цифрам из разных карточек без выравнивания наборов, collar и разметки некорректно. Объявить «самую качественную модель без потери качества» на этих источниках невозможно. Нужна сопоставимая оценка RU/EN на репрезентативных записях.

## Python, Blackwell и память

Текущий исходный pyproject pyannote.audio требует Python >=3.10, torch/torchaudio >=2.8, torchcodec >=0.7. Python 3.12 удовлетворяет заявленной границе; это не проверка конкретного lock-файла. [Метаданные зависимостей](https://raw.githubusercontent.com/pyannote/pyannote-audio/develop/pyproject.toml).

PyTorch начал официально поддерживать Blackwell в 2.7 со сборками CUDA 12.8. [Релиз 2.7](https://pytorch.org/blog/pytorch-2-7/). В 2.12 стандартные cu128 wheels сняты с матрицы; для Blackwell рекомендованы CUDA 13.0+ wheels с Linux-драйвером >=580.65.06. Поэтому нельзя просто закрепить «последний torch + cu128». Наблюдавшийся в карте драйвер 610.57.04 численно новее этого порога, но реальный доступ к устройствам и загрузка kernels не проверены. [Релиз 2.12](https://pytorch.org/blog/pytorch-2-12-release-blog/).

TorchCodec зависит от совместимых shared libraries FFmpeg и имеет отдельную матрицу совместимости с torch/Python. Наличие executable ffmpeg само по себе недостаточно; текущий README допускает FFmpeg 4–9, но для выбранного релиза нужно сверять его собственную таблицу. [TorchCodec](https://github.com/meta-pytorch/torchcodec).

Точных подтверждённых пиков VRAM Community-1/Sortformer на RTX 5080/4070 Ti с трёхчасовым материалом не найдено. Поддержка архитектуры PyTorch не доказывает совместимость всей совокупности CTranslate2, torch, TorchCodec и CUDA-библиотек. Обе GPU требуют smoke-test с закреплёнными пакетами.

**Расчёт, не замер:** mono 16 kHz float32 занимает 16 000 × 4 × 10 800 = 691 200 000 байт (~659 MiB) за три часа только для waveform; дополнительные массивы/копии увеличивают RAM. Pipeline сохраняет промежуточные сегментации/embeddings, так что отсутствие программного лимита длительности не означает постоянное потребление памяти. Механическая нарезка файла с отдельной диаризацией нарушает общую идентичность меток.

## Присвоение меток тексту и жизненный цикл

WhisperX назначает сегменту или слову спикера с наибольшей суммарной длительностью пересечения. При отсутствии пересечения он может оставить метку пустой; nearest-fallback опционален. **Вывод:** один Whisper-сегмент может содержать смену говорящего, и одна метка на весь сегмент потеряет эту смену. Для более точной разметки нужны внутренние word timestamps либо разбиение текста по проверенным границам. Не обязательно показывать пользователю слова по отдельности. [Алгоритм назначения](https://raw.githubusercontent.com/m-bain/whisperX/main/whisperx/diarize.py).

Exclusive-диаризация упрощает выбор одной метки, но не восстанавливает пропущенные Whisper слова при одновременной речи. Неизвестный speaker должен оставаться допустимым значением; универсальный порог «уверенности» для сопоставления в этих API не установлен. [Описание exclusive-результата](https://huggingface.co/pyannote/speaker-diarization-community-1).

**Варианты для следующего решения, не принятые решения:**

- Сначала показывать ASR-текст без меток; после освобождения Whisper выполнить полный проход Community-1, назначить финальные метки и обновить UI/TXT/JSON. Это совместимо с последующим добавлением меток, избегает конкуренции моделей за VRAM, но добавляет ожидание финальной разметки.
- Диаризация до ASR даёт общую карту спикеров для дальнейшего текста, однако откладывает появление самого текста.
- Параллельная/online-диаризация даёт более ранние метки, но требует управления VRAM, revisions и сопоставления ID; выбранные источники не дают гарантии равного качества полной offline-кластеризации.

**Инженерная рекомендация для обсуждения:** создавать модели только внутри операции после команды UI; отдельные процессы для GPU-фаз позволяют завершать их при отмене и освобождать CUDA-контекст. Не вызывать from_pretrained при импорте/старте FastAPI. Это предлагаемая архитектура, не автоматическое свойство библиотек. Если диаризация отменена, частичный текст и незавершённость меток — разные признаки результата.

## Что требуется решить или проверить далее

1. Выбор diarization engine и допустимость принятия условий/получения весов Community-1.
2. Порядок фаз и момент финализации speaker labels; нужна ли отдельная alignment-модель ради точных границ смены спикера.
3. Политика ошибки диаризации при уже готовом ASR и точная семантика overlap/unknown.
4. При реализации: uv resolution, CUDA smoke-test обеих GPU, измерения RAM/VRAM и времени на длинных RU/EN записях; проверка пяти и более спикеров, возврата голоса после длинной паузы, тишины, музыки, наложения речи, отмены и освобождения GPU. Никакой из этих запусков в рамках исследования не выполнялся.
