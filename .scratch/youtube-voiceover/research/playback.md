# Воспроизведение подготовленного перевода YouTube

Исследовано 2026-09-10. Контекст: личный локальный Daevox; английский → русский; заранее подготовленная озвучка с разными синтетическими голосами. Исследование не выбирает продуктовый вариант и не проверяет видео экспериментально.

## Главный результат

Техническая управляемость embed не означает, что YouTube разрешает накладывать свою дорожку. Developer Policies, раздел III.I.7, прямо запрещают применять альтернативные аудиодорожки к видео через YouTube API Services. III.E.1 ограничивает скачивание, импорт, хранение и offline playback; III.I.5 запрещает вмешательство в рекламу. Поэтому embed + локальная озвучка нельзя закладывать как документированно разрешённую интеграцию. [YouTube Developer Policies](https://developers.google.com/youtube/terms/developer-policies)

Общие Terms разрешают личный просмотр и embed, но скачивание/изменение контента требуют разрешения сервиса либо письменного разрешения YouTube и применимых правообладателей. Личное использование само по себе не даёт общего разрешения на скачивание. Это факты опубликованных условий, а не вывод о правовом статусе конкретного файла или юрисдикции. Получение файла непосредственно от автора с правами на перевод — отдельный путь, который нужно отличать от скачивания YouTube. [YouTube Terms, Permissions and Restrictions](https://www.youtube.com/static?template=terms)

## Варианты для последующего решения

| Вариант | Технические свойства | Следствие для проекта |
| --- | --- | --- |
| YouTube iframe + отдельное локальное audio | Два независимых источника времени; сетевой embed остаётся необходим | Помимо синхронизации есть прямое ограничение условий выше; не считать базовым поддержанным путём |
| Локальное video + отдельное audio | Оба ресурса под контролем приложения; отдельные оригинал и перевод | Требует сохранять исходное видео, выдавать медиа и координировать два элемента |
| Локальное video с подготовленной смешанной дорожкой | Один медиаресурс и одна временная шкала | Упрощает просмотр; изменение баланса оригинала/перевода требует другого артефакта либо отдельного режима |

Последние две строки — архитектурный вывод, условный на допустимое получение исходного файла. Ни хранение локально, ни возможность yt-dlp не решают вопрос получения контента.

## YouTube API: возможности и пределы

Официальный API предоставляет play/pause, seekTo, getCurrentTime, mute/volume, состояния buffering/playing/paused/ended и события скорости. Seek может попадать на предшествующий keyframe; из paused остаётся paused, из других состояний начинает играть. setPlaybackRate — пожелание: фактическую скорость нужно брать из события и ограничивать getAvailablePlaybackRates. Полного набора событий seeked/timeupdate и механизма атомарной синхронизации с внешним audio API не документирует.

Embed может отказать для private/deleted (100), запрещённого встраивания (101/150), отсутствующего Referer/client identity (153). Нужны enablejsapi и корректный origin; минимальный viewport 200×200. onAutoplayBlocked сообщает отказ браузера. [YouTube IFrame API reference](https://developers.google.com/youtube/iframe_api_reference)

Вывод: если допустимость embed когда-либо будет отдельно обеспечена, потребуется эксперимент с дрейфом, перемоткой, buffering и рекламными переходами. Из документации нельзя вывести точность синхронизации или надёжное управление рекламными интервалами. Обещать доступность любого публичного ролика нельзя.

## Локальное воспроизведение

HTMLMediaElement определяет currentTime, playbackRate, play()/pause(), seeking/seeked, waiting/playing и seekable. play() возвращает Promise: интерфейс должен учитывать отказ старта. Seek зависит от доступных диапазонов и декодирования. У двух элементов нет обещания общего аппаратного clock. [HTML Standard: media elements](https://html.spec.whatwg.org/multipage/media.html)

Предложение для проверки, не принятое решение: видео задаёт время; audio следует фактическому времени после seeked; пауза и buffering останавливают оба потока; повторный старт ожидает готовности обоих; дрейф измеряется и корректируется. Порог коррекции и допустимые скорости следует определить прототипом. Предварительное смешивание в один ресурс сокращает этот класс ошибок. Совместимость контейнера/кодеков проверять на браузере пользователя, не выводить из расширения файла.

Старт по явной кнопке и обработка отказа надёжнее предположения об autoplay. Chrome разрешает muted autoplay, а старт со звуком зависит от взаимодействия/политик; для iframe есть делегирование autoplay. Это правило Chrome, не универсальная гарантия всех браузеров. [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay/)

## Выдача медиа и Range

Для локальных долгих записей нужен файловый HTTP endpoint с byte ranges: Accept-Ranges: bytes, ответ 206 с корректными Content-Range/Content-Length, 416 с Content-Range: bytes */N для неподходящего диапазона. Range относится к байтам, не секундам. RFC допускает игнорирование Range и ответ 200; поэтому поддержку нужно явно проверить. If-Range и валидатор позволяют избежать смешивания версий ресурса. [RFC 9110, sections 14, 15.3.7, 15.5.17](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests)

Проектное следствие: артефакт озвучки должен иметь устойчивую версию; опубликованный файл не перезаписывается частично. Endpoint получает идентификатор артефакта, а не произвольный путь клиента. Проверки будущей реализации: HEAD/GET, начало/середина/конец файла, недопустимый диапазон, перемотка без полного скачивания, отмена соединения. Это требования к будущему решению, реализации здесь нет.

## Что уже есть в Daevox

В текущей рабочей копии `apps/transcription-backend/src/transcription/worker.py:39` выполняет acquisition с `format=bestaudio/best`, фильтром public finished recordings и нормализацией в `audio.wav`. Fallback `best` формально может содержать видео, но устойчивого video artifact этот контракт не обещает. `apps/transcription-backend/src/transcription/service.py:407` удаляет временный каталог. Существующий StreamingResponse в `api.py` не является доказательством поддержки Range для медиа.

Следствие: повторное использование распознавания возможно, но готовый плеер нельзя построить только из сохранённого текста. Нужны решения о доступном источнике видео, владении и сроке жизни media artifacts, связи версии перевода с исходной временной шкалой и HTTP delivery. Текущий acquisition сам по себе не подтверждает соответствие условиям YouTube.

## Что остаётся решить с пользователем

- Принимается ли локальный исходный файл с допустимыми правами как основной/запасной вход, или доступность сценария только по YouTube-ссылке обязательна?
- Нужен ли offline просмотр и живое изменение баланса голосов, или достаточно заранее сведённого результата?
- Какие браузер, длительность и точность синхронизации считать критериями прототипа?

Исследование завершает сбор фактов; эти продуктовые решения не приняты. Источники прочитаны без скачивания/доступа к видео. Данные о точности, рекламе, codec compatibility и throughput не измерялись.
