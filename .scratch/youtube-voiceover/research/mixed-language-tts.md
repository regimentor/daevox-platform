# Английские термины в русской озвучке: проверка и варианты реализации

Дата: 2026-09-11. Production-код не менялся, backend не запускался. Эксперименты работали отдельными процессами на RTX 5080; пользовательский Ornith-1.5-9B использовался через уже работающий localhost:8080 на другой GPU.

## Вывод

Для ближайшего исправления рекомендован Silero с отдельным текстом произношения, детерминированным глоссарием и защитой терминов/чисел при LLM-переводе. Простая просьба LLM «напиши всё кириллицей» ненадёжна: в опыте исчезала латиница, но менялись числа и названия. Qwen3-TTS 0.6B с `language=Auto` — работающий кандидат для следующего сравнения качества, пока не доказанная замена на целом ролике.

## Подтверждённая причина

Установленный `v5_5_ru.pt`, SHA256 `50081637b602126ee06cb3bc8a744d25651d2da149ee8864b9a379bfdd934437`, содержит `questions_public_eugene_int_intensity/multi_acc_v3_package.py`. В `prepare_text_input` (строки 275–295 внутри архива) регулярное выражение удаляет символы вне алфавита модели. В проверенном пути aidar исчезли английские буквы и цифры, а синтез завершился успешно.

## Метод и границы проверки

Шесть специально выбранных коротких фраз: названия/аббревиатуры; числа; API/runtime; .NET/C#; версия/модель GPU; код memcpy/std::vector. Это малый диагностический набор, не статистика надёжности. Для четырёх первоначальных LLM-вариантов использован temperature=0, thinking=false; один пакет на вариант. Получены 36 WAV Silero, один гибридный WAV и четыре WAV Qwen. Ещё один вариант перевода со словарём проверен только текстом и не прошёл разбор JSON.

Дополнительная проверка 21 WAV выполнена faster-whisper-large-v3, revision `edaa852ec7e145841d8ffdb056a99866b5f0a478`, language=ru, beam_size=5, без VAD. ASR — диагностический сигнал: оно тоже ошибается, особенно на иностранных названиях. Субъективная оценка тембра/естественности и проверка всего ролика не выполнялись.

Исходники, входы, ответы LLM, WAV и результаты находятся в `apps/transcription-backend/data/tts-options/`: `corpus.json`, `llm-results.json`, `silero-results.json`, `asr-results.json`, `hybrid-results.json`, `qwen-output/result.json`. Каталог данных игнорируется Git; это локальные воспроизводимые материалы, не поставляемый код.

Время LLM относится к пакету из шести коротких фраз, исключает TTS и не предсказывает время полного ролика. Ручной словарь эксперимента — выбранные произношения, а не универсальный стандарт. В частности, названия продуктов, акронимы и код допускают разные договорённости.

## Что показал Qwen

Qwen/Qwen3-TTS-12Hz-0.6B-CustomVoice, revision `85e237c12c027371202489a0ec509ded67b5e4b5`, Ryan, BF16/SDPA, RTX 5080. Одна составная фраза про AMD/Rust/GPU/C++/WebGPU/API/runtime, в двух написаниях и двух языковых режимах.

| Вход / режим | Синтез | WAV | Диагностическое ASR |
| --- | ---: | ---: | --- |
| Смешанный / Russian | 5.40 с | 11.04 с | Сильное расхождение во второй половине фразы |
| Кириллица / Russian | 11.81 с | 25.36 с | Искажённые названия, необычно длинная запись |
| Смешанный / Auto | 6.22 с | 13.76 с | Восстановлены основные термины, Rust → «рост» |
| Кириллица / Auto | 5.30 с | 11.44 с | Восстановлены основные термины, Rust → RAS |

ASR-ошибка не доказывает соответствующую ошибку синтеза. Эти результаты поддерживают дальнейшее прослушивание Auto, но не обещание безошибочной озвучки. Пик allocated PyTorch 2.34–2.71 GiB, reserved до 3.27 GiB; это не полная память процесса. Для Silero измеренный peak allocated около 351 MiB. Объём файлов Qwen 0.6B — 2.5 GB; среда также занимает место.

[Подробности моделей, зависимостей и первичные источники](multilingual-tts-options.md). [Официальный Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS), [Chatterbox](https://github.com/resemble-ai/chatterbox). Поддержка русского и английского не равна гарантии смешанной речи внутри предложения.

## Предлагаемая реализация A: минимальное исправление Silero

1. Сохранить читаемый перевод отдельно от `speech_text`. В субтитрах остаются Rust/GPU, в Silero поступают «раст/джи пи ю».
2. После перевода и любого сокращения сформировать speech_text через версионированный глоссарий, нормализатор чисел и символов. Значения вроде C++, C#, .NET и std::vector обрабатывать как целые сущности. Аббревиатуры можно раскрывать по согласованной политике, например GPU → «графический процессор», если смысл и контекст позволяют.
3. Для неизвестного термина запросить у LLM только произношение этого термина в контексте, сохранить принятое соответствие на весь ролик. Не переписывать заново всё предложение. Словарь можно пополнять автоматически, но его предложения остаются потенциально ошибочными.
4. До TTS проверять необработанные буквы, цифры, операторы и пустые фразы. Нельзя удалять неподдерживаемое и объявлять успех. Неизвестное произношение должно давать повторную обработку/видимую ошибку.
5. Нормализация чисел должна учитывать падеж, единицы, версии и идентификаторы: 2.5 как версия отличается от десятичного числа; модель GPU отличается от количества ядер. Простая глобальная замена цифр недостаточна.
6. Хранить speech_text и версию подготовки вместе с результатом; включить их в ключ кэша. Иначе переиспользуются старые WAV с пропусками.

Это наименьший объём изменения рабочего конвейера. Однако если LLM уже исказила число при переводе, последующая подготовка его не восстановит.

## Предлагаемая реализация B: подмена при LLM-переводе с защитой смысла

Предпочтительное усиление A:

```text
Исходная фраза
  → выделение терминов, чисел и составных названий
  → замена защищёнными [[TERM_n]] с пояснениями для LLM
  → LLM переводит предложение и сохраняет метки
  → проверка идентификаторов и количества каждой метки
  → две детерминированные подстановки:
      text: исходное написание
      speech_text: согласованное произношение
  → проверка алфавита → TTS → фактическая длительность
```

Например `AMD uses Rust for GPU programming, not C++` переводится с защищёнными сущностями; текст для показа сохраняет AMD/Rust/GPU/C++, а речевое поле использует их произношения. Числа хранят исходное значение и тип. Составные `OpenAI SDK` и `RTX 4070 Ti` по возможности защищаются целиком, чтобы не получить перестановку компонентов.

При потере, дублировании или появлении лишней метки ответ отклоняется. Ограничение JSON-схемой помогает формату, но не доказывает точность фактов. Сокращение фраз должно сохранять те же сущности и отрицания; после него снова формируется речь. Длительность измерять по полученному WAV, сохраняя уже выбранную пользователем политику небольшого отставания и догоняния в паузах.

Вариант «LLM сразу возвращает text и speech_text со словарём» проще, но требует сопоставления сущностей между обоими полями и источником. После наблюдавшихся ошибок не рекомендован как единственная защита.

## Предлагаемая реализация C: сменный многоязычный движок

Добавить выбираемый для всего результата TTS engine с отдельным Python executable и контрактом phrase_id/text/speaker → WAV/duration/status. Загружать модель один раз на пакет; завершать worker после работы. Qwen имеет конфликтующие с текущим backend зависимости, поэтому отдельная среда необходима. Backend как отдельный постоянный сервис для эксперимента не нужен.

Для Qwen начать с естественного смешанного текста и Auto; применять выборочную подсказку только к плохо произносимым терминам. Смена движка может изменить голос и просодию. Перед миграцией сравнить весь исходный ролик и набор чисел/названий, а не четыре коротких WAV. Qwen 1.7B и Chatterbox пока не проверены аудио; дальнейшие скачивания и сравнение — отдельный этап.

## Критерии приёмки будущего исправления

Через согласованные публичные границы перевода/озвучки проверить: сохранность сущностей и чисел, отсутствие тихого удаления неподдерживаемых слов, читаемые субтитры, повторное озвучивание при изменении глоссария, сохранение всех фраз при рассинхронизации. Контрольные случаи: 4096, C#, C++, .NET, версия 2.5, RTX 4070 Ti, незнакомое название. Проверить полный ролик с прослушиванием; ASR использовать как дополнительный сигнал. Production-тесты и код в этом исследовании не менялись.
