## Question

Как разделить ответственность клиента и приложения за запуск, интерактивные шаги авторизации, готовность, локальные данные сессии и ключи, восстановление после перезапуска, штатное закрытие и выход из аккаунта на личном ПК? Какие гарантии клиент даёт при потере соединения или завершении backend?

Определить модель владения ресурсами и способы передачи параметров без проектирования UI приложения и без получения реальных секретов. Учесть существующие hooks жизненного цикла backend/framework; не привязывать независимый клиент к framework.

## Comments

2026-09-08, первый раунд: пользователь подтвердил ответственность приложения за интерактивную авторизацию через invoke и обработку состояний; отдельно потребовал QR-авторизацию. Клиент не содержит CLI и не читает секреты из окружения. Пути к базе/файлам, ключ шифрования и параметры TDLib задаёт приложение. start() запускает обмен, waitUntilReady({ signal, timeout }) отдельно ожидает готовность авторизованного аккаунта; подписаться можно до старта. close() сохраняет сессию; выход из аккаунта — отдельная явная операция. При закрытии новые вызовы отклоняются, не получившие ответа запросы отклоняются при окончательном закрытии; повторный close безопасен.

Проверено по [официальной схеме TDLib](https://github.com/tdlib/td/blob/master/td/generate/scheme/td_api.tl): QR-вход запрашивается requestQrCodeAuthentication; authorizationStateWaitOtherDeviceConfirmation содержит link для QR, который часто обновляется. Клиент должен передавать эти обновления без потери актуальной ссылки; отрисовка QR относится к приложению. QR-путь не должен обходить последующие состояния, например запрос пароля двухэтапной аутентификации. Это описание механизма TDLib, а не дополнительный UI клиента.

2026-09-08, второй раунд: пользователь подтвердил все три предложенных границы: авторизация отдельно от сети; новый экземпляр после окончательного закрытия/фатального сбоя; отмена ожидания close без прерывания штатного закрытия. Обсуждение завершено.

## Answer

Согласовано с пользователем 2026-09-08:

- Приложение управляет интерактивной авторизацией через invoke и состояния TDLib. Клиент не содержит CLI и не читает секреты из окружения.
- QR-авторизация обязательна: requestQrCodeAuthentication доступен через invoke; обновления authorizationStateWaitOtherDeviceConfirmation передают актуальный link. Отрисовка QR и получение пароля, если TDLib запрашивает его следующим шагом, принадлежат приложению.
- Приложение явно задаёт параметры TDLib, пути к базе и файлам, ключ шифрования. Клиент не выбирает скрытые каталоги и не генерирует постоянный ключ самостоятельно.
- start() запускает обмен с TDLib; подписки можно создать заранее. waitUntilReady({ signal, timeout }) отдельно ожидает готовность авторизованного аккаунта. Авторизация и подключение к сети — разные состояния: потеря сети сама по себе не сбрасывает авторизацию; состояние соединения доступно через обновления.
- close({ signal, timeout }) инициирует штатное завершение с сохранением сессии. Выход из аккаунта — отдельная явно запрошенная операция. Повторный close безопасен.
- С началом закрытия новые вызовы отклоняются. Запросы, оставшиеся без ответа, отклоняются при окончательном закрытии.
- AbortSignal и timeout у close отменяют только ожидание конкретного вызывающего. Штатное закрытие продолжается; клиент не сообщает об освобождении ресурсов и не выгружает библиотеку до подтверждения завершения TDLib.
- После окончательного закрытия или фатального сбоя нужен новый экземпляр клиента. Сохранённые данные сессии можно использовать повторно; скрытого пересоздания и повторной отправки запросов нет. Это поведение управляемых сбоев клиента, не гарантия выживания процесса при аварии нативного кода.

Распределение конкретных ресурсов FFI между потоками и экземплярами относится к задаче «Исполнение FFI и доставка обновлений». Подключение к hooks backend и реакция приложения на состояния — отдельная задача «Подключение клиента к жизненному циклу backend».
