# Исполнение FFI и доставка обновлений

## Question

Где исполнять блокирующее ожидание TDLib и как доставлять обновления независимым подписчикам без блокировки backend: владение FFI и receive loop, уступка управления для send/close, порядок доставки, поведение медленных или бросающих ошибку обработчиков и пределы очередей? Допускать ли асинхронные обработчики, какие гарантии давать при отписке и перегрузке?

Базовые invoke/onUpdate уже согласованы. Исследование предлагает worker_threads как кандидата; конкретный механизм и гарантии ещё не выбраны. Никакие обновления нельзя молча отбрасывать как несущественные по прикладному смыслу: независимый клиент не выбирает сценарий за приложение.

## Comments

Пользователь подтвердил первый раунд:

- Один выделенный worker_threads worker, общий для экземпляров клиента внутри процесса, владеет FFI и всеми нативными вызовами, получает и маршрутизирует ответы/обновления. Цикл регулярно уступает управление для команд отправки и закрытия; ожидание TDLib не занимает основной поток backend.
- Async-обработчики поддерживаются. У каждого подписчика своя последовательная очередь с ожиданием его Promise. Остальные подписчики и ответы invoke не ждут асинхронного завершения этого обработчика. Тяжёлый синхронный код обработчика остаётся на основном потоке и может его блокировать.
- Исключение или отклонённый Promise обработчика отключает только проблемную подписку. Отдельный обработчик ошибок клиента явно сообщает приложению об ошибке и подписке. Остальные подписчики и клиент продолжают работу; автоматического повтора обработки нет.

Во втором раунде пользователь подтвердил конечный настраиваемый лимит очереди с отключением подписки при переполнении и немедленную отписку с очисткой ожидающей очереди. Обсуждение завершено.

## Answer

- Один выделенный worker_threads worker, общий для экземпляров клиента внутри процесса, владеет FFI и всеми нативными вызовами. Он получает ответы/обновления и маршрутизирует их соответствующим клиентам. Цикл регулярно уступает управление для обработки send/close, не занимая основной поток ожиданием TDLib.
- onUpdate поддерживает async-обработчики. Для каждой подписки обновления обрабатываются последовательно, с ожиданием Promise обработчика. Асинхронная задержка одного подписчика не задерживает остальных и разрешение invoke. Синхронный код обработчиков выполняется в основном потоке; отдельной изоляции CPU для них не обещается.
- Исключение либо отклонение Promise отключает только проблемную подписку. Приложение получает явное сообщение через отдельный обработчик ошибок клиента, с указанием подписки. Автоматического повтора нет; остальные подписчики и клиент продолжают работу.
- У каждой подписки конечный настраиваемый предел очереди. При переполнении подписка отключается с явной ошибкой о нарушении полноты её потока. Остальные подписки продолжают работать. Продолжать доставку с молча пропущенными обновлениями нельзя.
- Отписка немедленно прекращает приём новых обновлений и удаляет ещё не обработанную очередь. Уже выполняющийся обработчик заканчивает самостоятельно; его возможная ошибка всё равно перехватывается и сообщается приложению. Повторная отписка безопасна.

Внутреннее планирование receive, обмен между потоками и выбор значений лимитов должны реализовать эти гарантии. Очереди подписчиков не являются дисковым журналом с повторным воспроизведением. Уточнение необходимых проверок вынесено в задачу «Проверки клиента TDLib перед реализацией».
