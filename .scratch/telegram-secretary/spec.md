# Секретарь: выбор Telegram-чатов и архив сообщений

Состояние: исходная спецификация первого этапа реализована в backend и веб-клиенте.
Последующие возможности включают импорт истории за 30 дней, дневные саммари и автоответчик.
Текущий запуск и поведение описаны в [README backend](../../apps/backend/README.md),
схема и её применение — в [README базы](../../packages/db/README.md).

Ниже сохранены требования первого этапа и история решений; исключения этого этапа
не описывают границы всей текущей платформы. Обновление документа не означает новой ручной приёмки.

## Результат первого этапа

Пользователь выбирает Telegram-чаты на существующей странице Telegram. Backend независимо от браузера сохраняет доступные сообщения выбранных периодов в локальный архив. Будущий агент получает пригодную для обработки выборку с известными ограничениями полноты.

Архив является исходным материалом для секретаря. Запуск llama.cpp, извлечение памяти и ответы агента относятся к следующему этапу.

## Пользовательский сценарий

1. Подключить один личный Telegram-аккаунт существующим способом. Дождаться определения аккаунта и готовности локального хранилища.
2. На странице Telegram найти чат по названию, username или ID. Доступны личные переписки, боты, «Избранное», группы и архивные чаты; каналы и секретные чаты исключены. До окончания фоновой загрузки поиск явно охватывает только известную часть каталога.
3. Включить индивидуальный переключатель. UI подтверждает выбор после записи в SQLite и отдельно показывает ожидание Telegram, догрузку или текущий сбор. Общего черновика и кнопки массового сохранения нет.
4. Получать входящие сообщения и собственные ответы в архиве. Закрытие браузера не останавливает backend-сбор. Отсутствие сети Telegram допускает изменение выбора при доступных backend, аккаунте и БД.
5. Выключить чат, сохранив накопленный архив. Повторное включение открывает новый период; выключенный промежуток не догружается. Полученные изменения существующих записей продолжают учитываться.
6. После простоя восстановить доступные сообщения открытого периода. При неопределённой непрерывности авторизации пользователь видит отдельное действие возобновления с текущего момента. Текущая работоспособность не скрывает известные пробелы архива.

Секундные границы включаются целиком; offline-оценка времени приблизительна. Это не гарантированное отсечение с точностью до момента нажатия. Отправка, просмотр и другие действия, меняющие состояния сообщений в Telegram, не входят в сбор.

## Границы реализации

| Владелец                                     | Ответственность                                                                                                 |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `apps/backend`, `TelegramConnection`         | Единственный клиент TDLib, идентичность аккаунта, lifecycle и ограниченный внутренний интерфейс чтения/подписки |
| `apps/backend`, секретарь в `AppState`       | Периоды, очередь обновлений, догрузка, слияние, повторы, HTTP и видимое состояние сбора                         |
| Новый workspace `@daevox/db` в `packages/db` | SQLite через `node:sqlite`, схема, миграции, транзакции и выборка для будущего потребителя; без TDLib-клиента   |
| `@daevox/telegram-contract/secretary`        | Общие DTO и строгие валидаторы контракта секретаря                                                              |
| `apps/web-client`                            | Вариант A на странице Telegram, индивидуальные команды, поиск/фильтры/пагинация и polling раз в секунду         |

SQLite работает синхронно в основном процессе backend, ограниченными порциями с передачей управления между ними. Файл архива находится вне репозитория по настраиваемому пути. Общие dev-зависимости принадлежат корню npm workspaces; runtime-зависимости — владельцу workspace. Общий framework не перепроектируется.

## Контракты на границах

HTTP предоставляет снимок состояния, страницу чатов, изменение наблюдения и явное возобновление. Перечень маршрутов, тела, ошибки и правила версий находятся в разделе «HTTP и контекст ответов» [контракта сбора](issues/05-ingestion-contract.md). Публичного произвольного TDLib invoke и API выдачи текстов переписки для этого экрана нет.

Успех команды означает завершённую запись настройки, периода и версии. Потерянный ответ требует чтения актуального состояния; автоматический повтор команды запрещён. Запоздавшие ответы не могут подменить состояние другого аккаунта или авторизации.

Архив разделяет настройку, периоды, прогресс и пробелы. Ключ сообщения включает аккаунт, чат и окончательный ID; сообщения и прогресс порции фиксируются атомарно. Правила полей и преобразования ID определены в [модели хранилища](issues/03-archive-storage.md). Будущая выборка по аккаунту, чату и периоду возвращает версии и ограничения полноты, исключая удалённое и запрещённое содержимое; статусов обработки моделью пока нет.

## Восстановление и пределы результата

Подписка и периодическая история дополняют друг друга. Дедупликация, сохранённый прогресс и проверки версии не позволяют старой истории отменить полученную правку, подтверждённое удаление или новый запрет сохранения. Короткие страницы, отсутствие продвижения и удаление из кэша не доказывают полноту либо удаление сообщения.

Полученный запрет сохранения исключает содержимое из будущей выдачи и очищает сохранённые содержательные поля. Недоступность сообщения и запрет различаются. Архив хранит последнее известное состояние, без полной истории правок и без обещания мгновенно узнавать все изменения старой переписки.

Ошибка архива сохраняет выбор пользователя и доступность управления Telegram. Автоматическое восстановление не стирает известные пробелы. Преобразование группы требует отдельного включения новой супергруппы. Правила нового входа, обычного перезапуска и неопределённого продолжения определены в [контракте сбора](issues/05-ingestion-contract.md).

## Приёмка и передача в реализацию

Матрица автоматических проверок, обязательный ручной сценарий на тестовых Telegram-чатах и согласованный нагрузочный ориентир находятся в [задаче приёмки](issues/06-acceptance-spec.md). Там же определены имеющиеся команды и необходимые дополнения к тестовым средствам. Без обязательного ручного прогона этап не объявляется полностью принятым.

Результат реализации должен включать исходный код, миграции, настройку пути архива, инструкции запуска и воспроизводимые проверки. Отчёт различает выполненные, неуспешные и невыполненные проверки и содержит версии среды. Успех прототипа UI не является проверкой интеграции; артефакт прототипа связан из решения о пользовательском сценарии.

Исходные исследование и прототип сохраняются в отдельных временных checkout и могут отсутствовать на другой машине. Для реализации обязательны решения в репозитории и закреплённые ссылки на источники; перенос временных артефактов не должен быть скрытой зависимостью запуска приложения.

## За пределами первого этапа

Модель llama.cpp и память пользователя; автоматические ответы или отправка сообщений; каналы и секретные чаты; скачивание и распознавание вложений; загрузка истории до включения; несколько одновременно подключённых аккаунтов; отдельная учётная запись пользователя backend; пользовательская очистка архива. Полный перечень границ находится в [карте](map.md).
