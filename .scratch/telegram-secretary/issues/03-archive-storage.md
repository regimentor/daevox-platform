## Question

Какая модель данных и граница `packages/db` обеспечат согласованный жизненный цикл наблюдения, устойчивую догрузку и последующую обработку сообщений агентом?

Связать аккаунт, Telegram-чат, автора, сообщение, интервалы наблюдения и прогресс синхронизации; определить уникальные ключи, представление идентификаторов и атомарность записи сообщения с продвижением прогресса.

Согласовать достаточный состав сообщения: текст и подписи, автор на момент сообщения и стабильный идентификатор, время, reply-связь (в том числе на несохранённое сообщение), типы и идентификаторы вложений. Определить минимальную границу для будущего потребителя архива, чтобы исключать удалённое и не путать сохранение с обработкой агентом; проектирование очереди выполнения llama.cpp не входит в вопрос. Проверить сценарии падения процесса и ошибки записи, не превращая `packages/db` в владельца Telegram-сессии.

Учесть факты исследования: sender_id бывает user или chat; reply может указывать на другой чат или историю и содержать неизвестные ID. Различить временный file.id и устойчивые remote-идентификаторы, не обещать доступность вложения по сохранённому ID. Представить ограничение can_be_saved и неопределённую актуальность записи в соответствии с решением о жизненном цикле.

## Answer

### Хранилище и ответственность

- Использовать SQLite через встроенный `node:sqlite`, без ORM. Отдельный локальный файл располагается вне репозитория, путь задаётся настройкой. Собственное шифрование архива в первый этап не входит. При выборе пользователь был уведомлён о статусе release candidate у API в используемом Node 26; техническая опора — [официальная документация Node](https://nodejs.org/api/sqlite.html).
- Создать npm workspace `@daevox/db` в `packages/db`. Он владеет соединением с БД, схемой, миграциями и операциями хранения. Общие dev-инструменты остаются в корне; дополнительные runtime-зависимости, если понадобятся, принадлежат workspace. Для выбранного встроенного драйвера отдельная npm-зависимость не нужна.
- Backend преобразует обновления Telegram в данные архива и управляет сбором. `@daevox/db` не владеет Telegram-сессией и не принимает произвольные TDLib-объекты как публичный контракт хранения.
- Отдельный worker для SQLite отклонён. Синхронные операции БД выполняются в основном процессе backend. Алгоритм сбора должен учитывать блокировку основного потока на время таких операций; размеры порций и порядок передачи управления определяются в задаче о контракте сбора, без переноса БД в worker.

### Идентичность и связи

- Уникальный ключ сообщения — `(accountId, chatId, messageId)`. Настройки и архив изолированы по аккаунту; область Telegram-чата — `(accountId, chatId)`.
- В TypeScript-модели архива и API Telegram ID представлены десятичными строками. В SQLite они хранятся как целые числа. Адаптеры проверяют целочисленность и безопасный диапазон закреплённого TDLib `int53` при преобразованиях. ID чатов допускают отрицательные значения; ограничения положительного account ID нельзя копировать на все идентификаторы. Это решение не распространяется автоматически на произвольные поля TDLib `int64`.
- Автор различается по виду (`user` или `chat`) и идентификатору в контексте аккаунта. У сообщения сохраняются имя и username, известные при первом получении, без утверждения об имени на момент отправки. Текущие сведения об авторе могут обновляться отдельно.
- Reply-ссылка допускается на отсутствующее в архиве сообщение, другой Telegram-чат либо другой поддерживаемый схемой объект. Не требовать наличия архивной записи назначения; неизвестные части ссылки остаются неизвестными.
- Преобразование группы в супергруппу представляется отдельной связью старого и нового чатов того же аккаунта. Записи старого архива не получают идентичность новой супергруппы. Правило явного включения новой группы остаётся из решения о жизненном цикле.

### Содержимое и состояния архивной записи

- Хранить последнее известное содержимое, время отправки, время известной правки, входящее/исходящее направление и внутренний номер версии записи. Полная история редактирования в первый этап не входит.
- Для текстовых сообщений и подписей хранить доступный текст; для вложений — тип и идентификаторы. Различать локальный `file.id` и удалённые идентификаторы, не считать локальный ID устойчивым между экземплярами TDLib и не обещать доступность файла по сохранённому ID.
- Для голосовых, стикеров и других сообщений без текста сохранять тип, автора, время, идентификаторы и доступную подпись; для служебных событий — вид события. Скачивание и распознавание содержимого остаются вне scope.
- После подтверждённого удаления содержимое удаляется из локального архива. Остаются идентификаторы и отметка удаления, препятствующая случайному восстановлению при повторной догрузке. Это не пользовательская очистка архива. Потерю доступа и удаление только из кэша не приравнивать к подтверждённому удалению.
- Для сообщения с запретом сохранения допустимы только идентификаторы аккаунта, чата и сообщения, время и причина пропуска. Текст, подпись, авторские снимки, reply-содержимое и идентификаторы вложений такой записи не сохраняются. Этот ограниченный состав имеет приоритет над общими полями сообщения.
- Удаление, запрет сохранения и неизвестная актуальность после пробела — разные основания обработки. Технические номера версий и курсоры не являются гарантией актуальности содержимого на сервере Telegram.

### Наблюдение, прогресс и полнота

Хранить раздельно следующие сущности; точные имена SQL-таблиц остаются деталью реализации:

| Сущность             | Назначение                                                                           |
| -------------------- | ------------------------------------------------------------------------------------ |
| Настройка наблюдения | Выбранные Telegram-чаты каждого аккаунта и намерение пользователя собирать сообщения |
| Период наблюдения    | Начало и окончание промежутка, за который новые сообщения должны попадать в архив    |
| Прогресс догрузки    | Сохранённая позиция восстановления сообщений соответствующего чата и периода         |
| Пробел архива        | Известная неполнота и её причина, независимо от текущей работоспособности сборщика   |

- Обычный перезапуск Daevox не закрывает период наблюдения. Выключение наблюдения и явный выход закрывают его; последующее возобновление открывает новый период. Начальные настройки, периоды и данные всегда принадлежат конкретному аккаунту.
- Запись сообщений и соответствующее продвижение прогресса догрузки выполняются одной транзакцией. Ошибка или прерывание не должны оставлять прогресс, для которого данные ещё не записаны. Повторный проход опирается на устойчивые ключи и отметки удаления.
- Границы периода, представление курсора, согласование истории с live-обновлениями и замена временного исходящего ID определяются в [Контракте настроек и алгоритме сбора сообщений](05-ingestion-contract.md) с учётом принятой модели. Известный пробел нельзя снимать только по факту успешной записи новой порции сообщений.

### Инициализация и миграции

- При запуске создавать новую БД при её отсутствии и автоматически применять последовательные версионированные миграции до запуска сборщика. Схема и миграции принадлежат `@daevox/db`.
- При ошибке открытия или миграции сохранять существующие данные, отображать недоступность хранилища и не запускать сборщик. Автоматическая пересоздающая очистка БД не предусмотрена.
- Управление подключением Telegram остаётся доступным при ошибке архива. Начальное состояние хранилища должно быть известно до готовности сборщика; ошибку подготовки архива нельзя превращать в завершение всего backend. Это согласуется с существующим lifecycle framework, где HTTP может начать обслуживаться до завершения `onAppStart`.

### Граница будущего потребителя

Предоставить выборку по аккаунту, Telegram-чату и периоду с версиями записей и сведениями о неполноте. Удалённое и запрещённое содержимое в неё не попадает. Очередь обработки моделью, статусы «обработано» и запуск llama.cpp относятся к следующему этапу.

Решения этой задачи достаточны для продолжения карты. Публичные DTO и алгоритм записи уточняются в задаче о контракте; сценарий состояния хранилища — в [Пользовательском сценарии выбора Telegram-чатов](04-chat-settings-ui.md). В этой сессии изменены только документы; код workspace и БД не создавались.
