# Telegram-автоответчик на основе дневного саммари

Состояние: код реализован, автоматическая проверка выполнена; ручная интеграционная приёмка ожидает выбора тестовых чатов и разрешения реальной отправки. Результаты и инструкции: [реализация и проверка](implementation.md).

## Результат

В интерфейсе Daevox пользователь включает автоответчик для выбранных Telegram-чатов. Backend от имени подключённого личного аккаунта отвечает на подходящие новые входящие сообщения, используя последнее готовое дневное саммари того же чата и само входящее сообщение. Ответ явно подписан ИИ-секретарём.

## Пользовательский сценарий

1. Подключить личный Telegram-аккаунт. В списке личных переписок, групп и супергрупп, включая архивные, выбрать чат.
2. Включить отдельный переключатель «Автоответчик» рядом с «Наблюдением». По умолчанию автоответчик выключен. Включение также включает наблюдение; впоследствии наблюдение можно выключить независимо. Выключение автоответчика не изменяет настройку наблюдения.
3. После готовности Telegram к обработке новых событий входящие от других отправителей получают отдельные ответы через Reply в исходной теме. Закрытие страницы не останавливает backend.
4. Видеть фактическое состояние: работает, готовит саммари, недостаточно данных, ошибка или причина приостановки. При недоступном backend — «Нет связи», управление недоступно. Включённая настройка не равна готовности отправлять.
5. После перезапуска настройка сохраняется; отвечать только на новые сообщения после синхронизации. После явного logout требуется повторное включение; другой аккаунт не наследует настройки.

При явном переключении настройки отправлять в выбранный чат отдельное служебное уведомление:
«ИИ-секретарь: автоответчик подключён к этому чату.» или «ИИ-секретарь: автоответчик отключён от этого чата.».
Это дополнение пользователя от 2026-09-10; уведомления не являются Reply на входящее сообщение.
Повторное сохранение неизменной настройки не создаёт дубль. Ошибка уведомления не отменяет переключение,
неизвестная доставка не повторяется автоматически; действуют ограничения личного авторства и запрет оплаты.

## Контекст и содержание ответа

Источник — готовая дневная сводка за самый поздний день этого чата и аккаунта, а не сводка с самым поздним временем генерации. Вчерашний или более ранний день допустим. Саммари других чатов, ручные сводки latest/all и общая память пользователя не являются источниками этого этапа.

Известная правка или удаление исходных сообщений требует обновить затронутую сводку перед использованием. Новое входящее, не включённое в сводку за предыдущий день, не запрещает использовать её. При недостатке фактов сообщать об этом; не придумывать сведения и обещания от владельца.

| Ситуация                                                                           | Результат                                                                                                              |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Есть пригодная сводка и текст/подпись входящего                                    | Содержательный ответ на основе сводки и входящего                                                                      |
| Нет готовой сводки                                                                 | Запустить подготовку за самый поздний день с доступным текстом; ответить о подготовке и предложить задать вопрос позже |
| Выбранная сводка недействительна из-за известных изменений                         | Запустить обновление и ответить о подготовке                                                                           |
| Нет доступного текста для подготовки                                               | Сообщить, что данных пока недостаточно                                                                                 |
| Генерация ответа или подготовка завершилась ошибкой для ещё не отвеченного запроса | Фиксированный ответ об ошибке, причина в интерфейсе                                                                    |
| Фото, стикер или голосовое без текста                                              | Попросить написать вопрос текстом                                                                                      |
| Служебное событие или сообщение с нашей подписью                                   | Не отвечать                                                                                                            |

Согласованные тексты служебных ответов приведены в решении о поведении. Текст ответа — на языке входящего, подпись — русская. При отсутствии определимого языка технический fallback должен быть явно описан реализацией, не менять согласованное содержание служебной фразы и проверяться в сценариях без текста.

Каждый ответ, включая фиксированный, содержит подпись «Ответ от ИИ-секретаря для уважаемого @username». Подставлять username отправителя, иначе отображаемое имя; для автора от имени чата — его публичный username или название. Один ответ ограничен 3000 символами вместе с подписью и должен укладываться в доступный лимит Telegram. Подпись и привязку Reply формировать вне свободной генерации модели.

Одна подготовка саммари обслуживает несколько нуждающихся в ней входящих. Её завершение или последующая ошибка не порождают второй ответ на вопрос, уже получивший сообщение о подготовке. Выключенное наблюдение не блокирует автоответчик и не разрешает ему самовольно возобновить архивирование.

## Очередь и отправка

- Одно намерение ответа на пару чат/входящее сообщение в пределах аккаунта. Повтор события не создаёт второе намерение; правка обновляет существующее.
- Порядок внутри чата сохраняется. Между чатами обслуживание по очереди; действующую генерацию саммари не прерывать, ожидающие автоответы имеют приоритет перед следующей генерацией сводки.
- Срок — пять минут с получения входящего автоответчиком, включая ожидание, генерацию и повторы. Правка не продлевает срок. После срока не начинать отправку/повтор; показать причину пропуска.
- До передачи Telegram проверять аккаунт, включённость, текущий период обработки, срок, актуальность входящего, права, личное авторство, Reply и тему. Подготовленный ранее результат не отменяет эти проверки.
- Если исходное сообщение удалено — отменить ответ; если исправлено — формировать на новую версию в пределах исходного срока. Ручное сообщение владельца не отменяет ответ. Правка после отправки не порождает новый ответ.
- При недоступном Reply или теме пропускать с причиной. Не отправлять отдельное сообщение в общий чат.
- При запрете писать, возможности только канального авторства или необходимости платежа приостанавливать отправку, сохраняя настройку. После снятия препятствия — только новые сообщения.
- Однозначный временный отказ допускает повтор после задержки Telegram, в пределах срока и прежних условий отправки. Неизвестный результат запрещает автоматический повтор; показать «Результат отправки неизвестен», продолжать новые сообщения.
- Выключение автоответчика, logout, перезапуск и потеря связи отменяют не переданные Telegram ответы. Старую очередь после восстановления не досылать. Переданную отправку гарантированно отменить нельзя; учитывать поздние результаты без новой отправки.

Граница live/backlog консервативна: сообщения с неясной новизной на границе синхронизации пропускать. Персистентный учёт и сопоставление временного/окончательного исходящих ID предотвращают повторные действия приложения, но не дают безусловную гарантию exactly-once внешней доставки.

## Границы реализации

- Backend координирует приём новых событий, выбор сводки, очередь ответов и отправку независимо от наблюдения. Существующая локальная модель используется через общий механизм планирования модельной работы.
- Хранилище сохраняет настройки по аккаунту/чату и учёт намерений: исходный срок, версию входящего, Reply/тему, состояние, причину, исходящие идентификаторы. Запуск после сбоя не оживляет старую очередь.
- Общий контракт передаёт настройки и фактические состояния в web-client. Интерфейс не выполняет отправку и не управляет жизненным циклом через наличие открытой страницы.
- Использовать npm workspaces: общие dev-зависимости и orchestration принадлежат корню, runtime-зависимости — соответствующим workspace. Перед изменениями соблюдать ближайший AGENTS.md.
- Имена классов, таблиц, DTO, частоту повторной проверки препятствий и ограничение ёмкости очереди определить при реализации так, чтобы выполнялись правила срока, порядка и наблюдаемости. Проверки не должны зависеть от случайных реальных задержек.

## Критерии приёмки

Ниже согласованный порядок проверки реализации; этот раздел не сообщает о выполненных тестах.

| Группа                | Проверяемый результат                                                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Основной сценарий     | Включённый чат получает один подписанный Reply от личного аккаунта в правильной теме; выключенный чат и собственные сообщения не получают ответа                                            |
| Настройки             | Включение включает наблюдение; выключение наблюдения не останавливает автоответы; выключение автоответчика не меняет наблюдение; новая учётная принадлежность ничего не наследует           |
| Источник знаний       | Выбирается позднейший день, не позднейшее завершение; другая сводка/аккаунт не попадает в prompt; известные правки/удаления исключают старую версию                                         |
| Подготовка            | Отсутствие/недействительность запускает одну подготовку; пустой архив не выдаётся за идущую работу; успех/ошибка после служебного ответа не вызывает вторую отправку                        |
| Содержание            | Факты из контролируемой сводки доступны; отсутствие факта приводит к честному ответу; подпись, fallback имени и предел длины соблюдены; вложения и служебные события обработаны по правилам |
| Срок и справедливость | Управляемые часы проверяют момент до/на/после пяти минут, ожидание и повтор; правка срок не продлевает; активный чат не блокирует другие; текущая сводка не прерывается                     |
| Изменения             | Правка до отправки заменяет устаревшую генерацию; удаление отменяет; ручной ответ не отменяет; недоступные Reply/тема не заменяются обычным сообщением                                      |
| Доставка              | Повтор события не отправляет дубль; temporary/final ID связаны; временный отказ ждёт разрешённый срок; неизвестный результат не повторяется и не блокирует новые входящие                   |
| Восстановление        | Перезапуск/разрыв/logout на каждом этапе не досылают очередь; поздние ответы и updates не оживляют отменённую работу; backlog не принимается за новые сообщения                             |
| Ограничения           | Нет платежей или подмены личного авторства; снятие запрета восстанавливает только новые ответы; наша подпись предотвращает цикл                                                             |
| Интерфейс             | Переключатель, фактическое состояние, отсутствие связи, ошибки и причины пропуска отражают backend; проверены повторные действия и обновление страницы                                      |

### Автоматические проверки

Проверять backend управляемыми Telegram и LLM, с реальной временной БД и управляемыми часами. Аварийные завершения и восстановление — отдельным тестовым процессом. Browser e2e проверяет пользовательский сценарий через HTTP. Фикстуры искусственные, без рабочей переписки и данных авторизации.

Проверки для ожидаемо затронутых workspace, сверенные с текущими package.json:

```sh
npm run verify -w @daevox/telegram-contract
npm run verify -w @daevox/db
npm run verify -w @daevox/backend
npm run verify -w @daevox/web-client
npm run test:e2e -w @daevox/web-client
```

Дополнить штатными проверками TDLib/framework, если реализация затронет эти workspace, и проверками формата/линта из действующих корневых scripts. Не запускать изменения схемы рабочей БД ради тестов. Успешная симуляция отправки не подтверждает реальную доставку Telegram или качество выбранной локальной модели.

### Ручной прогон

Провести один отдельный прогон после автоматических проверок: выбранная личная переписка, группа с темой и контрольный выключенный чат; реальная локальная модель и тестовые тексты. Проверить личное авторство, Reply/тему, адресата подписи, ответ по факту из сводки, недостаток знаний, отсутствие саммари, независимость наблюдения, остановку/возобновление и отсутствие ответов на пропущенные сообщения.

Состав тестовых чатов и разрешение реальной отправки определить перед этим прогоном. Согласование спецификации не является его выполнением. Редкие гонки и неизвестную доставку проверять управляемыми источниками, не провоцируя их на рабочей переписке.

### Условие завершения реализации

Реализация принята, когда выполнены соответствующие автоматические проверки, браузерные сценарии и ручной прогон, нет известных нарушений принятых правил, переданы инструкции запуска и диагностики. Для каждого результата указать команду/сценарий, среду и итог. Если ручной прогон недоступен, код может быть завершён, но проверка реальной интеграции остаётся явно невыполненной.

## Вне первой версии

Каналы и секретные чаты; ответы на пропущенную переписку; распознавание вложений; отмена при ручном сообщении владельца; автоматические платежи; общая память или саммари других чатов; гарантированное распознавание любых сторонних автоответчиков. Реализация приложения не входит в текущую карту планирования.
