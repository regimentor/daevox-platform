# Реализация и проверка автоответчика

Дата: 2026-09-10. Реализация выполнена поверх существующего рабочего дерева Telegram-секретаря.
Изменения framework, существующий архив и данные Telegram-сессии не откатывались.

## Состав

- `packages/db`: отдельные настройки и журнал намерений, независимая версия настройки, атомарное
  включение наблюдения, восстановление без повторной отправки, инвалидирование дневной сводки.
- `apps/backend/src/domain/auto-reply`: приём после синхронизации, очередь с круговым обслуживанием,
  срок пять минут, локальная модель, подпись, права/платежи/автор/Reply/тема, учёт результатов TDLib.
- Общий `ModelScheduler` для ручных и дневных сводок и автоответов; текущая работа не прерывается.
- Контракт и `POST /api/secretary/auto-reply` проверяют аккаунт, экземпляр backend, период аккаунта
  и версию настройки. Интерфейс показывает настройку, фактическое состояние, причину и отсутствие связи.

## Автоматические проверки

Среда: Linux, Node 26.8.1, npm workspaces, временные SQLite-базы через Drizzle push, управляемые
Telegram и LLM. Проверки дочерних процессов и браузера запускались с разрешением на локальные процессы.
Рабочая БД, рабочая переписка, реальные реквизиты и реальная отправка не использовались.

| Команда                                       | Результат                                                                                                       |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `npm run verify -w @daevox/telegram-contract` | Пройдено, включая валидацию команды автоответчика                                                               |
| `npm run verify -w @daevox/db`                | Пройдено, 6 тестов                                                                                              |
| `npm run verify -w @daevox/backend`           | Пройдено, 58 тестов                                                                                             |
| `npm run verify -w @daevox/web-client`        | Пройдено: типы, 13 тестов, coverage, production build, Storybook build                                          |
| `npm run test:e2e -w @daevox/web-client`      | Пройдено, 3 сценария Chromium                                                                                   |
| Линт затронутых workspace                     | Пройдено                                                                                                        |
| Корневой `npm run lint`                       | Общая команда также проверяет vendor TDLib и падает на существующих ошибках его JavaScript; vendor не изменялся |

Backend проверяет выбор последнего дня и изоляцию чатов, подписанный Reply в теме, служебные ответы,
общую подготовку без повторного ответа, правки входящего и источника сводки, удаление, выключение,
смену аккаунта, потерю связи, границу срока, дубли, temporary/final ID, неизвестный результат без
повтора, задержку FLOOD_WAIT, безопасный resend, ограничения оплаты/Reply/темы и круговое обслуживание.
Отдельный процесс аварийно завершается после записи состояний; повторное открытие БД не оживляет очередь.

Browser e2e проверяет включение наблюдения вместе с автоответчиком, независимое выключение наблюдения,
получение подписанного Reply через настоящий HTTP backend с управляемым TDLib, сохранение настройки
после reload, остановку отправки и блокировку переключателя при недоступном backend. Скриншот проверен.
Ранее существовавший сценарий QR-входа актуализирован под текущий интерфейс TelegramWorkspace.

## Ручная интеграционная проверка — не выполнена

Нужны выбранные пользователем тестовые чаты и отдельное разрешение на реальные сообщения.
Полная приёмка по spec.md пока не завершена. Автоматические проверки не подтверждают доставку
реальным Telegram или качество реальной локальной модели.

1. Остановить backend, сохранить резервную копию архива, применить `npm run db:push`, запустить
   существующий llama-server и backend. Настройки по умолчанию выключены.
2. Выбрать личную переписку, группу с темой и контрольный чат с выключенным автоответчиком.
3. В тестовом чате подготовить дневную сводку с искусственным фактом, включить автоответчик,
   дождаться готовности. С другого аккаунта задать вопрос; проверить личное авторство, Reply,
   тему, подпись отправителя, ответ по факту и отсутствие выдуманных обещаний.
4. Проверить вопрос вне сводки, отсутствие сводки, вложение без текста, русский и другой язык.
5. Выключить наблюдение и проверить новый автоответ. Затем выключить автоответчик и убедиться,
   что новые вопросы не получают ответа, а настройка наблюдения не меняется.
6. Проверить остановку/возобновление backend: сообщения простоя не получают ответов, новое после
   готовности получает ответ. Проверить logout и необходимость повторного включения.
7. Зафиксировать выбранные чаты, модель, фактические результаты и ошибки. Редкие гонки и неизвестную
   доставку не провоцировать на рабочей переписке — они проверены управляемыми источниками.

Запуск и диагностика описаны также в [README backend](../../apps/backend/README.md).

## Уведомления о переключении

По дополнительному запросу пользователя добавлены отдельные сообщения о подключении и отключении.
Backend проверяет порядок быстрых переключений, отсутствие дублей при неизменной настройке,
отсутствие отката настройки при неизвестной доставке и отмену отправки при смене аккаунта.
Browser e2e проверяет оба уведомления вместе с обычным подписанным Reply.
