# Подключение личного Telegram-аккаунта через QR

Состояние: согласовано, готово к реализации.

Спецификация согласованной первой версии. Описывает будущую реализацию; рабочий вход в Telegram в рамках этой карты не выполнялся. Канонические решения и их история находятся в [карте](map.md) и связанных задачах.

## Цель и границы

Локальный пользователь открывает экран Telegram в Daevox, подключает один личный аккаунт через QR, при необходимости вводит пароль двухэтапной аутентификации, видит состояние подключения и может завершить сессию и подключиться снова. Обычный перезапуск backend сохраняет сессию.

Приложение работает на личном ПК, без аутентификации/авторизации пользователя backend, ролей, JWT и отдельного секрета управления. Telegram-авторизация остаётся обязательной для доступа к самому аккаунту. Текущие DB/JWT, прикладная логика backend и схема БД являются удаляемым демо framework; совместимость с ними и миграция демо-данных не требуются.

Не входят в первую версию:

- Вход в Daevox через Telegram, Bot API и вход по номеру телефона.
- Несколько Telegram-аккаунтов, многопользовательский сервис и удалённый доступ к приложению.
- Восстановление забытого 2FA-пароля внутри Daevox и сброс данных из неподдерживаемого шага входа.
- Чтение переписки, выбор чатов и инструменты agentic-задач после подключения.
- Перепроектирование общей библиотеки TDLib. Обнаруженный дефект библиотеки, блокирующий сценарий, оформляется отдельно.

Основание: [владение сессией](issues/02-session-ownership.md), [сценарий экрана](issues/03-connection-screen.md).

## Модули и зависимости

| Модуль                                                    | Ответственность                                                                                                                                                           |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lib/tdlib`, `@daevox/tdlib`                              | Существующий типизированный клиент: invoke, updates, запуск и завершение. Не содержит UI или прикладного сценария. Ограничение zero npm runtime dependencies сохраняется. |
| Прикладной модуль подключения в backend                   | Владеет текущим клиентом TDLib, преобразует updates в состояние экрана, выполняет допустимые команды, управляет версиями, ошибками и восстановлением.                     |
| AppState                                                  | Создаёт и запускает прикладной модуль вместе с backend, обеспечивает штатное закрытие.                                                                                    |
| `packages/telegram-contract`, `@daevox/telegram-contract` | Общие browser-safe DTO и runtime-проверки данных для backend и веб-клиента; без импортов TDLib/framework.                                                                 |
| HTTP-контроллер Telegram                                  | Проверяет запросы, отдаёт снимок, передаёт команды прикладному модулю. Не реализует второй автомат авторизации.                                                           |
| Экран `/telegram` в web-client                            | Отображает снимок, опрашивает backend и отправляет явные действия пользователя.                                                                                           |
| `qrcode.react` в web-client                               | Локальный SVG-рендер актуальной ссылки через `QRCodeSVG`, без внешнего QR-сервиса.                                                                                        |

Использовать npm workspaces. Runtime-зависимости принадлежат workspace-потребителям: TDLib — backend, QR-рендерер — веб-клиент, общий контракт — обоим. Общие dev-инструменты остаются в корне. Новый workspace контрактов должен иметь собственный `verify`, чтобы root orchestration его не пропускала.

Удалить демо AuthController, DialogsController, JWT middleware/service, DB-healthcheck, DB/JWT-config и неиспользуемый workspace `packages/db`; удалить соответствующие импорты, ненужные зависимости и демо-проверки, обновить lockfile. Сохранить bootstrap Application, локальный HTTP healthcheck без БД и необходимые элементы framework. Healthcheck показывает доступность backend, а не готовность Telegram.

Основание: [контракт состояния и команд](issues/04-state-contract.md). Совместимость выбранного QR-рендерера с React 19 и локальное кодирование проверены в [исследовании рендеринга](/tmp/daevox-telegram-qr-research/.scratch/telegram-qr-auth/research/qr-rendering.md).

## Запуск, конфигурация и хранение

- Один локальный экземпляр backend владеет одним клиентом TDLib и одним набором постоянных каталогов сессии. Нельзя одновременно использовать их двумя клиентами.
- Backend слушает loopback вместо демо `0.0.0.0`. Его HTTP и экран доступны без авторизации Telegram и при управляемой ошибке конфигурации/запуска клиента.
- Реквизиты Telegram API-приложения `api_id`/`api_hash`, стабильный ключ шифрования и явные пути к каталогам базы/файлов задаются серверной конфигурацией/.env. Веб-формы для них нет. Пароль 2FA — отдельный временный шаг.
- Реальные секреты и все данные сессии исключаются из Git. Пример конфигурации содержит только заглушки; проверка отсутствующих/неверных значений даёт понятное состояние `configuration_required`, не стирает каталоги и не останавливает остальной backend.
- Веб-клиент использует публичный `VITE_API_BASE_URL`, по умолчанию `http://127.0.0.1:3000`. Backend принимает точный `WEB_CLIENT_ORIGIN`, для текущего dev-сценария `http://127.0.0.1:5173`. Другие локальные порты задаются согласованно; адреса по умолчанию должны совпадать с инструкцией запуска.
- Настроить необходимые CORS/OPTIONS для GET/POST и Content-Type без cookies/credentials и wildcard origin. Проверять Host/Origin; внешние origins не разрешать. Это проверка источника запроса, а не вход пользователя.
- Использовать подготовленную закреплённую TDLib и поддерживаемый локальным проектом Node с `node:ffi`. Backend запускается с `--experimental-ffi`; сборка native artifact остаётся явным шагом workspace TDLib.
- При старте подписаться на необходимые updates до начала обмена, передать параметры и получить текущее состояние. Новая подписка wrapper не воспроизводит прежнее событие автоматически. Восстановленное состояние, включая промежуточное, нельзя безусловно заменять новым QR-входом.
- При штатной остановке закрыть клиент с сохранением сессии. После окончательного закрытия/управляемого фатального сбоя новый экземпляр создаётся только после освобождения старого; результаты и callbacks прежнего поколения не меняют новое состояние.

Штатное восстановление TDLib сохраняется: она может продолжить записанный `logOut` после перезапуска. Backend не ведёт собственного постоянного намерения выхода и не повторяет команду от себя. Перезапуск не обещает отмены выхода. При аварийном завершении процесса до записи данных на диск сохранность не гарантирована.

Управляемая ошибка клиента показывается как `failed` с явным перезапуском. Авария всего backend-процесса наблюдается браузером как потеря связи с backend; этот проект не обещает изоляцию аварии нативной библиотеки от процесса.

Основание: [ограничения TDLib](issues/01-qr-protocol-research.md), [владение сессией](issues/02-session-ownership.md).

## Пользовательский сценарий

Согласованный внешний вид и переходы: [решение экрана](issues/03-connection-screen.md), [интерактивный первоисточник](/tmp/daevox-telegram-qr-prototype/apps/web-client/app/prototypes/telegram-connection.prototype.html).

| Ситуация                                    | Что видит пользователь и какие действия доступны                                                                                                    |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сессии нет                                  | Кнопка «Подключить Telegram». Открытие страницы само по себе не начинает вход.                                                                      |
| Команда входа принята, ссылки ещё нет       | Ожидание получения QR; успешный HTTP-ответ ещё не означает готовность QR.                                                                           |
| Ожидание подтверждения на другом устройстве | Актуальный QR и краткие инструкции. Ссылка обновляется на том же шаге автоматически; ручной кнопки обновления и точного countdown нет.              |
| Требуется 2FA                               | Поле пароля и «Продолжить». После отправки поле очищается, повторная отправка до результата/разрешения повторить недоступна.                        |
| Неверный пароль                             | Ошибка на том же шаге, возможность новой попытки когда она разрешена. Старую ошибку не переносить в другой шаг.                                     |
| Ограничение попыток                         | Понятное ожидание; срок показывается только когда известен. Фиксированного числа попыток или выдуманного таймера нет.                               |
| Авторизация подтверждена                    | Имя и username при наличии, действие «Отключить аккаунт». Пока метаданные загружаются или недоступны, не объявлять аккаунт неавторизованным.        |
| Пользователь нажал «Отключить»              | Подтверждение «Отключить» / «Оставить подключённым» и объяснение необходимости нового входа после выхода.                                           |
| Выход выполняется                           | Ожидание подтверждения Telegram, в том числе без сети. Новый вход до завершения старого экземпляра недоступен. Закрытие страницы не отменяет выход. |
| Выход подтверждён                           | Состояние без подключённого аккаунта, доступен новый QR-вход.                                                                                       |
| Потеря сети Telegram                        | Сообщение о связи отдельно от авторизации. Авторизованный аккаунт не считается отключённым. QR скрыт до актуальной ссылки после восстановления.     |
| Потеря backend                              | Последнее известное состояние явно обозначено, QR скрыт, команды заблокированы. После восстановления получить новый снимок.                         |
| Фатальный сбой клиента                      | Ошибка и «Перезапустить подключение». Сохранённая сессия используется повторно, если пригодна.                                                      |
| Сессия отозвана в Telegram                  | Сообщение о завершении сессии и возможность нового входа.                                                                                           |
| Неверная конфигурация                       | Понятное сообщение об исправлении серверных настроек; backend остаётся доступным.                                                                   |
| Шаг вне QR/2FA                              | Сообщение о неподдерживаемом состоянии и «Проверить состояние», без сброса данных или нового входа.                                                 |

При повторном открытии экрана состояние восстанавливается из backend, а пароль не сохраняется. Пояснение для забытого пароля не запускает recovery-процесс в Daevox.

QR рендерится локально через `QRCodeSVG`: полная строка в `value`, `marginSize={4}`, согласованная область 180px, контрастные тёмные модули на светлом фоне в обеих темах, без `imageSettings`. Демонстрационная область вместо QR, вымышленный аккаунт, панели состояния модели и сценарные кнопки прототипа в продукт не переносятся.

## HTTP-контракт

| Метод и путь                    | Назначение                                       | Тело                   |
| ------------------------------- | ------------------------------------------------ | ---------------------- |
| `GET /api/telegram/state`       | Полный снимок, в том числе «Проверить состояние» | Нет                    |
| `POST /api/telegram/connect`    | Начать QR-вход                                   | `expected`             |
| `POST /api/telegram/password`   | Передать пароль 2FA                              | `expected`, `password` |
| `POST /api/telegram/disconnect` | Начать выход после подтверждения                 | `expected`             |
| `POST /api/telegram/restart`    | Явно восстановить клиент после сбоя              | `expected`             |

`expected` содержит `instanceId` и `controlVersion` последнего применённого снимка. Вход проверяется во время выполнения, неизвестные/неверные поля отклоняются. Generic JSON parser framework не заменяет такую проверку. Пароль и QR не передаются в URL. Ответы имеют `Cache-Control: no-store`.

### Снимок

| Поле                                    | Контракт                                                                                                                                                       |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `instanceId`                            | Случайный идентификатор текущего запуска backend.                                                                                                              |
| `revision`                              | Монотонная версия снимка в пределах instanceId.                                                                                                                |
| `controlVersion`                        | Версия контекста команд; меняется при смене шага/допустимости действий/поколения клиента и принятии/завершении команды. Одна ротация QR её не меняет.          |
| `client`                                | `initializing`, `running`, `failed`, `configuration_required`.                                                                                                 |
| `connection`                            | `unknown`, `offline`, `connecting`, `ready`, независимо от авторизации.                                                                                        |
| `authorization.kind`                    | `initializing`, `not_connected`, `requesting_qr`, `qr`, `password`, `connected`, `logging_out`, `unsupported`. Остальные поля зависят от варианта.             |
| `authorization.link` для `qr`           | Полная актуальная строка или `null`, если нужно ждать новую ссылку. В других вариантах этого поля нет.                                                         |
| `authorization.account` для `connected` | `{ id: string, displayName: string, username: string \| null }` либо `null` до получения метаданных. В других вариантах этого поля нет.                        |
| `allowedActions`                        | Подмножество `connect`, `submit_password`, `disconnect`, `restart`. Сервер всё равно повторно проверяет действие.                                              |
| `operation`                             | `null` либо текущая/последняя операция: `id`, `kind`, `status` (`pending`, `completed`, `failed`) и безопасная ошибка при наличии. Входных секретов в ней нет. |
| `error`                                 | `null` либо безопасная прикладная ошибка с кодом, сообщением и необязательным `retryAt`, если срок повтора действительно известен.                             |

WaitingForNetwork отображается как offline; Connecting/ConnectingToProxy — connecting; Updating/Ready — ready. Сырые updates TDLib в браузер не передаются. Новое состояние сохраняется в прикладном модуле до выдачи через GET; вкладки наблюдают один источник состояния.

Сведения об аккаунте backend получает через getMe после Ready. Ошибка этого дополнительного чтения не сбрасывает авторизацию. Backend убирает QR после смены шага, потери готовности связи или смены клиента; после восстановления ждёт актуальное событие текущего экземпляра TDLib. Публичного TTL ссылки нет.

### Исполнение команд

1. Атомарно проверить expected, доступность клиента и допустимость действия. Отметить единственную активную изменяющую команду и изменить controlVersion до первого асинхронного ожидания.
2. Вернуть `202 { instanceId, operationId }` после принятия в память backend. Продолжить выполнение независимо от жизни HTTP-запроса/страницы.
3. Публиковать ход и результат в снимках. Ok от TDLib не заменяет соответствующее состояние авторизации: QR должен быть получен, авторизация подтверждена, выход — завершён с освобождением экземпляра.
4. При ошибке обновить operation/error и допустимые действия. Долгое ожидание не становится ошибкой только из-за истечения времени HTTP.

Нет очереди конфликтующих команд. Параллельная команда либо действие из устаревшего контекста получает 409 и не доходит до TDLib. После перезапуска instanceId другой, старые команды отклоняются. Операции/версии живут только в памяти; replay, журнал команд и собственное восстановление намерения выйти отсутствуют.

Команда connect завершается при получении подходящего следующего шага QR-входа, а не удерживает общую блокировку всё время ожидания сканирования. На шаге пароля можно принять отдельную команду password. Команда disconnect остаётся незавершённой до подтверждённого выхода; перезапуск клиента не создаёт второй экземпляр поверх ещё работающего старого.

### Ошибки

- До принятия команды: неверное тело — 400; устаревший контекст, занятость или недопустимое состояние — 409; недоступный клиент/конфигурация — 503.
- GET возвращает 200 со снимком даже при ошибке Telegram или отсутствии конфигурации, если сам backend доступен.
- Ошибка уже принятой команды находится в последующем снимке. Стабильные коды: `invalid_request`, `stale_state`, `busy`, `invalid_state`, `invalid_password`, `rate_limited`, `configuration_error`, `client_unavailable`, `telegram_error`.
- Неизвестные ошибки преобразуются в общее безопасное сообщение. Сырые сообщения/структуры TDLib не пересылаются и не логируются вместе с секретами.
- При новой попытке или смене шага старая ошибка команды очищается. Параметры повторной попытки публикуются только если надёжно известны.

### Поведение веб-клиента

- Полный снимок при открытии, возврате на экран и после команды; далее опрос через 1 секунду после завершения предыдущего чтения. Одновременно выполняется не более одного GET.
- Уход со страницы/скрытие вкладки приостанавливает опрос. При возврате сначала обновляется состояние; старый QR не считается актуальным без этого обновления.
- Сетевой timeout GET/POST — 5 секунд. После потери связи повторяются только GET с задержкой 1, 2, 4, далее максимум 5 секунд; после успешного снимка возвращается обычный опрос.
- Неактуальные GET-ответы отбрасываются по порядковому номеру чтения. Новый снимок после команды/возврата инвалидирует старое чтение; запоздавший ответ не включает действия и не возвращает старый QR.
- POST не повторяется автоматически, даже при потере ответа. Сначала читается состояние; двойной клик локально блокируется, а серверная версия защищает от гонки вкладок.
- Пароль очищается после передачи и не сохраняется в browser storage. Пароль, QR, реквизиты и дампы авторизации не попадают в логи, трекер и постоянное хранилище браузера.

Полное основание и история выбора: [контракт состояния и команд](issues/04-state-contract.md).

## Приёмка

Реализация принята только после автоматических проверок и ручного прогона с реальным аккаунтом. Матрица ниже — план будущей проверки, не отчёт об уже выполненных тестах.

### Автоматические проверки без личного аккаунта

Использовать управляемую зависимость TDLib и реальные прикладные интерфейсы. Проверять наблюдаемое поведение, не копировать реализацию в тест. Временные каталоги тестов не совпадают с каталогами личной сессии.

| Уровень           | Что должно быть доказано                                                                                                                                                                                                                                                                |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Прикладной модуль | QR-вход с 2FA и без неё; получение и ротация ссылки при неизменном типе состояния; неверный пароль и ограничение попыток; Ready отдельно от сети; завершение выхода отдельно от Ok.                                                                                                     |
| Жизненный цикл    | Старт backend без готового Telegram; неверная конфигурация не блокирует healthcheck/снимок; восстановление моделируемых готового и промежуточных состояний; штатное сохранение сессии; явный restart после ошибки; освобождение старого клиента и отбрасывание его поздних результатов. |
| Гонки и команды   | Два одновременных POST дают одну принятую команду и один отказ; stale instanceId/controlVersion отвергаются до invoke; QR-ротация не создаёт ложный конфликт контекста; HTTP 202 предшествует результату; потеря HTTP-ответа не создаёт повторного invoke.                              |
| Ошибки и данные   | Runtime-проверка DTO, безопасные сообщения, очистка прежних ошибок, неподдерживаемый шаг без сброса; пароль/реквизиты отсутствуют в любых снимках, QR — вне соответствующего шага. Секреты и QR не попадают в логи и browser storage.                                                   |
| Настоящий HTTP    | GET/POST/OPTIONS, коды и заголовки, корректная конфигурация адреса API, разрешённый локальный origin и отказ чужому origin; API работает после удаления демо DB/JWT.                                                                                                                    |
| UI                | Начальный снимок, непересекающийся polling, скрытие/возврат вкладки, отбрасывание запоздавшего GET, раздельные ошибки сети Telegram/backend, скрытие/обновление QR, очистка поля пароля, блокировка повторной отправки и подтверждение выхода.                                          |
| Browser e2e       | Сквозной основной сценарий с реальным тестовым HTTP backend и управляемой TDLib, включая две вкладки. Только browser route mocks не считаются проверкой CORS/реального HTTP.                                                                                                            |
| QR и отображение  | Локальное SVG-кодирование актуальной ссылки без внешних запросов, читаемые элементы в светлой/тёмной темах и на узком экране; читаемость настоящего QR подтверждается ручным сканированием.                                                                                             |

Модель должна покрывать перезапуск во время выхода в обоих допустимых результатах: TDLib восстановила LoggingOut либо прислала иное фактическое состояние. Backend не добавляет собственного механизма повторной отправки. Для обязательного native smoke достаточно offline-вызова, но он не заменяет проверку авторизации.

### Команды проверки

Из корня репозитория после реализации:

```sh
npm run verify -w @daevox/telegram-contract
npm run verify -w @daevox/backend
npm run verify -w @daevox/web-client
npm run test:e2e -w @daevox/web-client
npm run verify -w @daevox/tdlib
npm run lint
npm run format:check
```

`verify` нового workspace контрактов должен быть добавлен при его реализации. TDLib verify включает check, unit и native smoke; для него нужны существующие native artifact/metadata, поддерживаемый Node с FFI и используемый скриптом `mise`. Если artifact ещё не подготовлен, явная подготовка — `npm run build -w @daevox/tdlib`; сборку не скрывать внутри запуска приложения. Она требует системных средств сборки из README TDLib.

Root `npm run verify` остаётся общей orchestration-командой, но не заменяет отдельные lint/format и web e2e. Нерелевантные существующие сбои отмечаются отдельно; проверки, непосредственно доказывающие эту функциональность, должны пройти.

### Ручной сквозной прогон

Проводится после автоматических проверок, с подготовленной TDLib, реальными реквизитами и аккаунтом пользователя. Реквизиты, ключи и данные сессии остаются вне Git; QR и пароль не включаются в отчёт.

1. Открыть локальный `/telegram` без входа в Daevox. Запросить QR, дождаться как минимум одной ротации без сканирования; экран заменяет код на том же шаге.
2. Отсканировать актуальный код настоящим Telegram-клиентом и подтвердить вход. Если у аккаунта включена 2FA, пройти имеющийся шаг пароля. Увидеть подключённый аккаунт с корректными сведениями.
3. Повторно открыть страницу, затем штатно перезапустить backend с теми же каталогами и ключом. Подключение восстанавливается без нового QR; пароль не сохранён в форме.
4. Подтвердить «Отключить аккаунт». Дождаться фактического завершения, проверить завершение соответствующей сессии в Telegram и возврат к состоянию без подключённого аккаунта.
5. Выполнить новый QR-вход и убедиться, что старый экземпляр/данные операции не мешают повторному подключению.

Настройки 2FA не меняются ради приёмки. В отчёте указать, какой реальный вариант пройден; оба варианта обязательны в автоматических сценариях. Редкие состояния, принудительные сбои, отзыв сессии и потери связи обязательно моделируются автоматически; дополнительно наблюдённые реальные случаи можно приложить к отчёту, но искусственно провоцировать flood limits или менять настройки аккаунта не требуется.

Отчёт реализации содержит результат автоматических команд и ручных шагов, ревизию кода/TDLib и ограничения проверки, без секретов. Если ручной прогон ещё не выполнен, реализация не помечается принятой: указывается, что автоматические проверки пройдены, а сквозная приёмка ожидается.

Основание: [критерии приёмки](issues/05-acceptance-spec.md).
