## Question

Какие наблюдаемые результаты достаточны, чтобы считать QR-подключение реализованным, и какие проверки должны выполняться автоматически либо вручную с настоящим аккаунтом?

Согласовать проверку первого входа с 2FA и без неё, обновления QR, неверного пароля, восстановления сохранённой сессии, перезапуска backend, потери сети, отключения и повторного входа. Учесть решения по доступу и нескольким вкладкам. Проверить оставшийся туман карты, явно определить поддерживаемые и неподдерживаемые сценарии и собрать согласованную спецификацию `../spec.md` со ссылками на решения, без реализации функциональности.

Для сценария перезапуска во время выхода проверить принятую границу: собственного сохранения намерения и повторной отправки logOut в backend нет, но штатное восстановление TDLib допускается. Проверить работу локального приложения без демо DB/JWT, отсутствие секретов/данных сессии в Git и доступность backend при ошибочной конфигурации Telegram.

Опора на согласованный HTTP-контракт: проверить начальный снимок и polling без пересечения GET, отбрасывание запоздавших ответов, HTTP 202 отдельно от результата TDLib, отсутствие автоматического повтора POST при потере ответа, конфликт команд двух вкладок и устаревший instanceId/controlVersion. Проверить временное скрытие QR при потере связи, актуализацию ссылки, локальный SVG-рендер без внешних ресурсов и очистку поля пароля. Уточнить, какие из этих гарантий доказываются тестами прикладного модуля/HTTP/UI без аккаунта, а какие требуют ручного прогона с TDLib.

## Answer

Согласован обязательный критерий готовности реализации: автоматические проверки без личного аккаунта плюс ручной сквозной прогон на аккаунте пользователя. Только автотестов недостаточно, чтобы объявить реализацию принятой.

- Автоматически покрыть оба пути входа — с 2FA и без неё, ротацию QR, ошибки пароля и ограничения попыток, сохранение/восстановление моделируемого состояния, штатное закрытие, фатальный сбой и поздние callbacks старого экземпляра.
- Через прикладной модуль и реальный тестовый HTTP проверить DTO, коды/заголовки, 202 отдельно от результата, конфликты вкладок, stale instanceId/controlVersion и отсутствие автоматического повтора принятой команды. Для браузерного e2e нужен тестовый backend с управляемой зависимостью TDLib; только route mocks не доказывают CORS/реальный HTTP.
- Проверить наблюдаемое поведение UI: polling, запоздавшие ответы, потерю сети Telegram отдельно от backend, видимость актуального QR, очистку пароля, подтверждение выхода и неподдерживаемое состояние без сброса. Проверить локальный SVG-рендер, светлую/тёмную темы и узкий экран.
- Подтвердить удаление зависимостей от демо DB/JWT, доступность backend при неготовом Telegram/ошибочной конфигурации, отсутствие секретов и сессии в Git и отсутствие секретов/QR в логах и browser storage.
- Сохранить существующие проверки целостности и native smoke TDLib. Offline smoke не является проверкой настоящего входа, сохранения аккаунта или выхода.
- Вручную дождаться обновления QR, войти с фактическими настройками аккаунта, повторно открыть страницу и перезапустить backend с сохранённой сессией, выполнить подтверждённый выход и новый вход. Настройки 2FA не менять ради проверки; в отчёте указать реально пройденную ветку. Остальные редкие/аварийные случаи обязательны в управляемых автоматических сценариях, искусственно провоцировать flood limits не требуется.
- Отчёт будущей реализации содержит результаты команд/ручных шагов, ревизии и ограничения без секретов. Если ручной прогон не выполнен, приёмка остаётся незавершённой.

Собрана [итоговая спецификация](../spec.md) с принятыми границами, сценарием, модулями, HTTP-контрактом, матрицей и командами проверки, ручным прогоном и указателями на первоисточники. Все остальные задачи карты разрешены, неоформленных вопросов к реализации в текущем scope не осталось. Новые задачи для реализации в этой сессии не создавались.
