## Question

Какой прикладной контракт передаёт согласованные состояния подключения и команды между backend и веб-клиентом? Выбрать доставку обновлений и получение начального снимка, форму состояний/ошибок, операции начала QR-входа, ввода 2FA и отключения, а также защиту от устаревших команд и конкурирующих вкладок.

Определить владельца актуальной QR-ссылки, очистку чувствительных временных данных, восстановление отображения после переподключения веб-клиента и границы преобразования сырых состояний TDLib. Выбрать способ отображения QR и допустимые зависимости согласно правилам npm workspaces. Основываться на принятых сценариях и возможностях framework; не проектировать универсальный Telegram API для браузера.

Демо DB/JWT и текущую прикладную логику backend можно удалить при реализации; совместимость с ними не требуется. Контракт предназначен для локального приложения без аутентификации/авторизации пользователя, без токена управления и без привязки Telegram-сессии к демо-пользователю БД. Определить необходимый каркас backend взамен демо в рамках этого контракта. Секреты и содержимое сессии исключаются из Git.

Реализовать согласованные границы владения: локальное прослушивание вместо демо `0.0.0.0`, доступность backend при неготовом Telegram, штатное сохранение сессии, явный перезапуск после фатального сбоя и освобождение старого экземпляра до создания нового. Backend не хранит намерение выхода между запусками и не повторяет команду сам; восстановленное состояние TDLib доставляется как фактическое.

Учесть результаты исследования: QR обновляется без смены типа состояния, snapshot и события могут приходить в разном порядке, конкурирующие authentication-команды влияют друг на друга, а timeout/AbortSignal wrapper не отменяет уже отправленную операцию. Согласовать классификацию ошибок и неизвестных состояний, ожидание ограничений частоты и восстановление после прекращения подписки.

Опора на согласованный прототип: вход начинается явно; отдельно представлены ожидание QR, пароль/ожидание проверки/ограничение попыток, подключение, выход, ошибка конфигурации и фатальный сбой. Потеря сети Telegram отделена от потери связи веб-клиента с backend. Для неподдерживаемого шага нужна только проверка состояния, без сброса; восстановление забытого 2FA-пароля не входит в первую версию. Задать критерий, когда QR скрывается и когда снова считается актуальным, и обеспечить получение имени/username подключённого аккаунта. Панели управления моделью из прототипа в продукт не переносятся.

## Answer

Согласован контракт локального экрана Telegram: единое состояние backend, HTTP polling, принятие команд отдельно от их результата и описанное разделение модулей. Далее — точная запись контракта для последующей реализации.

### HTTP и доставка

| Маршрут                         | Назначение                                                   |
| ------------------------------- | ------------------------------------------------------------ |
| `GET /api/telegram/state`       | Полный текущий снимок; также действие «Проверить состояние». |
| `POST /api/telegram/connect`    | Начать QR-вход из допустимого состояния.                     |
| `POST /api/telegram/password`   | Передать пароль текущего 2FA-шага.                           |
| `POST /api/telegram/disconnect` | Начать подтверждённый пользователем выход.                   |
| `POST /api/telegram/restart`    | Явно восстановить клиент после фатального сбоя.              |

- Веб-страница — `/telegram`. Чтение состояния не запускает новую авторизацию и не является проверкой удалённой действительности сессии.
- Веб-клиент использует явный публичный `VITE_API_BASE_URL` с локальным адресом backend (по умолчанию `http://127.0.0.1:3000`), а не относительный `/api` на сервере React Router. Backend разрешает точный настроенный `WEB_CLIENT_ORIGIN` (для текущего dev-сценария `http://127.0.0.1:5173`), отдаёт необходимые CORS/OPTIONS для GET/POST и Content-Type, без cookies/credentials и без wildcard origin. Порты/адреса настраиваются согласованно для локального запуска; API proxy и reverse proxy для этого контракта не требуются.
- На открытой видимой странице один GET одновременно. Следующий опрос — через 1 секунду после завершения предыдущего; при открытии, возврате на страницу и после команды — немедленный новый снимок. Уход со страницы/скрытие вкладки приостанавливает опрос; возврат сначала обновляет состояние.
- Ответы состояния и команд имеют `Cache-Control: no-store`; QR, пароль и ошибки не попадают в URL. У GET нет побочных эффектов авторизации.
- Сетевое ожидание GET/POST ограничено 5 секундами на стороне браузера. После потери связи повторяются только чтения, с задержкой 1, 2, 4, затем максимум 5 секунд. Получение успешного снимка возвращает обычный опрос.
- Неактуальные ответы GET отбрасываются по порядковому номеру чтения в браузере. Новый снимок после команды/возврата на экран инвалидирует предыдущее чтение; ответа старого запроса недостаточно для повторного включения действий.

### Форма снимка

Снимок — browser-safe DTO без импортов TDLib или framework:

- `instanceId`: случайный идентификатор текущего запуска backend.
- `revision`: монотонная версия опубликованного снимка в пределах instanceId.
- `controlVersion`: версия контекста допустимых команд. Меняется при изменении шага, доступности действий, поколения клиента или принятии/завершении команды; одна лишь смена QR-ссылки не отменяет допустимые команды.
- `client`: `initializing | running | failed | configuration_required`.
- `connection`: `unknown | offline | connecting | ready`, отдельно от авторизации. WaitingForNetwork соответствует offline; Connecting/ConnectingToProxy — connecting; Updating/Ready — ready, поскольку обновление данных не означает отсутствие сетевого соединения.
- `authorization`: discriminated union по `kind`: `initializing`, `not_connected`, `requesting_qr`, `qr`, `password`, `connected`, `logging_out`, `unsupported`. Поля отдельного варианта не присутствуют в остальных вариантах.
- Для `qr`: `link: string | null`; null означает ожидание актуальной ссылки. Для `connected`: `account: { id: string; displayName: string; username: string | null } | null`. Пока сведения об аккаунте загружаются, факт авторизации остаётся действительным; отсутствие метаданных не начинает новый вход.
- `allowedActions`: подмножество `connect | submit_password | disconnect | restart`; определяет отображение, но сервер повторно проверяет каждую команду.
- `operation`: текущая либо последняя операция без её входных секретов — `id`, `kind`, `status: pending | completed | failed`, безопасная ошибка при наличии. Завершение команды не подменяет состояние авторизации.
- `error`: безопасное прикладное сообщение с кодом и необязательным `retryAt`, когда срок повтора действительно известен. QR и пароль не включаются в текст ошибки.

Backend единолично преобразует TDLib updates в снимок. Новое состояние сохраняется прежде, чем станет доступно GET; для нескольких вкладок возвращается одна и та же версия. Локальная потеря связи с backend хранится в веб-клиенте, а не выдаётся за состояние Telegram.

### Команды, гонки и потеря ответа

- Все POST принимают `expected: { instanceId, controlVersion }`; password дополнительно принимает только `password`. Тело проверяется во время выполнения, неизвестные/неверные поля отклоняются. Generic у framework JSON parser сам по себе не является проверкой данных.
- Backend атомарно проверяет ожидаемый контекст и допустимость действия, отмечает единственную активную изменяющую команду и меняет controlVersion до первого асинхронного ожидания. Из другой вкладки параллельное либо устаревшее действие получает 409, без постановки в очередь.
- Принятая команда возвращает `202 { instanceId, operationId }` сразу после регистрации в памяти backend. Это означает принятие, не авторизацию/завершение выхода. Ход операции и реальный результат видны через снимки.
- HTTP timeout, закрытие страницы или потеря ответа не отменяют уже принятую команду. Веб-клиент не повторяет POST автоматически: сначала получает актуальный снимок, затем показывает доступные действия. Долгая операция остаётся ожидающей, а не превращается в ошибку только по времени.
- GET/HTTP timeout не переносится как отмена в TDLib invoke. При завершении/ошибке команды backend обновляет состояние; QR-вход и выход не считаются законченными по одному Ok: необходим соответствующий шаг авторизации/завершение клиента.
- Операции и версии хранятся только в памяти; после перезапуска instanceId новый, старые POST отклоняются. Журнал команд, автоматический replay и собственное сохранение намерения выйти отсутствуют.

### Ошибки и чувствительные данные

- Неверное тело — HTTP 400; устаревший контекст, недопустимое состояние или занятая операция — 409. Недоступный клиент/конфигурация до принятия команды — 503. GET при этих состояниях возвращает 200 со снимком, чтобы экран продолжал работать.
- Ошибка уже принятой команды отражается в operation/error следующего снимка и очищается при новой попытке либо переходе в другой шаг авторизации; старую ошибку пароля нельзя показывать у подключённого аккаунта. Минимальные стабильные коды: `invalid_request`, `stale_state`, `busy`, `invalid_state`, `invalid_password`, `rate_limited`, `configuration_error`, `client_unavailable`, `telegram_error`.
- Неизвестные ошибки TDLib преобразуются в безопасное общее сообщение; сырые сообщения и произвольные структуры TDLib в браузер не пересылаются. Параметры повторной попытки передаются лишь когда надёжно известны, фиксированного лимита попыток или выдуманного таймера нет.
- Пароль существует только в поле/теле запроса и памяти выполняемого вызова; после передачи UI очищает поле. Пароль, QR-ссылки, реквизиты и дампы авторизации не логируются и не сохраняются в browser storage/трекер.
- Транспорт локальный, без аутентификации пользователя. POST принимает JSON, проверяются Host/Origin для локального веб-клиента; произвольные внешние origins не разрешаются. Это проверка источника запроса, не дополнительный вход или секрет управления.

### QR и восстановление

- Backend владеет QR-ссылкой и убирает её из снимка после смены шага, потери готовности связи с Telegram или смены экземпляра клиента. После восстановления сети QR появляется только по актуальному событию авторизации текущего экземпляра TDLib.
- При потере связи с backend браузер скрывает QR и блокирует команды; новый снимок восстанавливает отображение. QR не имеет клиентского countdown, поскольку публичный TTL неизвестен.
- Сведения об аккаунте backend получает через getMe после Ready; отображение Connected не зависит от успеха этого дополнительного чтения. Невозможность загрузить метаданные отображается как отдельная безопасная ошибка, не как выход из Telegram.
- Потеря подписки на TDLib/фатальная ошибка переводят модуль в failed; дальнейшие команды блокируются до явного восстановления. Новый экземпляр не использует ресурсы старого до подтверждённого освобождения.

### Модули и замена демо

- AppState владеет прикладным модулем подключения Telegram. Транспортные handlers читают снимок и передают узкие команды этому модулю; сам TDLib наружу не выдаётся.
- Общий browser-safe workspace `packages/telegram-contract` (`@daevox/telegram-contract`) содержит DTO и проверки данных без runtime-зависимости на TDLib/framework. Его используют backend и веб-клиент.
- Backend получает runtime-зависимость на `@daevox/tdlib`. Для локального SVG-рендера в веб-клиенте используется `qrcode.react` с `QRCodeSVG`, полной ссылкой в `value`, `marginSize={4}` и без imageSettings/внешних ресурсов. Размер соответствует согласованной области QR (180px), цвета самого QR — контрастные тёмные модули на светлом фоне в обеих темах. Ограничение zero npm deps библиотеки TDLib сохраняется.
- При реализации удалить демо AuthController/DialogsController/JWT middleware и service, DB-healthcheck, DB/JWT-config и неиспользуемый демо workspace `packages/db`; зависимости и проверки, обслуживающие только демо, удалить вместе с ними. Сохранить bootstrap Application, локальный HTTP healthcheck без доступа к БД и необходимый framework.
- Секреты и постоянные каталоги исключить из Git; пример конфигурации содержит только заглушки. Сборка/запуск backend учитывают существующий native artifact TDLib и `--experimental-ffi`.
