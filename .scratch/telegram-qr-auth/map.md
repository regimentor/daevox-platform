# Подключение личного Telegram-аккаунта через QR

Labels: wayfinder:map
Status: resolved

## Текущее состояние

Подключение реализовано. Результаты и границы приёмки — в
[отчёте реализации](implementation.md), текущий запуск — в [README backend](../../apps/backend/README.md).

Остальные разделы сохраняют ход исходного проектирования. `Status: resolved` у карты
означает завершение планирования; приёмка и последующие задачи имеют собственные статусы.

## Destination

Согласованные решения и спецификация подключения личного Telegram-аккаунта к Daevox через QR в веб-клиенте, достаточные для последующей реализации backend и UI. Сценарий включает пароль 2FA, сохранение сессии после перезапуска, состояние подключения, отключение и повторный вход.

## Notes

- Пользователь подтвердил цель и перечисленные границы 2026-09-09. Это планирование по `wayfinder`; код приложения в этой карте не реализуется.
- Для обсуждений применять `grilling` и `domain-modeling`; для исследования — `research`; для обсуждения экрана — `prototype`.
- Исходный сценарий из карты [Клиент TDLib для Daevox](../tdlib-client/map.md): self-hosted на личном ПК, один личный Telegram-аккаунт. Пользователь подтвердил локальное приложение без аутентификации и авторизации пользователя backend. Многопользовательский сервис не проектируется.
- Подключение Telegram-аккаунта означает предоставление Daevox авторизованной Telegram-сессии. Текущие авторизация backend, прикладная логика и схема БД — демо для проверки framework; пользователь разрешил удалить их при реализации. Сохранять совместимость с демо или связывать Telegram-сессию с демо-пользователем не требуется.
- Библиотека `@daevox/tdlib` уже предоставляет invoke, обновления и lifecycle. По решению [Владение сессией и жизненный цикл клиента TDLib](../tdlib-client/issues/03-session-lifecycle.md) приложение управляет авторизацией и QR. Интеграция с backend ранее отложена; AppState — предполагаемая точка владения.
- На момент исследования backend содержит демо DB/JWT и не подключает TDLib; веб-клиент — стартовый каркас. Готового интерфейса подключения или доставки его состояния пока нет; демо не является продуктовым требованием.
- Ограничение zero npm runtime dependencies из прежней карты относится к библиотеке TDLib; автоматически распространять его на UI и backend нельзя. Разделение зависимостей и QR-рендерер определены в решении о контракте backend и веб-клиента.
- Трекер: `docs/agents/issue-tracker.md`. У открытой невзятой задачи нет Status; взятие — `Status: claimed`, завершение — `Status: resolved`. Blocked by ссылается на номера дочерних задач. Детали решения живут в Answer задачи; карта содержит только указатели.
- Итог: [согласованная спецификация для реализации](spec.md). Карта завершена; реализация и её приёмка выполняются следующим отдельным этапом.

## Decisions so far

- [Ограничения QR-авторизации и завершения сессии TDLib](issues/01-qr-protocol-research.md): подтверждены ротация QR, 2FA, восстановление и различия закрытия/выхода; выявлены требования к актуальному состоянию и согласованию команд.
- [Владение Telegram-сессией и доступ к управлению подключением](issues/02-session-ownership.md): один клиент в AppState, локальное использование без входа в backend, серверные секреты вне Git и штатное восстановление TDLib без собственного возобновления выхода.
- [Пользовательский сценарий экрана подключения Telegram](issues/03-connection-screen.md): согласованы отдельный экран, явный QR-вход, шаг 2FA, подтверждение отключения и отображение состояний связи и сбоев по интерактивному прототипу.
- [Контракт состояния и команд между backend и веб-клиентом](issues/04-state-contract.md): полный снимок по HTTP, polling раз в секунду, команды с 202 и проверкой версии; общий workspace DTO, локальный SVG QR и замена демо DB/JWT.
- [Критерии приёмки и полнота спецификации QR-подключения](issues/05-acceptance-spec.md): обязательны автоматические проверки и ручной прогон с текущими настройками аккаунта; итоговая спецификация собрана, карта готова к передаче в реализацию.

## Out of scope

- Реализация и развёртывание функциональности в рамках этой карты.
- Вход в сам Daevox через Telegram, Telegram Login и Bot API.
- Вход по номеру телефона как запасной способ авторизации.
- Восстановление забытого 2FA-пароля внутри Daevox и сброс данных из неподдерживаемого шага входа в первой версии; границы зафиксированы в [сценарии экрана подключения Telegram](issues/03-connection-screen.md).
- Несколько Telegram-аккаунтов и проектирование многопользовательского сервиса.
- Аутентификация/авторизация пользователя backend, отдельный секрет управления и удалённый доступ к приложению.
- Чтение переписки, выбор чатов и инструменты agentic-задач после подключения.
- Перепроектирование общей библиотеки TDLib; обнаруженные дефекты оформляются отдельно, если блокируют выбранный сценарий.
