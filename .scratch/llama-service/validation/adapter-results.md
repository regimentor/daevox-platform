# Проверка Rust-адаптеров

2026-09-13. Изолированный стенд `/tmp/daevox-rust-adapter-validation`; приложение не менялось. Код и Cargo.lock сохраняются в `codex/prototype-llama-adapters`, `experiments/llama-adapters/`.

## Проверено

### hf-hub 1.0.0

Собран реальный crate, не Python-замена. Локальный HTTP-сервер отдаёт файл 4 MiB порциями с задержкой. Timeout Future после 250 мс оставил 819200 байт под конечным именем model.gguf; спустя ещё 250 мс размер не изменился. Повтор успешно скачал 4194304 байта. Оба GET без Range: обычный `download_file().local_dir()` повторяет загрузку с начала. Исходник версии подтверждает File::create и отсутствие Range на этом пути.

Реальный публичный GGUF: `bartowski/SmolLM2-135M-Instruct-GGUF`, revision `09816acd5d99df7be770d85ea30822623dab342c`, Q4_K_M, 105454432 байта. Rust-worker остановлен после создания файла (16375 байт). Повторный worker завершился с Result::Ok; SHA256 `2e8040ceae7815abe0dcb3540b9995eaa1fa0d2ca9e797d0a635ae4433c68c2d` совпал с предыдущей загрузкой. Получены события прогресса и Complete. Повторный успех не доказывает сетевую докачку; отдельная семантика отмены Xet Future не проверена. Процесс worker — проверенная граница остановки.

Следствия для проектирования, требующие фиксации:
- Загружать только в каталог незавершённой операции, публиковать локальный комплект после успешного Result; существование файла с именем .gguf не означает завершённость. Это не дополнительный этап integrity-проверок, исключённый пользователем.
- Для этой версии local_dir после паузы показывать «файл будет скачан заново». Сохранённый partial нельзя обещать продолжить через этот API. Настоящий Range-resume потребует другого пути/адаптера и проверки сервера; не считать его готовой возможностью hf-hub.
- Для контролируемой остановки предложен отдельный Rust download-worker; in-process Xet cancellation пока не доказана. Worker остаётся частью Rust backend, Python CLI не требуется в production.
- В конфигурации эксперимента отключена неявная авторизация `HF_HUB_DISABLE_IMPLICIT_TOKEN=1`, кеши локальны /tmp. hf-hub иначе читает env/сохранённый токен.

### NVML и sysinfo

`nvml-wrapper = 0.13.0`, `sysinfo = 0.37.2`; точные транзитивные версии в Cargo.lock. Обе NVIDIA карты доступны через NVML: UUID, PCI, имя, память, utilisation, температура, мощность, fan_speed(0), compute processes. sysinfo после второго измерения видит 32 логических CPU, RAM 66651742208 байт, занятую RAM/swap, датчики k10temp Tctl/Tccd1/Tccd2 и другие компоненты. PCI-инвентаризация на момент проверки показывает ровно две GPU (обе NVIDIA).

Нулевые utilisation и fan speed на простаивающей 4070 Ti получены как Ok(0), а не подставлены вместо ошибки. Production всё равно должен хранить доступность каждой метрики отдельно: этот снимок не гарантирует доступность любого сенсора всегда. Частоты CPU/все вентиляторы/потеря драйвера во время работы отдельно не испытывались.

### INI закреплённого llama.cpp

Семь фикстур прочитаны реальным router без загрузки весов:
- Комментарии и CRLF принимаются; исходный файл не меняется. Возвращаемая router нормализованная строка preset уже без комментариев: её нельзя использовать как исходник редактора.
- Повтор ключа: действует последнее значение.
- Повтор секции: более поздняя секция сбрасывает старые значения, а не дополняет их.
- Неизвестный ключ и строка ключа с ведущим отступом: router завершился с ошибкой разбора/валидации.
- port=12345 в пресете молча исключён/заменён router на управляемый порт. Core обязан показать конфликт до применения согласно уже принятому решению.
- Объединённая фикстура с развёрнутыми ctx-size=2048 у a и 4096 у b сохраняет раздельные настройки; общую [*] разных файлов нельзя просто склеить.

Отдельный минимальный Rust writer сохранил комментарий и CRLF побайтно после изменения значения; после внешней правки отверг запись по старой версии, сохранив внешнее содержимое. Это проверка raw-text подхода и обнаружения уже произошедшего конфликта; не доказательство отсутствия всех гонок с внешним редактором. Полный компилятор каталога INI, перечень path-параметров, версия-зависимая валидация и гонки атомарного сохранения ещё требуют реализации и приёмочных проверок.

Предлагается диагностировать повтор секции как ошибку применения, повтор ключа как предупреждение с явным последним значением; исходник сохранять как черновик без нормализации. Это предложение строже поведения upstream и требует решения пользователя.

### Axum SSE через Vite /core/

Реальный Axum, ограниченный Tokio broadcast на четыре события, snapshot + id, keepalive; временный Vite использует proxy `/core/` с удалением префикса. HTTP-клиент получил snapshot и последовательные metric. При переподключении Last-Event-ID=16 дошёл до Axum, новый snapshot имел id=18. Искусственно задержанный потребитель получил gap=14 и новый snapshot; обычный клиент после него получал metric. Данные не блокируют producer: это свойство выбранной ограниченной очереди/обработки Lagged, не автоматическая гарантия SSE.

Граница проверки: медленное чтение из broadcast имитировалось внутри SSE-handler; насыщение сетевого socket buffer/прокси не измерялось. Browser EventSource не использовался, но HTTP-поток и заголовок reconnect прошли реальный Vite proxy. Проверен новый тестовый proxy, не существующий /core/: в приложении такого маршрута пока нет.

Production reverse proxy в репозитории не выбран и не настроен; README только требует его наличия. Поэтому production SSE buffering/timeouts не проверены. Применять результат Vite к неизвестному production proxy нельзя. Существующие потребители не запускались и их настройки не менялись; приёмка через будущий core остаётся в итоговой спецификации.

## Завершение

Все worker, Axum, Vite и router процесса стенда завершены. В /tmp оставлены ~277 MiB Cargo cache, ~2,3 GiB debug target, ~101 MiB модель и небольшие фикстуры. В ветку попадут только скрипты, Cargo.lock и логи; бинарники/кеши/веса исключены.

Задача остаётся claimed: требуются решения о поведении паузы/worker, диагностике INI и границе production proxy. Нет основания называть все будущие Rust-адаптеры production-ready.
