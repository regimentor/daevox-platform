# Локальный сервис llama.cpp на Rust — спецификация первой версии

Статус: утверждена пользователем 2026-09-13. Версия: 1.

Документ определяет требования к последующей реализации. Production-код ещё не написан. Обоснования решений — в [карте](map.md) и её задачах; термины — в [глоссарии](CONTEXT.md). Имена DTO, конкретные HTTP-маршруты и технические детали ниже входят в утверждённый контракт.

## 1. Назначение и границы

Расширяемый backend `apps/core` на Rust управляет llama.cpp на этой машине. Интерфейс — существующий `apps/web-client`. Потребители inference: web-client, Telegram-секретарь, сервис медиа и локальные приложения. В каждый момент допускается не более одного экземпляра обслуживающей модели, в том числе во время замены. Проектор входит в комплект этой модели.

Первая версия: ручной запуск core через Cargo, web-client через Vite dev server. Всё слушает loopback. Не входят: LAN/несколько машин, новый web-client, private/gated Hub и HF-токены, несколько активных моделей, draft-модель, systemd/автозапуск, перенос секретаря или медиа в core, долговременная история метрик, автоматическое управление свободным местом и резерв диска. Production reverse proxy отложен.

Основания: [граница backend](issues/03-runtime-boundary.md), [runtime](issues/04-model-lifecycle.md), [запуск](issues/10-storage-startup.md), [адаптеры](issues/14-adapter-validation.md).

## 2. Состав и владение

| Компонент | Ответственность |
| --- | --- |
| Core, Tokio/Axum | Управление состоянием, допуск и проксирование inference, операции, каталог, настройки, наблюдение |
| Штатный router llama-server | Применение сгенерированного INI, создание и управление дочерним экземпляром |
| Rust download-worker, reqwest | Скачивание выбранных файлов, Range/If-Range, пауза/отмена и прогресс; отдельный процесс, принадлежащий core |
| hf-hub | Поиск публичных репозиториев, metadata и состав файлов |
| SeaORM/SQLite | Каталог, сборки, настройки, операции, ключи повторов; без истории метрик |
| sysinfo / nvml-wrapper | CPU/RAM/процессы/сенсоры и NVIDIA GPU |
| Существующий web-client | Библиотека, редактор INI, запуск пресетов, сборки, логи, система |

Cargo управляет Rust-зависимостями. Monorepo сохраняет npm workspaces; общие dev-зависимости и orchestration принадлежат корню. Первый запуск core: `cargo run --manifest-path apps/core/Cargo.toml --bin core`; production-службы не создаются. Конкретные зависимости фиксируются Cargo.lock, включая версии прототипов либо явно проверенные замены. Проверены hf-hub 1.0.0, reqwest 0.13.5, nvml-wrapper 0.13.0, sysinfo 0.37.2; прототипы содержат точные lockfiles. SeaORM и миграции ещё требуют проверки реализации.

Core — единственная поддерживаемая точка входа. Внутренние порты router и child не публикуются как consumer API. Неограниченный proxy к router management и параметр `autoload` не допускаются. Router запускается с отключённой автозагрузкой и лимитом одной модели; core не полагается на этот лимит вместо собственной последовательности переключения.

## 3. Файлы и сохраняемое состояние

Утверждённая структура реализации:

```text
apps/core/
  Cargo.toml, Cargo.lock
  vendor/llama.cpp/              # Git submodule, версия закреплена репозиторием
  presets/*.ini                 # исходники, Git tracked
  data/                         # целиком Git ignored
    core.sqlite
    backups/
    models/                     # завершённые файлы комплектов
    downloads/<operation-id>/   # partial и идентичности загрузок
    builds/<build-id>/
    generated/                  # применяемые версии общего INI
    logs/
    runtime/                    # lock, идентичности собственных процессов
```

Все пути разрешаются от каталога приложения, а не от случайного CWD. Веса, partial, кеши, БД, логи, сборки и генерируемые INI не попадают в Git. Полная дополнительная копия весов в глобальном HF-кеше не создаётся. Подписи временных CDN URL и секреты не включаются в metadata/логи; хранится исходный URL фиксированного Hub commit.

Таблицы SeaORM: `model_sets`, `model_files`, связи комплектов/файлов, `builds`, `settings`, `operations`, `request_keys`; при необходимости индексы пресетов, но исходным текстом владеют INI-файлы. Общие файлы учитываются явно: удаление комплекта/отмена загрузки не удаляет файл, на который ссылается другой комплект. Запись каталога не доказывает существование файла — при старте и действиях проверяется фактическое состояние.

Блокировка единственного core на директорию берётся до миграций и запуска процессов. Миграции SeaORM выполняются автоматически с согласованной резервной копией SQLite, включая WAL. Ошибка миграции прекращает запуск с диагностикой; удаления/сброса БД нет.

Срок истории завершённых операций и request keys — 7 дней; незавершённые остаются до разрешения. Текущая и предыдущая рабочие сборки сохраняются; прочие удаляются только вручную. Используемую сборку удалить нельзя.

## 4. Модели и скачивание

Путь пользователя: поиск Hub → репозиторий → GGUF-квантование → точный комплект файлов/общий размер → скачать. Поддерживаются одиночный GGUF, shards и подходящий проектор. При неоднозначном проекторе требуется выбор пользователя. Скачивание фиксирует commit; обновления upstream не меняют существующие комплекты и пресеты.

Идентичность комплекта: repository + commit + выбранный набор путей файлов. Повтор уже скачанного комплекта возвращает существующий; новая revision — отдельный комплект. У каждого файла собственная идентичность и смещение; итоговый прогресс суммирует фактически записанные байты без повторного счёта сохранённого префикса. Если размер неизвестен, процент/ETA отсутствуют, показывается объём.

Один комплект скачивается, другие стоят в очереди. Генерация и ручная фоновая сборка не запрещают скачивание. Пауза освобождает worker и сохраняет partial; paused-комплект не мешает следующему queued. Resume возвращает его в конец очереди. Внутреннее число соединений не является обещанием API.

Переходы: `queued → running → completed`; `running → pausing → paused`; `queued|paused|running → cancelling → cancelled`; ошибка — `failed` с причиной. Терминальное состояние паузы/отмены публикуется только после прекращения записей worker. После рестарта все незавершённые скачивания paused, не запускаются автоматически.

При resume worker заново получает metadata исходного pinned URL, сверяет identity/размер/ETag и запрашивает Range от длины partial с If-Range. Дописывание допускается только при корректном 206/Content-Range и той же идентичности. 200 вместо 206, несовпадение ETag, непригодный валидатор, неверный диапазон или 416 не разрешают молчаливое дописывание/удаление partial. UI показывает причину и отдельное действие «Скачать файл заново». Явный restart очищает только соответствующий принадлежащий операции partial; общие завершённые файлы сохраняются.

Результат download-worker, а не одно событие Complete или наличие .gguf, определяет завершение. Незавершённые файлы остаются в downloads; успешные публикуются в models с согласованным обновлением metadata. Это защита от объявления partial готовым, а не отдельный отложенный сценарий integrity/резерва диска. Ошибки файловой системы отображаются по общим правилам.

Удаление комплекта — вручную, после предварительного показа связанных пресетов. Активный комплект сначала выгружается явным действием. Пресеты сохраняются с отметкой missing files; общие файлы других комплектов не удаляются.

Основания: [каталог](issues/06-model-catalog.md), [проверенная докачка](validation/resume-results.md).

## 5. Пресеты и конфигурация

Фиксированный каталог `apps/core/presets/`, один исходный INI на модель, несколько секций-пресетов. Пользователь не выбирает произвольную директорию. Редактор получает исходный текст и opaque revision; сохраняет комментарии, переносы строк и оформление. Чтение нормализованного preset из router не заменяет исходник.

Общая `[*]` действует только внутри своего исходного файла. Core компилирует её значения в конкретные секции общего generated INI. Имена пресетов уникальны в каталоге. Относительные пути к известным файловым параметрам разрешаются от директории исходного INI и генерируются абсолютными. Произвольные строковые значения не преобразуются в пути; список файловых аргументов и aliases привязан к pinned llama.cpp и проверяется фикстурами.

Повтор секции/конфликт имени — ошибка применения. Повтор ключа — предупреждение с явным итоговым последним значением. Неизвестные параметры и попытка задать контролируемые core/router host, port, autoload, лимит моделей и подобные настройки — ошибка применения с диагностикой; молчаливого удаления ключа нет. Алиасы проверяются по семантическому параметру. Неподдерживаемый синтаксис показывается как ошибка с привязкой к строке, когда она определима.

Некорректный текст сохраняется как черновик, запуск запрещается. Save с устаревшей revision возвращает конфликт, в том числе после внешнего изменения. Действия: перечитать либо явно заменить своей версией. Генерация INI не переписывает исходники.

Изменение/удаление исходника не вызывает автоматический reload или остановку работающей модели. Хранятся отдельно текущий текст, saved revision и immutable applied revision экземпляра. Применение сохранённых изменений — перезапуск пресета через action bar по обычному переключению. Запуск операции захватывает конкретную версию: последующая правка не меняет уже принятую цель. Если клиент запускает устаревшую выбранную revision, он получает конфликт и актуальные данные.

## 6. Runtime и переключение

Состояния runtime: `empty`, `ready`, `waiting`, `unloading`, `loading`, `error`, `recovery_required`. Отдельные поля: выбранный последний пресет, готовый active instance, target операции, applied preset revision, build id. При unloading старый PID может существовать, но допуск запросов закрыт. После запуска core модели автоматически не загружаются.

Обычная загрузка/замена:

1. Атомарно проверить отсутствие другой runtime-операции, сохранить request key/операцию и закрыть допуск новых inference-запросов.
2. Если есть выполняющиеся запросы, ждать их завершения (включая streaming body). По умолчанию 300 с, положительное целое значение настраивается в UI. Это предел drain, не таймаут генерации/загрузки.
3. При истечении drain отменить переключение, открыть допуск старому готовому экземпляру. Результат операции содержит `drain_timeout`.
4. После drain отправить unload. HTTP success означает только принятие команды. Подтвердить завершение собственного старого экземпляра по идентичности процесса и состоянию router; при доступности NVML сверить исчезновение allocations его PID. Не ждать точного возврата общей VRAM к исходному числу.
5. Только после подтверждения остановки загрузить target с захваченными preset revision/build. Открыть допуск после подтверждения loaded/readiness внутреннего экземпляра. Если target=null, закончить empty.

Другие команды замены во время операции получают conflict, без очереди. Force ускоряет текущую waiting-операцию: прерывает её выполняющиеся запросы, затем выполняет тот же unload/подтверждение/загрузку. Force не разрешает два экземпляра.

Cancel во время waiting возвращает старую модель в ready. После начала unloading возврата нет: завершить остановку и остаться empty. Во время loading отмена прекращает запуск и подтверждает остановку прежде, чем перейти в empty. Ошибка нового экземпляра оставляет сервис без активной модели; нет автоперезапуска, изменения параметров, CPU fallback или автоматического возврата к старой модели.

После падения router — ошибка, без автоматического перезапуска модели. После падения core router и модель могут выжить. Новый core сверяет запись процесса (boot id, PID/start time, executable и дополнительные признаки собственного запуска), показывает recovery_required и действия завершения только доказанно своих процессов. Неопределённость принадлежности не разрешает kill. Дескриптор процесса/эквивалент должен исключать гонку переиспользования PID. До разрешения ситуации новый router/экземпляр не запускается.

Штатный shutdown прекращает допуск запросов, завершает собственные сборки/download-workers/router/model и фиксирует прерванные операции. Чужие процессы не останавливаются. Дерево child отслеживается по всем потокам родителя либо эквивалентным надёжным механизмом; children только главного потока недостаточно.

Основания: [жизненный цикл](issues/04-model-lifecycle.md), [проверка на машине](validation/runtime-results.md).

## 7. Сборка llama.cpp

Версия — commit submodule, изменяемый разработчиком через репозиторий. Core не обновляет upstream и не переключает submodule из UI. Подтверждённая тестовая база — `82d6bb284d1ff1c6ef37f29a4c3b63d1a8b11806`; утверждённый первый продуктовый pin совпадает с этой проверенной базой; смена commit проходит те же проверки.

Основной профиль — CUDA для обеих NVIDIA GPU и CPU; CPU-only выбирается явно. GPU сопоставляются по UUID/PCI, CUDA-index — атрибут текущего обнаружения. Fingerprint сборки включает commit, профиль, CPU/GPU architectures, действительные toolchain/compiler versions и параметры. Изменение драйвера запускает проверку совместимости, не безусловную пересборку.

Если подходящего артефакта нет, core готовит сборку автоматически; при загруженной модели автоматическая сборка отложена. Ручная фоновая сборка допускается. Одновременно одна сборка, по умолчанию 8 compiler jobs; настройка — положительное целое. Никаких системных установок, постоянного root и скрытого обхода несовместимости компилятора.

Новый артефакт строится в отдельной директории. Результат: успешная конфигурация/компиляция, запуск/health пустого router, перечень backend/devices, диагностика. Если inference не проверялся, UI явно показывает это; probe с весами не нарушает ручной запуск и единственный экземпляр.

Логи configure/build доступны в реальном времени. Cancel завершает собственное дерево сборки, сохраняет логи. Retry и clean rebuild запускаются вручную. Build success не применяет артефакт. Apply/rollback — отдельные runtime-операции с drain и заменой router; после них empty, загрузка вручную. Ошибка применения сохраняет предыдущий артефакт, автоматического rollback нет.

## 8. Наблюдение

Сессия от старта до остановки core имеет `session_id`. Каждую секунду независимо от браузера собираются CPU total/per-logical-core usage и частоты, доступные температуры, RAM/swap; все GPU — UUID/PCI/name/utilisation/VRAM/temp/power/fans; собственные процессы — CPU/RAM и GPU allocation при поддержке. Каждое измерение содержит время и признак доступности. Сбой collector не прекращает inference; отображаются last_success и разрыв графика, не подставленный ноль.

В памяти — последние 60 минут графиков, счётчики — вся текущая сессия. Переключение модели/закрытие браузера не сбрасывает сессию. Перезапуск core сбрасывает метрики и счётчики; SQLite/файлы не используются для истории метрик.

Inference-измерения связаны с request id, preset id, applied revision и build id. Счётчик in-flight действует до завершения upstream body/обработки, не до отправки заголовков. Успех, ошибка и отмена различаются. TTFT для streaming — от принятия core до первого содержательного токена/фрагмента ответа; role-only/служебный chunk не считается. Для nonstream TTFT неизвестен, отдельно доступно полное время ответа. Скорость генерации вычисляется только по реальным token/timing данным llama-server; количество символов не заменяет число токенов. Недоступные значения — null. Header показывает измеренную TPS текущего экземпляра с указанием источника/времени в раскрытии; устаревшая/отсутствующая скорость не выдаётся за текущую.

Логи core/router/model/build имеют source, timestamp, доступный level, instance/build/operation id. stdout и stderr читаются независимо, порядок внутри каждого потока сохраняется; общий порядок разных потоков не обещается. Чтение pipe и запись/доставка не должны блокировать процесс из-за медленного браузера. Очереди ограничены; потери сообщаются явно. Длинные строки ограничиваются/разбиваются с признаком truncation; неограниченного буфера строки нет.

Файлы в data/logs переживают перезапуск, общий предел 200 MiB для всех источников; старые сегменты удаляются первыми, включая ротацию текущего сегмента. UI: live, остановка автопрокрутки, фильтры, поиск и скачивание доступного лога. Удалённый ротацией фрагмент обозначается unavailable/gap. Пропуски SSE не означают остановки записи доступных файлов логов.

## 9. HTTP-контракт

### Адреса и общие правила

Core слушает `127.0.0.1:<configured-port>`; занятый порт — диагностическая ошибка, не завершение другого процесса. Конкретное свободное значение выбирается конфигурацией запуска. Vite proxy `/core/` снимает этот префикс: `/core/runtime` → core `/runtime`; `/core/v1/chat/completions` → `/v1/chat/completions`. Локальные приложения используют прямой `/v1`. Origin для браузерных команд ограничен фактическим origin web-client. Для доверенных локальных клиентов без Origin ключи не требуются; произвольный CORS не открывается. Это не аутентификация локальных процессов.

JSON — UTF-8; времена — UTC RFC3339, длительности — миллисекунды, размеры — байты, частоты — MHz, мощность — watts. Значение отсутствует как null с причиной, не 0. Идентификаторы непрозрачные строки; `preset_id` совпадает с конкретным именем секции. Пути файлов выбираются из каталогов core, а не принимаются как произвольные пути хоста.

Все запускающие/изменяющие состояние команды содержат `Idempotency-Key`. Core атомарно сохраняет ключ вместе с операцией/результатом. Повтор того же действия с тем же телом возвращает сохранённый результат; другое действие/тело с тем же ключом — 409. Срок защиты — 7 дней после завершения. Idempotency inference-запросов не предоставляется: генерация не переигрывается core автоматически.

Длительные команды — HTTP 202 `{operation_id}`; чтение — 200; синхронное создание — 201; удаление — 204 либо 202 при необходимости фоновой очистки, конкретно по таблице. В management errors: `{error:{code,message,retryable,details},request_id}`. Ошибка сохраняет понятную причину, но не секреты и не произвольный dump окружения.

### Основные DTO

- `RuntimeSnapshot`: `session_id`, `state`, `active_instance|null`, `target|null`, `current_operation_id|null`, `current_build_id|null`, `last_selected_preset_id|null`, `inflight_requests`, `recovery[]`, `revision`.
- `Instance`: `id`, `model_set_id`, `preset_id`, `applied_preset_revision`, `build_id`, `started_at`, `ready_at|null`, `status`. PID не служит публичной идентичностью экземпляра.
- `ModelSet`: `id`, `repo_id`, `commit`, `files[]`, `availability:downloading|available|missing|failed`, `download_operation_id|null`, `preset_ids[]`. `File`: `id`, `path`, `role:weights|shard|projector`, `size_bytes|null`, `downloaded_bytes`, `availability`.
- `Preset`: `id`, `source_file_id`, `model_set_id|null`, `saved_revision`, `applied_revision|null`, `can_launch`, `diagnostics[]`. `Diagnostic`: `severity:error|warning`, `code`, `message`, `line|null`, `key|null`.
- `Operation`: `id`, `type`, `status:queued|running|paused|succeeded|failed|cancelled|interrupted`, `phase`, `resource_id|null`, `created_at`, `updated_at`, `progress|null`, `error|null`, `allowed_actions[]`. Для download completed UI соответствует succeeded операции. Runtime/error хранится отдельно от failed операции.
- `Progress`: `bytes_done|null`, `bytes_total|null`, `bytes_per_second|null`, `percent|null`, `file_id|null`. Стандартного процента загрузки модели/сборки нет: если upstream не даёт надёжную долю, показывается этап и журнал.
- `MetricValue`: `value|null`, `unit`, `availability:available|unsupported|error`, `sampled_at`, `last_success_at|null`, `reason|null`. GPU id = UUID с PCI для сопоставления; numeric index вспомогательный.

OpenAPI и генерируемый TS-клиент должны покрывать все поля/enum/ошибки. UI не дублирует вручную расходящиеся типы. Прототипы не являются опубликованным API.

### Inference

Обязательны `GET /v1/models` и `POST /v1/chat/completions`; стандартные поля OpenAI response, streaming SSE, response_format json_schema и chat_template_kwargs передаются без потерь. `/v1/models` содержит только готовый активный пресет; при empty/recovery/switching возвращает пустой список. Обязательное поле `model` — конкретный preset id, без alias active и автозагрузки.

До начала ответа: отсутствие активной модели → 503 `no_active_model`; запрос другого пресета → 409 `preset_not_active`; закрытый допуск переключения → 503 `model_switching`; недоступный upstream → 502 `inference_upstream_error`. Формат `{error:{message,type,code,param}}` совместим с OpenAI SDK. Для незнакомого model и закрытого допуска первична фактическая причина недоступности runtime. Core не возвращает 200 с успешным пустым completion при ошибке.

После начала streaming нельзя сменить HTTP-статус. Ошибка отображается в допустимом error event либо обрывом; нормальный terminal marker не создаётся при аварии. Разрыв клиента передаёт отмену upstream; автоматического повтора генерации нет. Разрешённые пути/поля не должны позволять вызвать router autoload или management через query/body.

## 10. SSE и восстановление web-client

Event envelope: `{session_id,seq,type,timestamp,payload}`; SSE `id` кодирует session_id и возрастающий seq, `event` — type. Типы: `snapshot`, `runtime.changed`, `operation.changed`, `catalog.changed`, `preset.changed`, `build.changed`, `metric.sample`, `log.append`, `gap`.

Соединение подписывается и получает согласованный snapshot с границей seq без потери событий между снимком и подпиской. Snapshot содержит runtime, настройки, актуальные операции и ревизии каталогов; тяжёлые каталоги, графики и логи клиент запрашивает соответствующими GET. Клиент игнорирует события старой сессии/повторные seq.

При reconnect клиент передаёт Last-Event-ID, сервер возвращает актуальный snapshot. Непрерывный replay всей истории не обещается. При недоступном диапазоне, смене session или отставании consumer выдаются gap и новый snapshot. Пропущенные метрики могут быть добраны только из доступных 60 минут текущей сессии, логи — из сохранённых сегментов. За пределами доступного диапазона UI показывает пропуск.

Очереди потребителей ограничены, lag не тормозит producer. Нужны keepalive и прекращение ресурсоёмкой работы на закрытом соединении. Потеря SSE не останавливает runtime/сборку/скачивание. Vite proxy сохраняет streaming/Last-Event-ID; production buffering/timeout не входят в первую версию.

## 11. Интерфейс

Источник утверждённого дизайна: `codex/prototype-llama-core`, commit `037b83d`; вариант A. Прототип содержит демонстрационные данные и требует реализации по этому контракту.

- Header «Модели LLM» — только локальная библиотека и поиск/скачивание HF.
- Постоянный action bar в стиле macOS — активный пресет, доступная TPS, раскрытие с выбором/запуском/сменой/перезапуском пресета и переходом в управление.
- Отдельный download action bar — имя комплекта, справа круг с процентом внутри. Высота и отступы совпадают с runtime action bar. На паузе остаётся; по завершении/отмене исчезает. Раскрытие: прогресс, скорость, объём, пауза/продолжение/отмена и библиотека; необходимость restart отображается явно.
- Управление: обзор активной модели и этой машины, вкладки «Пресеты», «Система», «Сборки», «Логи». Карточки «Выбранный пресет» нет.
- В «Пресетах» — только редактирование, диагностика и сохранение. Запуск/применение — из action bar. Устаревший пресет, отсутствующие файлы и конфликт редактора видимы.
- «Сборки»: текущая/предыдущая/кандидат, параметры и результаты проверок, live stdout/stderr прямо во время сборки, cancel/retry/clean/apply/rollback.
- «Система»: все GPU, CPU и RAM, графики текущей сессии, недоступные сенсоры без выдуманных значений.
- У runtime-операции видны waiting/unloading/loading, цель, текущие запросы, доступные cancel/force. UI следует allowed_actions, но backend повторно проверяет разрешённость.

Prototype URL `/prototype/core` не определяет будущий продуктовый URL страницы. API-префикс `/core/` остаётся фиксированным; маршруты страниц вписываются в существующий React Router.

## 12. Подключение существующих потребителей

Настройки подключения меняются при реализации, не в рамках этой карты:

| Потребитель | Конфигурация и контракт |
| --- | --- |
| Секретарь / автоответчик | `LLAMA_BASE_URL` → loopback core `/v1`, `LLAMA_MODEL` → конкретный пресет; текущие OpenAI SDK timeout 180 с, maxRetries 0, AbortSignal |
| Медиа | `TRANSCRIPTION_LLM_BASE_URL` → core `/v1`, `TRANSCRIPTION_LLM_MODEL` → непустой конкретный пресет; текущие nonstream Chat Completions, strict json_schema, timeout 300 с |

Backend умеет выбрать первый `/models` при отсутствии LLAMA_MODEL; core возвращает не более одного готового пресета. Discovery и последующий POST не атомарны: model повторно проверяется на каждом запросе, ошибка не вызывает переключение. Медиа не выполняет discovery; пустая модель не подменяется автоматически.

Оба существующих потребителя сейчас используют nonstream LLM-запросы. Streaming отдельно проверяется локальным клиентом. `chat_template_kwargs.enable_thinking=false`, JSON schema и стандартные поля ответа должны сохраняться. Собственная очередь/планировщик секретаря не управляет моделью core и не заменяет его in-flight counter.

Drain защищает отдельный принятый запрос, а не всю многошаговую задачу перевода/дневной сводки. Между её запросами пользователь может сменить пресет; следующий запрос старого ID отклоняется. Существующий retry отдельных фраз у клиента не является retry core. Приёмка должна проверить, что эти ошибки понятны пользователю и не приводят к скрытой смене модели.

Проверенные по коду места: `apps/backend/src/domain/secretary/summarizer.ts`, `daily-summary.ts`, `summary-queue.ts`, `apps/backend/src/domain/auto-reply/content.ts`, `apps/transcription-backend/src/transcription/config.py`, `voice_worker.py`. Реальные env, end-to-end запросы этих приложений и их JSON schemas в прототипах не проверялись.
