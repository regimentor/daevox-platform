## Question

Как фиксируется и обновляется submodule, выбираются backend и GPU-архитектуры, проверяется совместимость драйвера/toolchain, определяется необходимость пересборки? Где граница между автоматической сборкой и установкой SDK/драйверов? Как ограничиваются ресурсы сборки, сохраняется предыдущая рабочая версия и выполняется проверка перед активацией? Определить отмену, повтор, ошибку и откат сборки без выполнения этих операций сейчас.

## Answer

1. **Версия исходников.** Core собирает commit llama.cpp, закреплённый Git submodule в репозитории. Версию обновляет разработчик через репозиторий; core не выбирает новую upstream-версию и не меняет submodule самостоятельно через UI. Commit, использованный в исследовании, не назначается версией продукта этим решением.
2. **Аппаратный профиль.** Основной профиль — CUDA с поддержкой обеих NVIDIA GPU этой машины и CPU. Core определяет оборудование и toolchain, подбирает параметры сборки и показывает их в интерфейсе. Точные GPU-архитектуры и совместимость установленного toolchain подтверждаются runtime-прототипом. Поддержка обеих карт сборкой не означает обязательное использование обеих каждым пресетом. CPU-only выбирается пользователем явно; при ошибке CUDA скрытого fallback нет.
3. **Системные изменения.** Core автоматически настраивает и выполняет сборку установленными инструментами. При нехватке или несовместимости компилятора, SDK или драйвера показывает диагностику и необходимые действия. Системные пакеты, SDK и драйверы устанавливает пользователь; core не обновляет ОС и не требует постоянных root-прав.
4. **Триггер сборки.** Если отсутствует подходящая сборка для текущего commit, выбранного профиля, CPU/GPU и toolchain, core автоматически готовит её. Изменение драйвера запускает проверку совместимости; пересборка требуется только при выявленной необходимости, а не при любой смене номера версии. Автоподготовка сборки не означает её автоматическое применение.
5. **Ресурсы.** Одновременно выполняется одна сборка. По умолчанию — 8 параллельных заданий компилятора; настройка доступна в интерфейсе. Автоматическая сборка откладывается, пока модель загружена. Пользователь может явно запустить фоновую сборку при загруженной модели, учитывая возможное замедление генерации. Это ограничение параллелизма, не обещание жёсткого лимита RAM или CPU.
6. **Изоляция артефактов.** Новая сборка выполняется в отдельной директории и не заменяет работающие файлы текущей версии. Текущая рабочая сборка сохраняется. Предварительные проверки и успешное завершение сборки необходимы для доступности действия применения; незавершённый результат применить нельзя.
7. **Отмена и повтор.** Отмена завершает процессы сборки, сохраняя логи. Ошибка сборки не затрагивает рабочую версию. Повтор запускается пользователем: доступны обычный повтор и чистая пересборка. Автоматический бесконечный повтор не вводится. Подробности очистки временных файлов принадлежат задаче хранения.
8. **Явное применение.** Пользователь отдельно выбирает «Применить сборку». Core останавливает обслуживание и заменяет router по [принятым правилам жизненного цикла](04-model-lifecycle.md): ожидание текущих запросов с настраиваемым пределом и возможность принудительного действия. После применения модель загружается пользователем через web-client, без автозагрузки. Предыдущая сборка сохраняется для ручного отката.
9. **Ошибка применения.** Если новый router не запускается или не проходит проверку готовности, показывается ошибка. Предыдущая сборка доступна через «Откатить»; автоматического отката и автоматической загрузки модели нет. Ошибка переключения сборки не должна уничтожать предыдущий пригодный артефакт.
10. **Уровень проверки.** Если локальных весов нет, допускаются предварительные проверки сборки и router; UI явно сообщает, что генерация на этой сборке ещё не проверена. Успешный compile или запуск router не выдаётся за проверенный inference. Проверки с весами должны соблюдать ограничение одной активной модели и явного управления её загрузкой.

Точные проверки совместимости и готовности router без активной модели устанавливаются в [проверке runtime и сборки](13-runtime-validation.md); размещение артефактов и очистка — в [хранении состояния и запуске сервиса](10-storage-startup.md). Эти задачи уточняют механизм исполнения принятой политики. Реальных сборок, установок и изменений submodule в этой сессии не выполнялось.
