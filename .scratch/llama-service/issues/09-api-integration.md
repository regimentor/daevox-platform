## Question

Как существующий веб-клиент обращается к Rust-backend и сохраняется локальная граница доступа? Каковы контракт команд, идентификаторы операций, ошибки, повторы и поток событий? Где inference endpoint и как стабильно обозначаются модель/пресет для секретаря, медиа и локальных приложений? Какие существующие настройки или scheduler-предположения нужно согласовать, чтобы не получить двух владельцев переключения? Нужны ли ключи доступа и разделение management/inference? Выбрать способ синхронизации TypeScript-контракта, обратную совместимость и поведение после разрыва соединения.

## Constraints

Соблюдать принятое решение [Одна активная модель: переключение, запросы и восстановление](04-model-lifecycle.md). Уточнять контракт и проверять механизм исполнения; не вводить автозагрузку, очередь новых запросов или автоматический возврат как несогласованные значения по умолчанию.

Соблюдать [решение о каталоге INI](07-preset-directory.md): фиксированный путь, lossless исходный текст, область [*] в пределах файла, разрешение путей от исходного INI, явное применение и конфликты внешнего редактирования. Проверить отображение ошибок контролируемых router параметров и отсутствие побочной выгрузки при обновлении исходников.

Соблюдать [решение о наблюдении](08-observability.md): метрики только в памяти сессии core, логи отдельно на диске. Уточнить механизм сбора, повторного подключения и ротации без добавления долговременной истории метрик.

## Comments

Первый раунд: «1 достаточно /core/; 2 ок; 3 ок, конкретный пресет; 4 да».
Второй раунд: «1 да; 2 ок; 3 ок; 4 ок» на предложения о локальном доступе, операциях/повторах, ошибках/отмене генерации и условном сохранении INI.

## Answer

1. **Адреса и интеграция.** Существующий web-client обращается к core через маршрут /core/ своего proxy. Core слушает только 127.0.0.1. Секретарь, сервис медиа и локальные inference-приложения обращаются к core напрямую. Для первой версии настраивается Vite dev proxy; позднейшим принятым уточнением production proxy отложен. Конкретный порт и внутреннее преобразование proxy-пути относятся к конфигурации запуска; внешний префикс web-client — /core/, не /core-api/.
2. **Inference.** Локальный вход /v1 совместим с потребителями: список моделей и chat completions, streaming и json_schema. Core передаёт запросы внутреннему llama-server. Management сборок, файлов и переключения — отдельный API для web-client; произвольный проброс router management и обход политики core не допускаются.
3. **Выбор пресета.** Поле model содержит имя конкретного пресета. /v1/models возвращает только активный, готовый к генерации пресет; полный каталог доступен management API. Запрос иного пресета получает ошибку, не автозагрузку и не подмену текущей моделью. Стабильный alias active не используется. Настройки существующих потребителей должны отражать выбранный пресет; их переключением по-прежнему управляет пользователь через web-client. Точные изменения существующего fallback выбора первой модели проверяются интеграционным прототипом в рамках этого контракта.
4. **Контракт и доставка.** Команды идут по HTTP; состояния операций, метрики и логи — через SSE. При открытии страницы клиент получает снимок состояния, затем изменения. После разрыва восстанавливает актуальное состояние; недоступные фрагменты логов показываются как пропуск. Обязательность снимка не подразумевает долговременную историю метрик: действуют границы сессии из решения о наблюдении. OpenAPI описывает контракт, TypeScript-клиент генерируется для web-client. Схемы SSE также должны быть согласованы с клиентом; сам факт OpenAPI не гарантирует описания семантики событий.
5. **Локальный доступ.** Отдельный вход и API-ключи в этой версии не вводятся. Управление предназначено web-client через proxy. Для браузерных команд проверяется допустимый источник запроса; произвольным сайтам доступ не открывается. Loopback и проверка browser origin не являются аутентификацией локальных процессов: это локальная доверенная среда, а не обещание изоляции приложений одного пользователя. Прокси не должен создавать непредусмотренную внешнюю границу доступа.
6. **Операции.** Скачивание, сборка и переключение сразу возвращают идентификатор операции, прогресс поступает через SSE; есть отдельное получение её состояния. Повтор команды с тем же идентификатором запроса возвращает существующую операцию, не запускает вторую. Конфликтующие команды получают ошибку без скрытой очереди, кроме принятой очереди скачиваний. Принятые исключения для ускорения текущего переключения и его отмены сохраняются. Срок хранения идентификаторов и восстановление операций после рестарта определяются в задаче хранения.
7. **Ошибки и отмена.** Различаются отсутствие активной модели, запрос другого пресета, переключение, конфликт операции и ошибка llama-server. При отключении inference-клиента core передаёт отмену дальше. Уже начатый streaming автоматически не перезапускается: клиент получает ошибку потока или обрыв. При завершении соединения core не должен считать модель освободившейся до подтверждения фактического окончания обработки; конкретный механизм проверяется runtime-прототипом. Форматы HTTP-ошибок должны быть совместимы с используемыми inference-клиентами.
8. **Условное сохранение INI.** Редактор получает текст и версию файла; сохранение включает исходную версию. Если она устарела, core возвращает конфликт. Принудительная перезапись — отдельное явное действие пользователя. Некорректный INI можно сохранить как черновик, но применение отклоняется. Конфликтная проверка относится и к внешним изменениям, не только к параллельным вкладкам UI.

Точные DTO, статусы HTTP и endpoint-таблица оформляются в итоговой спецификации согласно этой политике; технические неоднозначности, меняющие поведение, возвращаются в решения, а не закрываются неявными допущениями. Продолжение: [хранение и запуск](10-storage-startup.md), [UI](11-ui-workflow.md), [runtime-проверка](13-runtime-validation.md), [проверка адаптеров](14-adapter-validation.md). Реальные маршруты, конфигурации потребителей и код приложения пока не изменялись.

Уточнение после проверки адаптеров, принято пользователем: первая версия запускает web-client через Vite dev server с proxy /core/. Production reverse proxy пока не выбирается; результат проверки Vite не распространяется на production.
