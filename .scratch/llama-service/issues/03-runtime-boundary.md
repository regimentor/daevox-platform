## Question

Используем штатный router llama-server или собственное управление одиночным экземпляром? Кто владеет процессами, портами, проверкой готовности и маршрутизацией inference-запросов? Какие Rust runtime, HTTP и аппаратные адаптеры выбираем, где workspace и граница с существующими backend? Определить границы ответственности и причины выбора по исследованиям, не превращая эту задачу в реализацию.

## Answer

1. **Владелец выполнения.** Используем штатный router llama-server под управлением Rust-сервиса. Rust запускает и наблюдает router, управляет сборками llama.cpp, каталогом моделей и пресетами, отправляет команды загрузки/выгрузки и проверяет фактическое завершение операций. Router владеет дочерним экземпляром модели, применяет нативные INI-пресеты и направляет запросы экземпляру. Собственный параллельный supervisor дочерних экземпляров не вводится.
2. **Единый вход.** Веб-клиент и локальные приложения обращаются к Rust-backend для управления и inference. llama-server — внутренний исполнитель; прямое обращение потребителей к нему не является поддерживаемым путём интеграции. Rust учитывает активные запросы и контролирует допуск новых. Streaming, отмена, таймауты, ошибки и завершение запросов должны сохраняться на границе proxy; подробный контракт определяется в [API сервиса и подключении локальных потребителей Daevox](09-api-integration.md).
3. **Одна активная модель.** Принято исходное ограничение одной активной модели. Семантика перехода, поведение запросов, автозагрузка и вспомогательные веса остаются в [Одной активной модели: переключении, запросах и восстановлении](04-model-lifecycle.md). Ответ unload не считается доказательством остановки процесса или освобождения VRAM. Нельзя обходить политику Rust через неограниченный проброс management API или параметров autoload; допустимый контракт уточняется в задаче API.
4. **Состав backend.** Tokio для асинхронного выполнения и процессов; Axum для HTTP; sysinfo для CPU, RAM и процессов; nvml-wrapper для NVIDIA GPU. Доступность конкретных аппаратных показателей проверяется на хосте; отсутствие показателя не превращается в ноль. Версии фиксируются при подготовке прототипов/реализации, текущая рекомендация latest не является pin.
5. **Размещение и расширение.** Rust-backend размещается в apps/core и работает отдельным процессом. Это расширяемый backend; управление llama.cpp — его первая область ответственности в этой карте. Предложенное имя apps/llama-backend отклонено в пользу apps/core. Cargo управляет Rust-зависимостями; общая организация monorepo следует npm workspaces. Позднейшее уточнение пользовательского способа запуска находится в [решении о хранении и запуске](10-storage-startup.md). Каталог приложения пока не создаётся: текущая работа — спецификация.
6. **Граница с платформой.** Интерфейс добавляется в существующий apps/web-client. Core предоставляет собственную границу сервиса; существующие backend секретаря и медиа становятся его inference-потребителями по будущему контракту интеграции. Возможность расширения core не означает принятое решение о переносе в него существующих backend, framework или их данных. Такие переносы потребуют отдельного запроса и решений.
7. **Основание выбора.** Router сохраняет применение родного INI-формата и upstream-владение экземпляром; единый Rust-вход даёт место для учёта запросов и политики переключения. Цена решения — streaming proxy и согласование состояния с router. По [исследованию runtime](01-runtime-research.md), unload асинхронен и graceful drain не подтверждён; выбранная архитектура должна пройти [проверку runtime и сборки](13-runtime-validation.md).

Хранилище, загрузчик Hugging Face, правила редактирования INI, транспорт наблюдений и запуск сервиса остаются открытыми в своих задачах. Это решение закрывает границу runtime и базовый состав backend, не всю спецификацию.
