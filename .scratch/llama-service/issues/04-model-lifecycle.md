# Одна активная модель: переключение, запросы и восстановление

## Question

Что означает одна активная модель: запрет одновременного резидентного размещения при замене или только одновременного обслуживания? Как учитывать mmproj и возможную draft-модель? Нужна ли автозагрузка по API или только ручные команды? Что делать с текущими и новыми запросами при замене, отмене, OOM и падении? Как выбирается модель и что происходит при конкурирующих командах? Нужен ли автоматический возврат к предыдущей модели, автозапуск после перезапуска? Определить состояния, идентичности, владение и критерии готовности. Учитывать конкуренцию за GPU с сервисом медиа и сторонними процессами без предположения об эксклюзивном владении GPU.

## Comments

Второй раунд: пользователь ответил «1 ок; 2 ок; 3 ок; 4 ок» на предложения о запуске без активной модели, сериализации команд, отмене по фазам и настраиваемом ожидании 300 секунд.

## Answer

1. **Одна активная модель.** Замена последовательная: завершение работы старой модели → выгрузка → подтверждение остановки → загрузка новой. Старый и новый обслуживающие экземпляры не работают одновременно. Проектор входит в комплект модели; отдельная draft-модель для speculative decoding исключена из текущей версии.
2. **Инициатор.** Пользователь управляет загрузкой, выгрузкой и заменой через существующий web-client. Core предоставляет необходимые интерфейсу операции. Обычные inference-запросы не загружают и не переключают модель; запрос неактивной модели получает понятную ошибку. Самостоятельные management-клиенты не входят в принятый сценарий. Все потребители генерации используют единый вход core.
3. **Обычное переключение.** Core прекращает допуск новых запросов и ждёт завершения уже выполняющихся. Новые запросы получают временную ошибку «модель переключается» с возможностью повтора; очередь на период переключения не вводится. Уже начатые streaming-запросы учитываются до завершения, а не только до отправки заголовков. Если ожидание истекло, переключение отменяется и старая модель продолжает обслуживать запросы.
4. **Предел ожидания.** По умолчанию 300 секунд; пользователь может настроить его через интерфейс. Это предел ожидания текущих запросов, а не общий таймаут загрузки модели или генерации. Ограничения значения и хранение настройки уточняются в контракте API/хранилища.
5. **Принудительное переключение.** Отдельная команда прерывает текущие запросы и продолжает замену без ожидания указанного предела. Принудительный режим не разрешает перекрытие экземпляров или запуск новой модели до подтверждения остановки старой. Доказательство завершения остановки — предмет runtime-прототипа; одного success ответа unload недостаточно.
6. **Конкурирующие команды.** Одновременно выполняется одна операция переключения. Другое переключение в это время недоступно. Повтор той же команды возвращает состояние начатой операции, не запускает новую. Принудительное переключение ускоряет текущую замену, прерывая фазу ожидания запросов, а не создаёт параллельную замену. Идентификаторы и правила распознавания повторов задаются в API-контракте.
7. **Отмена по фазам.** Пока операция ждёт завершения запросов, отмена возвращает обслуживание старой моделью. После начала выгрузки автоматического возврата нет: старая модель потребует отдельной загрузки. Отмена загрузки новой модели останавливает её запуск, после завершения остановки сервис остаётся без активной модели. Нельзя объявлять операцию завершённой до подтверждения прекращения запуска/процесса. Контракт отображения промежуточных фаз уточняется в API и UI.
8. **Ошибка загрузки.** Если старая уже выгружена, а новая не загрузилась, core показывает причину и остаётся без активной модели. Возврат к предыдущей — явное действие пользователя. Автоматически менять параметры пресета, снижать требования модели или останавливать сторонние процессы, занявшие GPU, нельзя. Ресурсы машины могут одновременно использовать секретарь, медиа и другие приложения; core не предполагает эксклюзивного владения GPU.
9. **Запуск и сбой.** После запуска core активной модели нет; последний выбранный пресет сохраняется, загрузка выполняется кнопкой в web-client. После падения llama-server показывается ошибка, модель автоматически не перезапускается. Сохранённый выбор не означает работающий экземпляр. Обнаружение оставшихся процессов после падения core и согласование фактического состояния уточняются в задаче хранения/запуска, с сохранением запрета одновременного запуска второго экземпляра.
10. **Наблюдаемое состояние.** Интерфейс должен различать отсутствие активной модели, готовую модель, ожидание завершения запросов, выгрузку, загрузку и ошибку операции. Сохранённый пресет, цель текущей операции и фактически готовая модель не взаимозаменяемы. Точные DTO и сигналы готовности/остановки определяются в API-контракте и проверяются прототипом; системная загрузка VRAM сама по себе не доказывает готовность модели.
