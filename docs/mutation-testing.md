# Mutation testing

Mutation testing — scheduled/release-проверка способности тестовой базы замечать изменения
поведения в четырёх начальных областях риска: нормализации HTTP-ответа, HTTP-маршрутизации,
протоколе сообщений `daevox.v1` и терминальных состояниях Worker Pool.

## Выбор runner

Вместо универсального mutation-пакета проект использует небольшой ESM harness для Node.js 26
из `test/mutation/`. Начальная область — вручную проверенный каталог из 19 мутаций границ, кодов
ошибок, маршрутизации и cleanup. Harness не требует dev- или runtime-зависимостей, запускает
каждый mutant в новой временной копии проекта и использует V8 coverage от Node для разделения
`no-coverage` и `survived`. Поэтому runner воспроизводим на заявленной платформе проекта, а
mutation-инструменты не входят в npm tarball.

Запуск mutants для целевых модулей или связанных тестов, изменённых в рабочем дереве:

```sh
npm run mutation:changed
```

В pull-request CI переменная `MUTATION_BASE` добавляет committed-изменения относительно
базовой ссылки. Полный scheduled/release-профиль запускается командой:

```sh
npm run mutation:full
```

Обе команды сохраняют машиночитаемый и Markdown-отчёты в `test/mutation/results/`. Каждая запись
содержит строку исходника и сценарий. `survived` mutant завершает команду с ошибкой, пока его
не обнаружит тест наблюдаемого поведения либо эквивалентность не будет зафиксирована ниже и
mutant не будет удалён из исполняемого каталога.

## Baseline и gate

Начальная baseline для Node.js 26 хранится в `test/mutation/baseline.json`. Score считает `killed` и
`timeout` обнаруженными, а `survived` и `no-coverage` — необнаруженными. Начальный gate 80%
намеренно ниже baseline и не требует немедленных 100%. После стабильных scheduled-прогонов
`gate` постепенно повышается к `nextGate`; зафиксированные счётчики обновляются только по
полному прогону на неизменном дереве.

## Исключения

Каталог намеренно исключает механические изменения диагностики, имён приватных полей,
форматирования и защитных `settled`-проверок, для которых повторное разрешение Promise
ненаблюдаемо. Также исключена перестановка `clearTimeout` и соседнего удаления listener: оба
порядка синхронно освобождают одинаковые ресурсы и эквивалентны по поведению. Эти дублирующие
или эквивалентные mutants не входят в score.

Ещё два кандидата признаны эквивалентными по результату начального baseline-прогона. Удаление
явного подавления тела для статуса 204 ненаблюдаемо, поскольку HTTP transport Node сам подавляет
такое тело. Замена синхронной ветки `timeout === 0` уже существующим таймером с нулевой задержкой
всё равно отклоняет публичный Promise тем же `JobTimedOutError`; создание Worker и порядок
внутреннего таймера являются деталями реализации и не подходят для утверждений теста.
