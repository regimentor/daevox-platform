# Системное тестирование

## Fuzzing повреждённого HTTP и WebSocket-ввода

Короткий фиксированный corpus отделён от unit- и e2e-тестов и запускается отдельно:

```sh
npm run fuzz:corpus
```

Тесты самого fuzz harness входят в общую команду `npm run test:checks` и находятся в
`test/fuzz/corpus.test.ts`.

Corpus передаёт повреждённые HTTP-запросы и WebSocket frames через реальные TCP-соединения.
Он покрывает fragmentation и continuation, control frames между фрагментами, opcode, RSV,
mask, 7/16/64-bit длины, неполные frames, UTF-8, close frames, ping flood, oversized data,
случайные JSON-envelope, request target и percent-encoding, конфликтующий framing,
`Content-Length`, JSON/UTF-8, оборванное тело, длинные headers и медленную передачу около
`bodyLimit`. После recoverable WebSocket-ошибки то же соединение обязано обработать корректное
сообщение; после всего corpus новое HTTP-соединение и новый WebSocket handshake подтверждают
работоспособность приложения.

Расширенный seed-based профиль добавляет 200 генеративных cases и запускается отдельно:

```sh
npm run fuzz:full -- --seed 3672178701
```

По умолчанию один case ограничен 64 KiB входных данных, глубиной JSON 4 (допустимый максимум
16), 1000 операциями и общим timeout 1000 мс. Параметры можно безопасно уменьшить или
увеличить в пределах защитных границ:

```sh
npm run fuzz:full -- --seed 3672178701 --cases 500 --depth-limit 6 --case-timeout-ms 1500
```

Ошибка всегда содержит seed, индекс и имя case. Fuzzer сохраняет объединённые входные байты
в `test/fuzz/failures/*.bin` и JSON с исходными границами, chunk boundaries, ожиданием и готовой
командой replay. Case можно точно повторить из артефакта либо заново получить по seed и
индексу:

```sh
npm run fuzz:replay -- --replay ./test/fuzz/failures/failure-3672178701-42.json
npm run fuzz:full -- --seed 3672178701 --case-index 42
```

Успех означает, что каждый case получил допустимый HTTP-статус, ожидаемый WebSocket close code
с фактическим закрытием соединения или контролируемый reset до timeout. Прогон дополнительно
проверяет `uncaughtException`, `unhandledRejection`, баланс WebSocket connect/disconnect и
отсутствие оставшихся клиентских соединений. Две негативные контрольные мутации подтверждают,
что harness обнаруживает пропущенную проверку mask WebSocket frame и нарушение HTTP
`bodyLimit`.

## Stress очереди задач и WebSocket-сессий

Полный профиль запускается отдельно и не входит в `npm run check`:

```sh
npm run stress
```

Для быстрой проверки самого сценария предназначен ограниченный профиль:

```sh
npm run stress:smoke
```

Нагрузка растёт фиксированными ступенями concurrency `1,4,8,16,24` по 1000 мс, после чего
повторяется первая ступень восстановления. Для задач отдельно проверяются короткая (2 мс),
длинная (40 мс) и смешанная длительности при `poolSize` 1, около
`availableParallelism()` и на один выше. Ограниченная очередь заполняется ровно до
`queueSize=32`: порядок подтверждается результатами задач, лишняя задача обязана получить
публичный `JobQueueFullError`, затем новая задача подтверждает восстановление.

WebSocket-профили измеряют handshake, idle-сессии, последовательный поток одной сессии,
параллельные потоки разных сессий, массовое отключение и переподключение. Отдельно проверяются
публичные результаты `UNKNOWN_EVENT`, close code `1009` для слишком большого сообщения и
отклонённый handshake с неверным subprotocol. Смешанный профиль одновременно выполняет
обычный HTTP-запрос, независимое WebSocket-событие и длинную задачу.

Application events дополнительно проходят два встроенных профиля. Throughput ramp смешивает
HTTP- и WebSocket-producers, направляет события быстрым и медленным listener, измеряет время
ожидания mailbox и после каждой ступени сверяет принятые и обработанные идентификаторы, FIFO,
дубли и ожидаемые ошибки handler. Shutdown-chaos использует сохранённый в artifact seed,
выполняет 4 итерации в smoke и 20 в полном режиме и для каждой требует равенство
`accepted = handled + dropped + abortedActive` без `unhandledRejection`.
Для точного повтора transport-решений seed из artifact передаётся командой
`npm run stress:smoke -- --event-chaos-seed <seed>`; artifact сохраняет seed, порядок решений,
счётчики и сгруппированные причины producer-отказов.

Каждая ступень сохраняет throughput, p50/p95/p99 latency, error rate, queue wait, execution
time, RSS, heap, event-loop lag, число клиентских соединений и число фактически наблюдавшихся
Worker. Первая ступень задаёт локальную базу. Ступень считается деградировавшей при error rate
выше 5%, росте p95 latency более чем в 2,5 раза или queue wait более чем в 4 раза. Для
субмиллисекундных измерений используются нижние базы 1 мс latency и 0,5 мс queue wait;
единичный максимальный пик не определяет границу. Перед recovery изолированный процесс
запрашивает GC. После снижения нагрузки p95 обязана быть не
выше 1,5 базовой, queue wait — не выше 2 базовых, RSS — не более чем на 128 MiB плюс 16 MiB
на каждый созданный и сохраняемый пулом Worker, а heap — не более чем на 32 MiB выше базы.
Артефакт указывает последнюю устойчивую и первую
деградировавшую ступени и результат восстановления.

Полный сценарий ограничен concurrency 24, 128 соединениями, `availableParallelism()+1`
Worker, RSS 768 MiB и общим watchdog 120 секунд. Настройки ступеней можно безопасно уменьшить:

```sh
npm run stress -- --steps 1,2,4 --step-ms 500 --output ./test/stress/results/local.json
```

JSON-артефакты сохраняются в игнорируемом каталоге `test/stress/results/`. При превышении памяти,
общей длительности, ошибке ожидаемого публичного контракта или зависании дочерний процесс
аварийно завершается с ненулевым кодом.

## Воспроизводимые benchmarks

Короткий профиль для обычного CI и локальной проверки:

```sh
npm run benchmark:smoke
```

Стабильный профиль для незагруженного выделенного окружения:

```sh
npm run benchmark:full
```

Каждый из четырёх профилей запускается в отдельном дочернем процессе и проходит фазы warm-up,
измерения и cooldown:

- `http-json` — небольшой JSON request/response;
- `http-body-limit` — JSON размером 65 532 байта при `bodyLimit` 65 536 байт;
- `websocket` — последовательный request/response `daevox.v1` на каждой из восьми сессий;
- `job` — короткая CPU-bound задача в прогретом пуле из двух Worker.

Smoke использует 150/300/50 мс на фазы, full — 1000/3000/250 мс. JSON-артефакт
сохраняется в игнорируемый каталог `test/benchmark/results/`; путь выводится в конце сводки. Он
содержит версии Node.js и ОС, архитектуру, модель и число CPU, fingerprint окружения,
concurrency, pool size, размеры сообщений, длительности фаз, PID каждого отдельного процесса,
throughput, error rate, latency p50/p95/p99, event-loop lag, CPU и RSS. Job-профиль также
содержит отдельные p50/p95/p99 времени ожидания очереди и исполнения в Worker.

Версионируемый `test/benchmark/baseline.json` относится только к указанному в нём full-профилю и
точному fingerprint однородного окружения. При несовпадении режима или fingerprint
performance gate помечается `skipped`; абсолютный RPS между машинами не сравнивается. Любая
ошибка операции всё равно проваливает запуск. Начальные относительные пороги заданы явно в
`test/benchmark/config.ts`: падение throughput более 25%, рост p95 latency более 35% или рост error
rate более чем на один процентный пункт. Для job тот же порог p95 отдельно применяется к
ожиданию очереди и исполнению.

Baseline обновляется только на незагруженной целевой машине после нескольких стабильных full-
прогонов и осознанной проверки причины изменения:

```sh
npm run benchmark:full -- --update-baseline --confirm-baseline-update
```

После обновления нужно сохранить новый baseline вместе с описанием причины. Контрольную
чувствительность gate можно проверить искусственной задержкой; команда обязана завершиться с
ненулевым кодом и перечислить относительные регрессии:

```sh
npm run benchmark:full -- --inject-delay-ms 2
```

## Гонки отмены, timeout, результата и close

Команда воспроизведения:

```sh
npm run test:races
```

Короткий CI-профиль выполняет по три итерации каждого порядка событий. `RaceJob` передаёт
между основным потоком и Worker четыре барьера в `SharedArrayBuffer`: начало выполнения,
разрешение подготовки результата, готовность результата и разрешение завершения или падения
Worker. Состояние очереди подтверждается тем, что вторая задача не достигает своего барьера
начала, пока первая занимает единственный слот пула. После каждого терминального события
следующая задача подтверждает освобождение слота и, когда требуется, восстановление Worker.

Проверяются оба порядка для результата/отмены, результата/timeout, отмены/timeout, падения
Worker/отмены, падения Worker/timeout и `JobRunner.close()` с каждым терминальным событием.
Каждый публичный Promise сохраняет ровно одно наблюдаемое settlement; сообщение ошибки
содержит сценарий, порядок и номер итерации. Локальные timeout задач являются частью
проверяемого контракта, а timeout ожидания барьера служит только watchdog зависшего теста.

Транспортный профиль отменяет реальные HTTP-запросы во время чтения тела, HTTP-обработчика,
ожидания задачи и передачи большого ответа. WebSocket-сессия закрывается во время
WebSocket-обработчика, после чего обработчик завершается без позднего сообщения, а
`onDisconnect` наблюдается ровно один раз. Отдельно повторяются конкурирующие
`Application.listen()`/`close()`, закрытие до запуска и ошибка запуска на занятом порту.
Успешный прогон не оставляет Worker, соединения или необработанные поздние ошибки.

## Graceful shutdown под совместной нагрузкой

Команда воспроизведения:

```sh
npm run test:shutdown
```

Сценарий запускает четыре итерации с concurrency 2. В каждой итерации одно `Application`
обслуживает реальные HTTP- и WebSocket-соединения и владеет пулом из двух Worker. До
`Application.close()` наблюдаемыми барьерами подтверждаются:

- быстрый и долгий HTTP-обработчики;
- две выполняющиеся задачи, одна из которых ограничена job timeout;
- одна ожидающая задача;
- принятая WebSocket-сессия с выполняющимся долгим обработчиком.

Проверка измеряет полное время `close()` и использует настроенные
`http.shutdownTimeout`, job timeout, `terminationGracePeriod` и jobs `shutdownTimeout` как
контрактные границы. Дополнительный watchdog только ограничивает зависший тест и не служит
доказательством наступления состояния.

Успешный прогон подтверждает, что после начала shutdown не принимаются новые HTTP-соединения
и WebSocket upgrades; быстрая работа завершается; пережившая границы работа отменяется или
принудительно завершается; WebSocket-сессия закрывается кодом `1001`; её сигнал отменён, а
`onDisconnect` вызван один раз. Несколько конкурентных `close()` должны вернуть один Promise,
а все созданные запросы, сессии и задачи — получить терминальный результат до конца итерации.

## Soak утечек ресурсов

Короткий локальный профиль проверяет mixed-load harness примерно за четыре секунды:

```sh
npm run soak:short
```

Scheduled-профиль предназначен для однородного выделенного CI-окружения, длится четыре часа,
имеет общий timeout четыре часа пять минут и не входит в `npm run check`:

```sh
npm run soak:scheduled
```

Оба профиля непрерывно чередуют HTTP request/response, WebSocket connect/message/disconnect и
успешные, отменённые клиентом и завершившиеся по timeout задачи. WebSocket-сессии регулярно
пересоздаются; количество `onConnect` и `onDisconnect` сверяется после `Application.close()`.
Каждый transport-handler также отправляет внутреннее событие одному из двух listener. Быстрый
listener выполняется синхронно, медленный добавляет задержку 2 мс, а каждое 257-е событие
завершается ожидаемой ошибкой после фиксации обработки. Harness хранит только монотонные order,
счётчики и checksum, поэтому объём event-accounting не растёт с длительностью scheduled-прогона.
Каждый период сохраняет RSS, heap used, event-loop lag p95/p99, active handles и их типы,
listener, timer, клиентские соединения, наблюдавшиеся Worker, throughput по виду операции и
общую latency p50/p95/p99.

Первые 15 минут scheduled-профиля считаются разогревом. После разогрева устойчивым ростом
считается линейный наклон, превышающий порог при росте как минимум в 75% соседних интервалов.
Это исключает единичное ступенчатое расширение heap. Для однородной CI-машины заданы пороги:

- heap used — не более 256 KiB/мин;
- RSS — не более 512 KiB/мин;
- отношение p95 последней трети к первой трети — не более 1,35;
- отношение p99 последней трети к первой трети — не более 1,5;
- ни одной неожиданной ошибки mixed workload;
- accepted/handled и checksum application events совпадают, FIFO violations, duplicates, drops и
  queue rejections отсутствуют, expected/observed handler errors совпадают;
- после `Application.close()` нет прироста active handles, listener, timer, соединений и Worker
  относительно состояния до создания приложения.

JSON временного ряда и итог каждого порога записываются в `test/soak/results/`. При провале рядом
создаётся отдельный diagnostics JSON со списком active handles/resources, финальными
счётчиками, ошибками и конфигурацией контрольной утечки. Чувствительность resource audit
проверяется отдельной командой, которая запускает штатный прогон и отрицательные контроли
listener, timer и socket:

```sh
npm run test:soak-harness
```

Отдельный контроль можно воспроизвести напрямую; ожидается код выхода `1` и путь к diagnostic
artifact:

```sh
npm run soak:short -- --inject-leak listener
npm run soak:short -- --inject-leak timer
npm run soak:short -- --inject-leak socket
```

Длительность, разогрев, период измерений и cadence ожидаемых event-ошибок можно временно
переопределить аргументами `--duration-ms`, `--warmup-ms`, `--sample-interval-ms` и
`--event-error-every`; итоговый artifact schema v2 всегда содержит фактически использованную
конфигурацию и `summary.applicationEvents`.
