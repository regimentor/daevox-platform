# Документация предметной области

Правила использования документации предметной области инженерными навыками при изучении кодовой базы.

## Что читать перед исследованием

- Корневой `CONTEXT-MAP.md`, если он существует: он указывает на `CONTEXT.md` отдельных контекстов. Следует прочитать файлы, относящиеся к исследуемой области.
- Связанные общесистемные архитектурные решения из корневого `docs/adr/`.
- Связанные контекстные ADR внутри соответствующего workspace, например `lib/framework/docs/adr/`.

Если этих файлов нет, следует продолжить работу без предупреждений и без предложения создать их заранее. Навык `/domain-modeling` создаёт их по мере необходимости, когда определяются термины или принимаются решения.

## Структура файлов

Репозиторий использует многоконтекстную структуру:

```text
/
├── CONTEXT-MAP.md
├── docs/adr/                     ← общесистемные решения
├── apps/
│   └── <application>/
│       ├── CONTEXT.md
│       └── docs/adr/             ← решения контекста
└── lib/
    └── <library>/
        ├── CONTEXT.md
        └── docs/adr/             ← решения контекста
```

Доступные контексты перечислены в корневом `CONTEXT-MAP.md`. Архитектурные решения framework
находятся в `lib/framework/docs/adr/`.

## Использование терминов глоссария

Если результат работы называет понятие предметной области — например, в заголовке задачи, предложении рефакторинга, гипотезе или названии теста, — следует использовать термин из соответствующего `CONTEXT.md`. Нельзя заменять его синонимами, которые глоссарий явно отвергает.

Если нужного понятия нет в глоссарии, следует проверить, действительно ли оно относится к проекту, либо отметить пробел для `/domain-modeling`.

## Конфликты с ADR

Если предлагаемая работа противоречит существующему ADR, конфликт следует обозначить явно, а не переопределять решение молча.
