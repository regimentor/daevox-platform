# HTTP transport и выполнение HTTP-обработчиков

## Назначение

Добавить принадлежащий `Application` HTTP transport на `node:http`: запуск слушателя, преобразование входящего запроса в `HttpRequestContext`, сопоставление HTTP-маршрута, создание HTTP-контроллера, выполнение HTTP-обработчика, нормализацию `HttpResponse` и корректное завершение работы. Добавить example-приложение, которое по HTTP запускает задачу в принадлежащем приложению `Job Runner`.

## Application и конфигурация

`Application` принимает существующий объект `jobs` и новый объект `http`:

```js
const app = new Application({
  jobs: {},
  http: {
    bodyLimit: 1024 * 1024,
    shutdownTimeout: 30_000,
    onError(error, ctx) {
      console.error(error, ctx);
    },
  },
});
```

- `bodyLimit` — конечное неотрицательное целое число байтов; значение по умолчанию — 1 MiB. При `0` допускается только пустое тело.
- `shutdownTimeout` — конечное неотрицательное число миллисекунд; значение по умолчанию — 30 секунд.
- `onError` — необязательная функция наблюдаемости для неожиданных ошибок.
- Неизвестные поля `http` и неверные значения синхронно отклоняются `InvalidHttpOptionsError`.
- Отдельный тайм-аут одного HTTP-запроса не поддерживается.

## Жизненный цикл HTTP transport

```js
const address = await app.listen({
  port: 3000,
  host: '127.0.0.1',
});
```

- `listen()` принимает объект ровно с `port` и необязательным `host`; `host` по умолчанию равен `127.0.0.1`.
- `port` допускает `0`, чтобы операционная система выбрала свободный порт.
- Promise разрешается только после события `listening` и возвращает `{ address, family, port }` фактического TCP-адреса.
- Приложение может успешно запуститься без зарегистрированных HTTP-контроллеров; все запросы получают `404`.
- После начала первого `listen()` регистрация HTTP-контроллеров запрещена.
- Второй или конкурентный `listen()` запрещён.
- Ошибка запуска, включая ошибку привязки адреса, переводит приложение в необратимое failed-состояние; повторный `listen()` запрещён.
- После начала `close()` регистрация и запуск запрещены.
- Нарушения состояния отклоняются публичным `ApplicationStateError`.

`Application.close()` является идемпотентным и возвращает один Promise для всех конкурентных вызовов:

1. прекращает принимать новые HTTP-соединения;
2. ожидает активные HTTP-запросы не дольше `http.shutdownTimeout`;
3. после тайм-аута отменяет сигналы оставшихся запросов и закрывает их соединения;
4. после завершения HTTP-запросов закрывает принадлежащий приложению `Job Runner` по его собственной политике shutdown.

`close()` до `listen()` также необратимо закрывает приложение и `Job Runner`. Если `close()` вызван во время запуска, он ждёт исход запуска и затем завершает transport; ошибка запуска не мешает освобождению остальных ресурсов. После закрытия приложение нельзя запустить повторно.

## HTTP-контроллер

После сопоставления HTTP-маршрута для каждого HTTP-запроса создаётся новый экземпляр класса:

```js
new HttpController({ jobRunner });
```

- Передаётся реальный внутренний `JobRunner` с полными методами `run()` и `close()`.
- Вызов контроллером `jobRunner.close()` намеренно закрывает общий пул задач приложения.
- `HttpControllerBase` не допускает прямого создания экземпляра.
- Конструктор базы принимает объект ровно с `{ jobRunner }`, отклоняет неизвестные поля и сохраняет `jobRunner` в собственном доступном только для чтения свойстве.
- Пользовательский класс по-прежнему обязан напрямую наследовать `HttpControllerBase`.
- Ошибка конструктора контроллера считается неожиданной: HTTP-обработчик не вызывается, клиент получает `500`, ошибка передаётся в `onError`, другие запросы продолжают обрабатываться.

## Контекст HTTP-запроса

HTTP-обработчик получает новый объект `HttpRequestContext`:

```js
{
  method,
  path,
  params,
  query,
  headers,
  body,
  signal,
}
```

- `method` — нормализованный HTTP-метод в верхнем регистре.
- `path` — pathname запроса без query string.
- `params` — замороженные декодированные параметры сопоставленного HTTP-маршрута.
- `query` — новый `URLSearchParams`, сохраняющий повторения и порядок.
- `headers` — новый WHATWG `Headers`.
- `body` — разобранное JSON-значение либо `undefined` для пустого тела.
- `signal` — `AbortSignal` запроса.
- `IncomingMessage`, `ServerResponse`, socket и IP-адрес в контекст не входят.

Сигнал отменяется при преждевременном отключении клиента во время чтения тела, выполнения HTTP-обработчика или записи ответа, а также при принудительном HTTP shutdown. Отключение клиента не передаётся в `onError`, если ответ уже невозможно отправить. Связь задачи с запросом всегда явная: обработчик самостоятельно передаёт `ctx.signal` в `jobRunner.run()`.

## Чтение JSON-тела

- Непустое тело принимается для любого HTTP-метода, если `Content-Type` равен `application/json` либо имеет суффикс `+json`.
- Параметры media type разрешены; поддерживается только UTF-8. Неподдерживаемый media type или charset даёт `415`.
- Пустое тело даёт `body: undefined`.
- Некорректный JSON даёт `400`.
- Превышение `bodyLimit` даёт `413`; считаются фактически прочитанные байты, а не только `Content-Length`.
- Транспортные ошибки чтения и отмена очищают listeners и не оставляют выполняющийся HTTP-обработчик.

## Сопоставление HTTP-маршрутов

- Явно зарегистрированные HTTP-маршруты имеют приоритет.
- При отсутствии явного `HEAD` используется совпадающий `GET`; HTTP-обработчик выполняется, но тело не отправляется.
- При отсутствии явного `OPTIONS` для известного пути transport отвечает `204` и заголовком `Allow`.
- Известный путь с неподдерживаемым методом даёт `405` и `Allow`.
- Неизвестный путь даёт `404`.
- `Allow` детерминированно перечисляет явные методы, неявный `HEAD` при наличии `GET` и автоматический `OPTIONS`.
- Некорректное percent-кодирование URL даёт `400`.

Для поддержки `405`, `HEAD` и `OPTIONS` внутренний HTTP-слой может расширить возможности `HttpRouter`, но маршрутизатор остаётся внутренним каталогом и не выполняет HTTP-обработчики.

## Выполнение HTTP-обработчика

- Найденный собственный метод контроллера вызывается с `HttpRequestContext` и `this`, равным новому экземпляру контроллера.
- Синхронные и асинхронные результаты обрабатываются одинаково.
- Ожидаемая ошибка выражается публичным `HttpError`; остальные исключения считаются неожиданными.
- Фреймворк не сопоставляет ошибки задач с HTTP-статусами автоматически: это политика HTTP-обработчика.

## HttpResponse

HTTP-обработчик обязан вернуть объект следующей формы:

```js
{
  status: 200,
  headers: new Headers(),
  body: { ok: true },
}
```

- `status` обязателен и является целым числом от `200` до `599`.
- `headers` необязателен; если присутствует, обязан быть экземпляром WHATWG `Headers`.
- `body` необязателен; поддерживаются JSON-совместимые значения, строки, `Buffer` и `Uint8Array`.
- Объект ответа допускает только поля `status`, `headers` и `body`; неизвестные поля являются нарушением контракта.
- Необъектный результат, неверное поле, неподдерживаемое тело и ошибка JSON-сериализации считаются нарушением контракта и дают стабильный `500` через общий путь неожиданных ошибок.
- `body: undefined` означает отсутствие тела. Top-level JSON-значение без JSON-представления, `BigInt`, циклический объект и иная ошибка сериализации дают `500`; вложенные `undefined` обрабатываются обычной семантикой JSON.
- JSON получает default `application/json; charset=utf-8`, строка — `text/plain; charset=utf-8`, байты — `application/octet-stream`.
- Явно заданный `content-type` сохраняется без проверки соответствия телу.
- `Content-Length`, `Transfer-Encoding` и `Connection` принадлежат фреймворку и запрещены в пользовательских headers.
- Тело полностью нормализуется и сериализуется до отправки заголовков; потоковые и частичные ответы не поддерживаются.
- Для `HEAD`, `204` и `304` тело не отправляется. Для `HEAD` вычислимый `Content-Length` соответствует сериализованному телу результата `GET`.

## HttpError и обработка ошибок

Публичная ожидаемая ошибка создаётся так:

```js
throw new HttpError(
  422,
  {
    headers: new Headers({ 'x-error-code': 'INVALID_VALUES' }),
    body: { error: 'Invalid values' },
  },
  { cause },
);
```

- Статус `HttpError` является целым числом от `400` до `599`.
- `headers` и `body` следуют контракту `HttpResponse`; `cause` не раскрывается клиенту.
- `HttpError` доступен прямым публичным импортом и не вызывает `onError`.
- Неожиданная ошибка, ошибка контроллера или нарушение контракта ответа вызывает `onError(error, ctx)` и даёт стабильный JSON-ответ `500` без `name`, `message`, `stack` и `cause` исходной ошибки.
- HTTP-ответ не ждёт завершения Promise из `onError`.
- Синхронная ошибка или отклонение Promise самого `onError` перехватывается и передаётся в `console.error`, не меняя ответ клиенту.

Инфраструктурные ошибки имеют единый JSON-формат `{ "error": "..." }`:

- неверное кодирование URL или JSON — `400`;
- неизвестный путь — `404`;
- неподдерживаемый метод — `405`;
- превышение тела — `413`;
- неподдерживаемый media type или charset — `415`;
- неожиданная ошибка — `500`.

`InvalidHttpOptionsError`, `HttpError` и `ApplicationStateError` являются публичными классами, доступны прямыми импортами и поддерживают `instanceof`.

## Example-приложение

```text
examples/jobs-http/
├── JobsController.js
├── SumJob.js
└── main.js
```

В `package.json` добавляется команда `example:jobs-http`, запускающая `node examples/jobs-http/main.js`.

`POST /jobs/sum` принимает JSON `{ "values": [1, 2, 3] }`. HTTP-контроллер проверяет, что `values` является массивом конечных чисел, и при нарушении бросает `HttpError(422, ...)`. Затем он вызывает:

```js
const result = await this.jobRunner.run(SumJob, ctx.body, {
  signal: ctx.signal,
  timeout: 5_000,
});
```

`SumJob` вычисляет сумму в Worker и возвращает `{ sum }`. Успешный HTTP-ответ имеет статус `200` и JSON-тело `{ "sum": 6 }`. README показывает запуск example и пример запроса.

## Проверки

- Unit-тесты покрывают конфигурацию, `HttpControllerBase`, нормализацию ответа, `HttpError` и состояние приложения.
- Integration-тесты на реальном ephemeral-порту покрывают запуск, контекст, JSON, маршрутизацию, выполнение контроллера, запуск задачи, отмену клиента, ошибки и graceful shutdown.
- Проверяется отсутствие незакрытых серверов, соединений, timers и Worker после `close()`.
- Все исходники и тесты пишутся только на JavaScript в файлах `.js`; используются только встроенные возможности Node.js.
- `npm run check` завершается успешно.

## Вне scope

- Потоковые ответы, файлы, Server-Sent Events и WebSocket.
- Multipart, form-urlencoded, текстовое и сырое тело входящего запроса.
- Публичный HTTP-маршрутизатор и прямой доступ к `node:http` объектам.
- Middleware, dependency injection container и пользовательские transport adapters.
- Тайм-аут отдельного HTTP-запроса и настройки конкретного HTTP-маршрута.
- TLS, HTTP/2, Unix sockets, multiple listeners и повторный запуск приложения.
- Автоматическое сопоставление ошибок задач с HTTP-статусами.
- Fire-and-forget задачи, идентификаторы задач и хранение их результатов.
