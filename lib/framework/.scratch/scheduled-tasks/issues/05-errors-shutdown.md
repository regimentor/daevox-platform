# Определить ошибки, отмену и завершение ScheduledTask

Labels: wayfinder:grilling
Status: resolved

Parent: [Проработать концепцию запланированных задач ScheduledTask](../map.md)

## Question

Как наблюдать ошибки конструктора и run, продолжается ли расписание после ошибки и нужны ли timeout и retry?

После согласования пропуска перекрывающихся запусков уточнить наблюдаемость: достаточно ли
сообщения об ошибках или приложению также нужны уведомления о пропущенном срабатывании,
начале и завершении запуска? Нужна ли публичная инспекция активности и следующего запуска,
либо её следует исключить из концепции? Привязать наблюдения к имени класса ScheduledTask,
не раскрывая внутренний scheduler. Учитывать принятое разрешение разных классов с одинаковым
именем: достаточно ли имени в контексте ошибки или нужно также передавать ссылку на класс?

Когда close останавливает новые срабатывания и сколько ждёт активные run? Как сохранить их доступ к events и jobRunner до окончания grace-фазы? Что происходит с поздним rejection и зависшим run?

Решить, нужен ли AbortSignal и как передать его при исходном контракте run(appState). Не предполагать возможность принудительно прервать пользовательский код в основном потоке.

Результат должен явно описать дополнение принятого [порядка shutdown](../../../docs/adr/0011-addressed-application-events.md), а не молча изменить его.

## Answer

Согласовано с пользователем в двух раундах обсуждения.

### Ошибки выполнения и наблюдение

- Application принимает `scheduledTasks.onError(error, context)`. По умолчанию ошибки
  выводятся через console.error. Ошибка конструктора или run передаётся без обёртки.
- Контекст содержит `{ taskClass, taskName, phase }`. Ссылка taskClass различает
  зарегистрированные классы с одинаковым именем. Phase принимает constructor, run или shutdown.
- Ошибка конструктора или завершение run с ошибкой завершает текущую попытку. Расписание
  продолжает работать; автоматические retry не вводятся.
- Исключение или отклонённый Promise самого onError перехватывается и выводится в console.error,
  не ломая планировщик или shutdown. Ошибка наблюдателя не направляется рекурсивно в onError.
- Отдельные уведомления о пропусках, начале и успешном завершении запусков, публичный каталог
  расписаний и инспекция активности/следующего запуска не вводятся.

### Выполнение и отмена

- Timeout обычного выполнения run отсутствует. Пока Promise run не завершён, следующие
  срабатывания той же ScheduledTask пропускаются по принятой политике выполнения.
- Run получает второй аргумент `ScheduledTaskContext` с `signal: AbortSignal`:
  `run(appState, { signal }): Promise<void>`. Реализация с одним аргументом appState допустима.
  Это согласованное дополнение к первоначальному контракту объявления.
- В начале Application.close() прекращаются новые срабатывания и отменяются сигналы
  активных запусков. AbortSignal предоставляет возможность кооперативно завершить операции;
  сама отмена signal не означает завершения Promise run.

### Завершение приложения

- После ожидания HTTP/WebSocket-операций Application предоставляет оставшимся активным
  ScheduledTask отдельный общий бюджет `scheduledTasks.shutdownTimeout`, по умолчанию 30000 мс.
  Он относится ко всей фазе ожидания ScheduledTask, а не предоставляется последовательно
  каждой задаче. Завершившиеся ранее задачи не требуют ожидания.
- До конца этой фазы events и Job Runner ещё доступны. WebSocket-сессии закрываются
  по существующим правилам; их доступность ради ScheduledTask не продлевается.
- Если все активные run завершились раньше, Application сразу продолжает закрытие.
- По истечении бюджета Application прекращает ожидание ScheduledTask, затем закрывает
  отправку событий, ограниченно опустошает mailboxes и закрывает Job Runner по действующим правилам.
- Каждая всё ещё незавершённая ScheduledTask однократно наблюдается через onError как
  `ScheduledTaskShutdownTimeoutError` с phase shutdown и контекстом соответствующего класса.
  Само превышение этого бюджета не отклоняет Application.close().
- Поздний rejection после прекращения ожидания перехватывается внутри без повторного
  уведомления onError. Позднее завершение не возобновляет расписание.
- Пользовательский код в основном потоке принудительно не останавливается. Зависший
  синхронный код блокирует и выполнение таймеров, поэтому shutdownTimeout не гарантирует
  физическое прерывание или завершение процесса за указанный срок.

### Дополнение принятого порядка shutdown

По отношению к [ADR о внутренних событиях](../../../docs/adr/0011-addressed-application-events.md)
вводится новая фаза ожидания ScheduledTask между transport settlement и закрытием EventSender.
Остановка расписаний и отмена их сигналов происходят уже в начале close. Новый бюджет
добавляется к последовательным независимым бюджетам существующих подсистем; принятый
порядок закрытия событий и Job Runner сохраняется. Здесь записана концепция будущего
расширения; production-код и принятый ADR этим вопросом не изменяются.

## Comments

### Первый раунд обсуждения

Пользователь подтвердил:

- `scheduledTasks.onError(error, context)`, по умолчанию console.error; исходная ошибка
  и контекст `{ taskClass, taskName, phase }`, phase — constructor или run.
  После ошибки расписание продолжает работу без автоматических retry.
- Timeout обычного выполнения run не вводится. До завершения его Promise следующие
  срабатывания той же ScheduledTask пропускаются.
- Второй аргумент run — `ScheduledTaskContext` с AbortSignal:
  `run(appState, { signal }): Promise<void>`. Метод с одним аргументом appState допустим.
- Начало close прекращает новые срабатывания. После ожидания HTTP/WebSocket-операций
  активным ScheduledTask предоставляется отдельный бюджет scheduledTasks.shutdownTimeout,
  по умолчанию 30000 мс, до закрытия событий и Job Runner. WebSocket-сессии закрываются
  по существующим правилам и не остаются доступными ради ScheduledTask.

### Второй раунд обсуждения

Пользователь подтвердил отмену signal сразу при начале close; прекращение ожидания по
shutdownTimeout с однократной ошибкой для каждой незавершённой задачи без отклонения close;
перехват позднего rejection без повторного уведомления; диагностику только через onError
и изоляцию ошибок самого наблюдателя с выводом в console.error.
