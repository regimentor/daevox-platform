# Определить экземпляры и перекрывающиеся запуски

## Question

Создавать новый экземпляр ScheduledTask на каждый запуск, как контроллер, или один на регистрацию, как EventListener?

Если расписание срабатывает каждую секунду, а run занимает десять секунд, запускать параллельно, пропускать срабатывания или ставить их в очередь? Какие ограничения ресурсов нужны между разными ScheduledTask?

Чем считать завершение запуска: settlement run или также окончание Job, который run запустил без await? Как связать это с выбранной политикой повторных срабатываний?

## Answer

Согласовано с пользователем по четырём вопросам о времени жизни и выполнении.

- Каждый допущенный запуск создаёт новый экземпляр ScheduledTask. Экземпляр не
  переиспользуется; сохранение его состояния между запусками не предусмотрено.
  Это stateless-модель запланированной задачи. Согласованный доступ к общему AppState
  сохраняется, но framework не создаёт отдельного межзапускового состояния ScheduledTask.
- Для одной зарегистрированной ScheduledTask в одном Application допускается не более одного
  активного run. Пока возвращённый им Promise не завершён, новые срабатывания этой
  ScheduledTask пропускаются. Для пропущенного срабатывания экземпляр не создаётся.
- Пропуски из-за активного run не ставятся в очередь и не вызывают немедленный повтор
  после его завершения. Следующий запуск ожидает следующего срабатывания cron.
- Активность определяется завершением Promise самого run — успешным или с ошибкой.
  Вызов Job Runner внутри run не заменяет этот критерий.
- Чтобы ScheduledTask оставалась активной до завершения Worker Job, прикладной код
  ожидает `await this.jobRunner.run(...)` либо включает этот Promise в возвращаемую цепочку.
  Job, запущенный без ожидания, не продлевает активность ScheduledTask.
- Разные зарегистрированные ScheduledTask выполняются независимо. Общий лимит активных
  run не вводится; асинхронные операции разных задач могут перекрываться в основном потоке.
  Пул и очередь Job Runner сохраняют собственные ограничения для переданных им Worker Job.
- Ограничение повторного запуска относится к конкретной ScheduledTask, а не к общему
  Job Runner. Расписания разных Application по-прежнему независимы.

Связь с [семантикой cron](02-cron-semantics.md): объединённое просроченное срабатывание
после задержки event loop также подчиняется запрету запуска при активном run.
Оно не создаёт отложенного повтора в обход этого запрета.

Ошибки конструктора и run, зависший Promise, отмена и shutdown определяются в вопросе
[Определить ошибки, отмену и завершение ScheduledTask](05-errors-shutdown.md).

## Comments

Пользователь подтвердил все четыре предложения и уточнил: каждый запуск stateless;
следить нужно за Promise самой задачи, до его завершения следующий запуск той же задачи
не допускается. Состояние экземпляра между запусками сохранять не требуется.
