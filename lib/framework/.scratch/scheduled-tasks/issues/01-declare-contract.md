# Определить объявление ScheduledTask и доступ к окружению

## Question

Как выразить новый артефакт по правилам объявления контроллеров: базовый класс, собственные статические метаданные cron, идентичность и проверки при регистрации?

Исходные требования: один класс — одна запланированная задача; публичный нестатический async run получает AppState; конструктор принимает DI. Вспомогательные методы разрешены (ответ пользователя).

Нужно выбрать точные имена публичных типов и метаданных, необходимость явного имени, сигнатуру и результат run, проверку async-контракта, набор DI. Указаны jobRunner и events; означает ли «полное окружение» также websocket? AppState передаётся в run, а не в конструктор.

Сопоставить собственные prototype-методы, прямое наследование и snapshot metadata с существующими артефактами; не переносить требования Worker Job к metaUrl/default export автоматически.

Контекст: [контроллеры](../../../docs/adr/0005-transport-specific-controllers.md), [внутренние события](../../../docs/adr/0011-addressed-application-events.md), [AppState](../../../docs/adr/0014-application-state-lifecycle.md).

## Answer

Согласовано с пользователем 2026-09-10.

- Прикладной класс напрямую наследует публичный `ScheduledTaskBase` и объявляет собственное
  статическое поле `cron` с шестипольной cron-строкой. Точная грамматика и временная семантика
  определяются в вопросе [Определить семантику шестипольного cron](02-cron-semantics.md).
- Имя запланированной задачи — имя класса (`TaskClass.name`). Отдельное обязательное
  `static name` не вводится. Правила конфликтов имён и повторной регистрации относятся к вопросу
  [Определить регистрацию и активацию расписания](04-registration-lifecycle.md).
- Единственная точка запуска — собственный публичный нестатический метод `run` в prototype.
  Вспомогательные методы разрешены. Унаследованный обработчик, static run или поле со стрелочной
  функцией не заменяют собственный prototype-метод.
- Контракт выполнения — `run(appState): Promise<void>`. Синтаксис `async` необязателен:
  обычный метод, возвращающий Promise, также допустим. Результат запуска не используется.
  Эта договорённость уточняет первоначальную формулировку «async run».
- Конструктор принимает DI-объект `{ jobRunner, events, websocket }`. Базовый конструктор
  предоставляет зависимости через `this.jobRunner`, `this.events`, `this.websocket` по образцу
  HTTP-контроллера. Собственный конструктор необязателен; при объявлении передаёт зависимости
  в `super(options)`.
- `AppState` не входит в constructor DI и передаётся аргументом `run`. Это общий экземпляр
  состояния соответствующего Application.
- ScheduledTask выполняется в основном потоке приложения и может запускать Worker Job через
  встроенный Job Runner. Требования Worker Job к `metaUrl`, отдельному модулю и default export
  не переносятся на ScheduledTask.

Форма объявления (иллюстрация концепции, не реализованный API; MyAppState и RefreshCacheJob —
прикладные типы):

```ts
class RefreshCache extends ScheduledTaskBase {
  static cron = '0 */5 * * * *';

  async run(appState: MyAppState): Promise<void> {
    await this.jobRunner.run(RefreshCacheJob, {});
  }
}
```

Время жизни экземпляра, проверки конфликтов и ошибки выполнения определяются в соответствующих
вопросах карты. Второй аргумент run с контекстом отмены позднее согласован в вопросе
[Определить ошибки, отмену и завершение ScheduledTask](05-errors-shutdown.md).
Реакция на нарушение Promise-контракта подлежит проверке полноты концепции.
