## Question

Что именно означает шестипольная cron-строка: порядок полей, разрешённая грамматика, часовой пояс, сочетание дня месяца и дня недели, невозможные даты?

Как трактовать перевод часов, задержку event loop и пропущенные срабатывания, включая время остановленного приложения? Требуются ли восполнение или сохранение расписания?

Решение должно описывать наблюдаемое поведение независимо от выбора cron-библиотеки. Сторонняя runtime-зависимость требует отдельного обоснования и согласования согласно [платформенному ADR](../../../docs/adr/0001-platform-and-dependencies.md).

## Answer

Согласовано с пользователем по результатам двух раундов обсуждения.

### Формат и календарь

- Принимаются строго шесть полей: секунда, минута, час, день месяца, месяц, день недели.
- Поддерживаются числа, `*`, списки `,`, диапазоны `-` и шаг `/`.
  Воскресенье обозначается `0` или `7`.
- Пятипольные строки, макросы вроде `@daily`, названия месяцев и расширения
  `L`, `W`, `#`, `?` отклоняются.
- Если ограничены оба поля дня месяца и дня недели, между ними действует «или».
  Например, `0 0 9 1 * 1` означает 09:00 первого числа месяца или каждого понедельника.
  Совпадение обоих условий в одну дату не создаёт два срабатывания.
- Расписание без возможной даты запуска отклоняется при регистрации. Например,
  `0 0 9 31 2 *` невозможно, а `0 0 9 29 2 *` допустимо для високосных лет.
  Проверяется выполнимость всего выражения с учётом «или»: ограничение дня недели
  может сделать выражение выполнимым даже при невозможном сочетании дня месяца и месяца.

### Часовой пояс

- Используется локальный часовой пояс процесса, определённый при запуске Application.
  Отдельная настройка часового пояса ScheduledTask не вводится.
- Изменение часового пояса сервера требует перезапуска Application.
- Если при переводе часов вперёд местное время запуска не наступает, запуск пропускается.
- Если при переводе часов назад местное время наступает дважды, каждое наступление
  является отдельным срабатыванием расписания.

### Пропущенные срабатывания

- Запуски за время остановленного приложения не восстанавливаются.
- При задержке работающего приложения, например из-за занятого event loop, несколько
  пропущенных срабатываний объединяются в один просроченный запуск. После него выбирается
  ближайшее будущее срабатывание; очередь исторических пропусков не создаётся.
- Несуществующее местное время при переводе часов не считается просроченным запуском.
- Эти правила определяют срабатывания расписания. Допуск запуска, если предыдущий run
  ещё активен, определяется в вопросе
  [Определить экземпляры и перекрывающиеся запуски](03-execution-policy.md).

Выбор библиотеки или внутреннего алгоритма этим решением не определяется.

## Comments

### Первый раунд обсуждения

Пользователь подтвердил:

- Строго шесть полей: секунда, минута, час, день месяца, месяц, день недели.
- Числа, wildcard `*`, списки `,`, диапазоны `-` и шаг `/`; воскресенье — `0` или `7`.
  Пятипольные строки, макросы, названия месяцев и расширения `L`, `W`, `#`, `?` не принимаются.
- Используется часовой пояс сервера, а не предложенный UTC.
- Если ограничены и день месяца, и день недели, они объединяются через «или».
- За время остановленного приложения запуски не восстанавливаются. Задержка работающего
  приложения приводит к одному просроченному запуску без воспроизведения каждого пропуска.
  Перекрытие с ещё активным run определяется отдельным вопросом карты.

### Второй раунд обсуждения

Пользователь подтвердил локальный часовой пояс процесса, определяемый при запуске
приложения, с перезапуском для изменения пояса; пропуск несуществующего местного времени
и оба срабатывания при повторении времени; отклонение невозможных расписаний при регистрации.
Уточнено правило задержки: один просроченный запуск, затем ближайшее будущее срабатывание.
