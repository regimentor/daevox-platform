# Системное тестирование Daevox Node Framework

## Назначение

Добавить отдельный слой системных проверок поверх существующих unit- и integration-тестов. Проверки должны доказывать работоспособность публичного API из внешнего приложения, корректность общего lifecycle HTTP, WebSocket и задач при конкуренции и отказах, отсутствие деградации производительности и утечек ресурсов, а также способность тестовой базы обнаруживать реальные дефекты.

Инициатива не меняет публичный API фреймворка. Она проверяет контракты `Application`, HTTP-контроллеров, WebSocket-протокола `daevox.v1`, исполнителя задач и пула работников, описанные в README и принятых ADR.

## Общие принципы

- Все тестовые исходники, fixtures и инструменты проекта пишутся только на JavaScript в файлах `.js`.
- Black-box проверки используют только публичный API и реальные HTTP/WebSocket-соединения; импорт внутренних компонентов в них запрещён.
- Конкурентные сценарии синхронизируются наблюдаемыми событиями, барьерами и управляемыми fixtures, а не произвольными задержками.
- Любая случайная генерация принимает и выводит seed, достаточный для точного повторения сбоя.
- Каждый долгоживущий процесс, сервер, socket, timer и Worker освобождается даже при падении проверки.
- Новые runtime-зависимости не добавляются. Необходимость новой dev-зависимости должна быть обоснована в задаче и не должна попадать в публикуемый пакет.
- Производительность оценивается только воспроизводимыми измерениями согласно ADR 0004.
- Нагрузочные проверки разделяют время ожидания в очереди и время исполнения операции, где это возможно.
- Ошибки тестов содержат конфигурацию нагрузки, seed, измеренные показатели и путь к сохранённому артефакту.

## Уровни запуска

### Обычный CI

В обычный CI входят детерминированные black-box e2e, тест установки tarball, короткие lifecycle/race-проверки и короткий smoke benchmark. Их суммарное время должно оставаться достаточно малым для запуска на каждом изменении.

### Scheduled и release CI

Stress, soak, расширенный fuzzing, полные benchmarks и mutation testing запускаются отдельно по расписанию или перед релизом. Они не входят в `npm run check`, если делают локальный цикл разработки существенно медленнее или зависят от стабильности выделенного окружения.

## Наблюдаемые показатели

В зависимости от сценария сохраняются:

- throughput и количество успешных/ошибочных операций;
- p50, p95 и p99 общей задержки;
- время ожидания задачи в очереди и время её исполнения;
- event-loop lag;
- CPU, RSS и heap;
- число открытых соединений, Worker и active handles;
- размер очереди и число принудительных завершений;
- seed, длительность, concurrency и размеры сообщений.

Порог регрессии должен сравниваться с версионируемой базой для одинакового профиля окружения. Абсолютный RPS не используется как переносимый критерий между разными CI-машинами.

## Набор задач

1. Black-box e2e приложения и установка npm tarball.
2. Graceful shutdown под совместной HTTP, WebSocket и Worker-нагрузкой.
3. Гонки отмены, timeout, завершения задачи и `Application.close()`.
4. Короткие воспроизводимые benchmarks с порогами регрессии.
5. Stress-тест очереди задач и WebSocket-сессий.
6. Soak-тест на утечки ресурсов и долговременную деградацию.
7. WebSocket frame fuzzing и HTTP malformed-input fuzzing.
8. Mutation testing для оценки чувствительности тестовой базы.

## Общие критерии приёмки

- Каждый сценарий документирует назначение, нагрузочный профиль, измеряемые показатели, критерий успеха и способ локального повторения.
- Быстрые проверки имеют отдельные npm-команды и могут выполняться в обычном CI.
- Тяжёлые проверки имеют отдельные npm-команды, ограничение длительности и машинно-читаемый результат.
- После каждого прогона приложение и дочерние процессы завершаются без оставшихся Worker, соединений и таймеров.
- Ошибка любой проверки воспроизводится указанной командой без ручного редактирования исходников.
- `npm run check` продолжает успешно завершаться.

## Вне scope

- Сравнение Daevox с другими Node.js-фреймворками.
- Установление маркетинговых показателей производительности.
- Распределённая нагрузка с нескольких физических машин.
- TLS, HTTP/2, WebSocket compression и другие возможности, отсутствующие в публичном API.
- Изменение семантики HTTP, `daevox.v1`, задач или lifecycle ради прохождения синтетического benchmark без отдельного архитектурного решения.
