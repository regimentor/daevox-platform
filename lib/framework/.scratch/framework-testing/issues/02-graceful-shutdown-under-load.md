# Проверить graceful shutdown под совместной нагрузкой

Добавить системные сценарии завершения `Application` при одновременно активных HTTP-запросах, WebSocket-сессиях и задачах пула работников.

## Требования

- Создать управляемые fixtures для быстрого HTTP-ответа, долгого HTTP-обработчика, ожидающей и выполняющейся задачи и долгого WebSocket-обработчика.
- До вызова `Application.close()` дождаться наблюдаемого подтверждения, что все виды работы действительно активны.
- Проверить прекращение приёма новых HTTP-соединений и WebSocket upgrades после начала shutdown.
- Проверить завершение быстрой активной работы в пределах grace period.
- Проверить отмену и принудительное завершение работы, пережившей настроенные `http.shutdownTimeout`, job timeout или termination grace period.
- Проверить закрытие принятых WebSocket-сессий кодом `1001`, отменённый сигнал сессии и однократный вызов `onDisconnect`.
- Проверить согласованный порядок завершения HTTP/WebSocket lifecycle и принадлежащего приложению исполнителя задач.
- Проверить несколько конкурентных вызовов `close()` и завершение всех вызывающих одним результатом.
- Выполнять сценарий многократно с ограниченным concurrency без использования фиксированных `sleep` как условия корректности.

## Критерии приёмки

- Ни один новый запрос, upgrade или запуск задачи не принимается после соответствующей границы shutdown.
- Активная работа либо корректно завершается, либо отменяется согласно публичным timeout-контрактам.
- `onDisconnect` вызывается ровно один раз на принятую WebSocket-сессию.
- `close()` укладывается в вычислимую верхнюю границу настроенных timeout с допустимым техническим запасом.
- После каждого прогона отсутствуют открытые соединения, Worker и зависшие Promise.
- `npm run check` проходит.

## Comments

Реализовано через TDD на подтверждённых публичных швах. Добавлена команда
`npm run test:shutdown`: системный сценарий выполняет четыре итерации с concurrency 2 и
реальными HTTP/WebSocket-соединениями при двух Worker. Управляемые Promise- и
`SharedArrayBuffer`-барьеры подтверждают активность быстрого и долгого HTTP-обработчиков,
долгого WebSocket-обработчика, двух выполняющихся и одной ожидающей задачи до вызова
`Application.close()`.

Проверены отказ новых HTTP-соединений и WebSocket upgrades, завершение быстрой HTTP-работы и
ожидающей задачи в grace period, job timeout с принудительным завершением после termination
grace period, отмена долгого HTTP-обработчика, принудительное завершение Worker после jobs
shutdown timeout, запрет новой задачи после закрытия исполнителя, WebSocket close code `1001`,
отменённый сигнал и однократный `onDisconnect`, порядок lifecycle и единый результат трёх
конкурентных `close()`. Все запросы, задачи и сессии получают терминальный результат в каждой
итерации; произвольные `sleep` не используются. Профиль и способ воспроизведения описаны в
`docs/system-testing.md`. `npm run check` проходит (111 тестов).
