# Добавить короткие воспроизводимые benchmarks и пороги регрессии

Создать benchmark-набор, измеряющий основные пути HTTP, WebSocket и пула работников без изменения архитектуры ради предполагаемой производительности.

## Требования

- Определить отдельные профили: простой HTTP JSON, HTTP JSON около `bodyLimit`, WebSocket request/response и короткая CPU-bound задача в прогретом Worker Pool.
- Запускать каждый профиль в отдельном процессе с фазами warm-up, измерения и cooldown.
- Фиксировать версии Node.js и ОС, число CPU, параметры pool/concurrency, длительность и размеры сообщений.
- Измерять throughput, p50/p95/p99 latency, error rate, event-loop lag, CPU и RSS; для задач раздельно учитывать ожидание и исполнение.
- Сохранять машинно-читаемый JSON-результат и краткую человекочитаемую сводку.
- Добавить короткий smoke-режим и полный стабильный режим для выделенного CI-окружения.
- Добавить версионируемую baseline для однородного окружения и проверку относительной регрессии; начальный допустимый порог документировать и сделать явной конфигурацией.
- Не использовать абсолютный RPS как переносимый gate между разными машинами.
- Описать процедуру обновления baseline только после осознанного подтверждения изменения.

## Критерии приёмки

- Повторные полные прогоны на одной незагруженной машине дают достаточно малый разброс для выбранного порога.
- Искусственно добавленная задержка приводит к провалу regression gate.
- JSON-артефакт содержит всю конфигурацию, необходимую для сравнения прогонов.
- Smoke-режим имеет ограниченную длительность и пригоден для частого запуска.
- Любая оптимизация, предложенная по результатам измерений, оформляется отдельно и ссылается на сохранённый benchmark.
- Новые runtime-зависимости отсутствуют, `npm run check` проходит.

## Comments

Реализован воспроизводимый benchmark-набор без новых зависимостей и изменений runtime.
Команды `npm run benchmark:smoke` и `npm run benchmark:full` последовательно запускают четыре
отдельных процесса: небольшой HTTP JSON, HTTP JSON размером 65 532 байта при `bodyLimit`
65 536, WebSocket request/response `daevox.v1` и короткую CPU-bound задачу в прогретом пуле
из двух Worker. Каждый процесс имеет warm-up, измерение и cooldown и освобождает Application,
соединения и Worker в `finally`.

JSON-артефакт фиксирует fingerprint среды, Node.js/ОС/CPU, параметры фаз, concurrency, размеры
сообщений, pool size и PID процессов, а также throughput, p50/p95/p99 latency, error rate,
event-loop lag, CPU и RSS. Job-профиль через общее монотонное время отдельно измеряет ожидание
очереди и исполнение Worker. Краткая сводка выводится в stdout, результаты сохраняются в
игнорируемый `benchmark/results/`.

Добавлен версионируемый full-baseline для Node.js v26.7.0, Darwin 25.6.0 и Apple M3 Max с 14
CPU. Gate сравнивает только одинаковые режим и точный fingerprint; пороги явно заданы как 25%
для падения throughput, 35% для роста p95 и один процентный пункт для error rate. Два full-
прогона на незагруженной машине прошли gate: изменение throughput было примерно от −4% до +4%,
наблюдаемый p95 оставался внутри порога. Контрольный full-прогон с `--inject-delay-ms 2`
завершился кодом 1 и зарегистрировал регрессии всех профилей. Обновление baseline требует
одновременно `--update-baseline` и `--confirm-baseline-update`; процедура описана в
`docs/system-testing.md`.

Smoke включён в `npm run check`; любая ошибка операции проваливает запуск даже при
несопоставимом baseline. `npm run check` проходит: 120 тестов и четыре smoke-профиля.
