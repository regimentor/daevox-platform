# Сравнение производительности HTTP-фреймворков

## Результат

Измерение выполнено 29 августа 2026 года на Node.js v26.7.0. Один процесс-клиент отправлял
`POST /benchmark` по keep-alive с JSON-телом, 16 параллельными запросами; warmup — 500 ms,
измерение — 2 s. Каждый сервер перезапускался перед своим измерением. Все ответы успешны,
ошибок — 0.

| Реализация                      | Пропускная способность, req/s | p50, ms | p95, ms | p99, ms |
| ------------------------------- | ----------------------------: | ------: | ------: | ------: |
| Node.js `http` (ориентир)       |                        34 544 |   0,424 |   0,808 |   1,039 |
| Daevox                          |                        28 097 |   0,513 |   1,012 |   1,376 |
| Fastify 5.12.1                  |                        28 031 |   0,526 |   0,961 |   1,245 |
| NestJS 12.0.1 / Express adapter |                        27 390 |   0,500 |   1,142 |   1,633 |
| Koa 3.2.1                       |                        27 331 |   0,539 |   0,984 |   1,296 |
| Hono 4.13.5 / Node adapter      |                        27 100 |   0,537 |   1,052 |   1,382 |
| Express 5.2.1                   |                        24 677 |   0,581 |   1,180 |   1,478 |

В этом прогоне Daevox практически совпал с Fastify по throughput: разница +0,24% в пользу
Daevox. Его p95 был примерно на 5,3% выше Fastify, а p99 — на 10,6% выше. Относительно
Express Daevox показал на 13,9% больший throughput, p95 ниже на 14,2%, p99 ниже на 6,9%.

## Методика и границы вывода

Тестовые приложения находятся в этом каталоге. `server.ts` реализует одинаковую конечную точку,
`run.ts` содержит общий генератор нагрузки. Node.js `http` показан как нижняя граница накладных
расходов, а не как фреймворк. NestJS работает через `@nestjs/platform-express`, поэтому его
результат характеризует типичную конфигурацию NestJS на Express, а не Fastify adapter.

Это микробенчмарк маршрутизации и JSON-ответа в одной машине. Он не измеряет middleware,
валидацию, DI, шаблоны, реальные бизнес-операции, WebSocket или worker pool. Один короткий прогон
не заменяет серию повторов; для решения об оптимизации следует повторить benchmark несколько раз,
зафиксировать средние значения и разброс, а также проверить отдельные профили из `test/benchmark`.

## Воспроизводимость

```sh
npm install --prefix benchmark/competitors
BENCHMARK_DURATION_MS=2000 BENCHMARK_WARMUP_MS=500 BENCHMARK_CONCURRENCY=16 \
  node benchmark/competitors/run.ts
```

Версии зафиксированы в `package.json`: [Express](https://www.npmjs.com/package/express),
[Fastify](https://www.npmjs.com/package/fastify), [Koa](https://www.npmjs.com/package/koa),
[Hono](https://www.npmjs.com/package/hono), [NestJS](https://www.npmjs.com/package/@nestjs/core).
